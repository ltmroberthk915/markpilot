## 3. The narrow fix: what the source actually does

* `dsh-markpilot/src-cm6/main.js:2237-2254` — `activateSourceCellSelection(inputView)` returns `false` unless: same view; exactly one selection range; `sel.head` inside a table; not a separator body; and the whole range fits **inside one** cell range (`ranges.findIndex(range => sel.from >= range[0] && sel.to <= range[1])`). It then requires **both** `anchor` and `head` to round-trip through the existing cell codec (`cellSourceOffset(mapped, cellTextOffset(mapped, pos - from)) === pos - from`) — this is what forbids half-escapes and any non-representable offset — and only then dispatches `setActiveCell` + `setTableSel(null)` with `Transaction.addToHistory.of(false)`, i.e. **no new history entry**, no new state field, no timer, and it reuses the existing cell overlay + shared codec by calling `activateCellOverlay(...)` with the preserved source range.
* `main.js:2256-2265` — `searchCellFocus` is unchanged in shape: `focus` handler requires `event.target === inputView.contentDOM` **and** `event.relatedTarget?.closest?.('.cm-search')`, then a single `queueMicrotask` re-checks view identity, `document.hasFocus()`, `activeElement === inputView.contentDOM` and `inputView.hasFocus` before re-taking the cell owner. Nothing in the fix loosens these guards.
* `main.js:5097-5098` — `installSplit({ …, focusSelection: activateSourceCellSelection })`.
* `dsh-markpilot/src-cm6/splitview.js:77-88` — read-only source `mousedown`: `posAtCoords` → `preventDefault()` → master `dispatch({selection:{anchor:pos}})` → `if (!focusSelection?.(a)) a.focus();` → align + highlight. So a successful same-cell/representable split handoff **never** calls the generic CM `focus()`, while every other shape (ordinary source, separator, cross-cell, partial escape, non-representable offset, `posAtCoords` miss) falls through to the old generic `a.focus()` fallback unchanged.
* `tools/quality/split-source-workflows.cjs` — both arms start from a fresh renderer and the recorded input is trusted Chromium input (`transport: 'Trusted Chromium renderer mouse/keyboard input; no OS physical input claim'`). The table arm calibrates the click from the **actual read-only CM** `coordsAtPos(28)` left+0.1 and requires `hit === 28 && char === 'b'` before clicking; the plain arm uses `INITIAL.indexOf('After')+3`. Crucially, there is **no read/wait/frame/repair between the source click and `keyboard.insertText('R')`**, none between `Control+y` and `1`, and each stage asserts full document text (so the neighbours survive), the directional source caret, a real writable owner, and the pane's read-only/same-text invariants; the disk arm waits until the file equals `FINAL`.

Causal scope is therefore exactly what the mutation shows: remove only the split-source-cell-owner routing and the **table** arm goes red with the original error (`immediate R full source / neighbors`, the `R` landing on its own line after the table) while the **ordinary-source** control stays green; byte-exact restore returns the canonical ASAR and both arms green. The installed 3.2.12 baseline reproduces the same red on the same stage with `productReached=true` and the same error text while its plain arm passes — which also matches the "first failed disk sample is still INITIAL, not proof that bad text was saved" reading: the 3.2.12 table arm failed before any write, so that sample is not evidence of a persisted bad document.

## 7. Material limits (explicit; none of these is repaired by this fix)

It runs against the same runtime EXE `d300992b…`, is **not** repaired, and is outside this single-root fix. My approval must not be read as covering it.
2. **Untested shapes stay untested**: outside-view / scroll-return lifecycles, partial escapes, separator rows, and cross-cell source ranges. The guards reject them (containment + codec round-trip) and they fall through to the old generic `a.focus()`, but that fallback was not pixel-covered for those shapes in this run.
3. **Transport ceiling**: Chromium trusted input is not a physical OS menu/accelerator test, and ordinary Unicode plus a synthetic `compositionend` does not prove real Windows IME. The suites' own transports say so (`no OS physical input claim`; `not OS menu clicks or physical accelerators`; `OS IME candidates/229/native accelerators unverified`).
4. **Exact scope of the green gesture regressions.** Formula gestures, the click/jitter distinction, native menu history and pending-image ownership are **earlier 3.2.12 fixes retained as passing regression evidence in 3.2.13**, not something this 3.2.13 root newly repaired (and not something it broke): their cases are green in the frozen run — cross-page-drag 2/2 including `formula-held-wheel-loop`, math-gesture 4/4 (click, jitter, local-loop, wheel-only), native-menu 10/10, native-pending-image 2/2, search-pending-image 1/1.
