## 高频错误与硬性对策（强制，2026-10-09 增补）

> 这五条来自实际踩坑统计（括号里是本轮复现次数）。每条都做成**可执行的检查**，不靠"下次注意"。

### 错-1 构建/同步失败被忽略 ⇒ 拿旧包量出"新读数"（3 次）

**症状**：`esbuild` 报错（或同步没做）之后，命令链继续打包 + 跑探针，于是**读数与代码不对应**——
我因此得出过"KP 段落高 187px""32px"这类根本不属于当次代码的结论。

**硬性**：
1. 构建一律走 `node .mp-verify\checklist\build-engine.cjs [--package]`（fail-fast：体检 → esbuild → 同步 → 校验 sha → 可选打包；任一步失败即停，不产出"半新半旧"的包）。
2. **任何读数必须写清"被测产物 sha16"**；探针启动后先断言产物 sha 与预期一致，不一致就报错退出，不出数。
3. 禁止把"构建"和"打包/探针"串在同一条命令里手工执行。

### 错-2 在模板字符串/引擎 CSS 里写反引号（3 次）

**症状**：引擎的 CSS 段是模板字符串，注释里写一个反引号就会**提前结束字符串** ⇒ 构建失败（进而触发错-1）。

**硬性**：引擎样式与模板字符串内的注释**禁用反引号**（要引用标识符就写 `CSS 类名` 的纯文本形式）。
`build-engine.cjs` 已内置"反引号配平"体检；提交前必须跑过。

### 错-3 单一尺子/单侧证据就下结论（3 次）

**症状三例**：① 只跑 20 万条随机 fuzz 就宣布"跳步改写等价"（真相：空属性值场景 70.4% 不等价，随机串撞不到）；
② 把"紧循环 dispatch 13ms"与"真实按键 1.3ms"当同一件事比较；③ 把"验收兜底合成件 1.4ms"当成"普通无巨行文档的对照臂"。

**硬性**：
1. **跳步/条件改写**（`indexOf` 跳读、状态位翻转、缓存复用）必须配**定向枚举**：空值、空字段、连续分隔符、边界重合，逐类穷举；随机 fuzz **只能当补充**。
2. 每条读数必须写明**尺子（方法）+ 测量顺序 + 夹具 sha + 产物 sha**；两把尺子的数**不许直接比**。
3. 对照臂必须是**同源同类**对象（同夹具、同尺子、同顺序）；"另一个夹具上的好数"不能当对照。
4. 结论进档必须带**时间范围**：写成"当时（何时）如此"；被推翻的结论**保留原文并就地标注**指向新结论——不许把历史结论当现状引用（本轮 5.12"字体度量"、PLAN 的 task-5"性能净负"都挂了三轮）。

### 错-4 同功能探针有多份实现，改了一份以为都改了（2 次）

**症状**：`perf-keys.cjs` 与 `probe-310.cjs` 各有一份 `instrument()`；我改了前者，验收跑的却是后者，
于是"硬化后的尺子"根本没生效，读数依旧失真。

**硬性**：
1. 改任何"尺子/判据"前，先 `grep` 同名函数与同一常量（如 `SAVE_DEBOUNCE_MS`、`instrument`），**列出全部实现**再动手。
2. 共享逻辑抽成单一实现（探针之间 `require` 同一文件），禁止复制粘贴出第二份。
3. 改完用**一条"自证命令"**证明当前跑的就是新版（例如打印版本标记/断言新分支被命中），不能只看文件已保存。

### 错-5 用裸字符串替换改文档/配置，或内联脚本处理中文（3 次）

**症状**：`.gitignore` 的 `/Typora-Editor-App/.perf/autosave-test-*/` 被替换成
`/Typora-Editor-App**/.perf/...`（规则失效）；PLAN 表格里 `\a` 被解释成 BEL 控制字符、`assets` 变 `ssets`；
`node -e "…中文…"` 经 PowerShell 传参被编码搅坏，脚本报"字符串未闭合"。

**硬性**：
1. 批量文本改动一律写成**幂等脚本**（放 `.mp-verify\checklist\`），要求：锚点**唯一且先断言存在**、
   已改过就跳过、**改完回读校验**（关键行包含断言 + 控制字符扫描 `charCode < 9 || (13,32)`）。
2. 含中文/多行内容的脚本一律**写成 `.cjs` 文件再跑**，禁止 `node -e` 内联。
3. 用 `edit` 工具做精确替换优于任何字符串替换；替换后必须回读该行确认。
4. **★ 替换串里含 `$` 时，必须用 replacer 函数**：`s.replace(needle, () => text)`。
   JS 的 `String.replace` 会把替换串里的 `$$` 解释成**一个字面 `$`**、`$&`/`$1` 等也有特殊含义
   ⇒ 直接传字符串会把源码里的 `$$` 悄悄写成 `$`（本轮实测：一行围栏判据被写成
   `qText.trim() === "$"`，**所有块公式识别全废**，而代码"看着像对的"、构建也不报错）。
   自证方式：改完对含 `$` 的行**数一遍 `$` 的个数**，并跑一次行为探针（本轮是靠"块公式不渲染"的截图才暴露的）。

## 高频错误·第二批（强制，2026-10-10 增补：改多窗口那一路的实战教训）

> 这四条来自"文件多开 + 菜单族"那一段连续踩坑。共同特征：**都不是产品难，而是我取证/改码的手法不可靠**。

### 错-6 凭记忆拼锚点改源码（5 次）

**症状**：写补丁脚本时按记忆拼多行锚点（还夹中文），锚点不命中；脚本打印"✗ 未命中"后**继续跑构建与验证**，
于是"改后读数"其实来自**根本没改的代码**——我因此白跑过整轮（图片大小、`second-instance` 两次）。

**硬性**：
1. 改 `src-cm6/`、`MarkPilot-CM6/` 里的产品代码，**先 `read` 出逐字节原文**（含缩进），再用 `edit` 工具精确替换；
   多行 JS/中文内容**不要**塞进 .cjs 的字符串数组去拼。
2. 补丁脚本必须把"锚点命中数"做成**前置断言**：`0 命中即 process.exit(1)`，且**同一命令内**先断言后继续。
3. 缩进是锚点的一部分：本会话 `second-instance` 的锚点就是 4 空格缩进（我按 2 空格拼，连错两次）。

### 错-7 探针的"读数拼装 / 漏参 / 破坏会话"（3 次，全部造成过误判）

**症状三例**：
① **跨两次 `evaluate` 拼一组读数**（先取 `mine` 再取 `docInfo`）⇒ 值与窗口串了，读成"新窗口拿到主会话文档"；
② **`page.evaluate(fn)` 忘了传参** ⇒ 应用按默认值回退（`openInNewWindow(undefined)` → 打开"当前文件"），
   我却读成"新窗口载入了主会话的文件"，为此连查三轮；
③ 用 `page.close()` 关窗 ⇒ **CDP 会话被拆**，后续所有 `evaluate` 超时，被我读成"关掉一个窗口，另一个也没了"。

**硬性**：
1. 一组相关读数**必须一次 `evaluate` 拿全**（同一个函数里取完再返回），禁止跨调用拼装。
2. `evaluate(fn, arg)` 的参数必须与函数签名逐项对齐；并在探针里断言"拿到的不是默认回退值"
   （例如断言目标文件确实被打开，而不是"当前文件"）。
3. 关窗口/关页面之后**必须重连 CDP 或改从主进程侧取证**；判断"应用是否还活着"用主进程事实
   （`BrowserWindow.getAllWindows().length`、`tasklist`、`main-debug.log`），不要用渲染侧超时反推。

### 错-8 现象与代码推断矛盾时，先信尺子、先改代码，而不是先看壳层 trace（3 次）

**症状**：多窗口两个"缺陷"，一个最终证明是**探针漏参**，另一个是**真缺陷**（关窗后全局 `win` 仍指向已销毁窗口、
会话未注销）；两者在渲染侧读数里长得一模一样，只有**壳层 trace** 能分开。

**硬性**：
1. 现象与推断矛盾时，**先加壳层 `dbg` trace**（`MP_DEBUG=1` → `userData/main-debug.log`），
   记录"谁、在什么时机、把什么写进了哪个会话/窗口"（含 `webContents.id`、`isPrimary`、路径末段）。
2. 渲染侧 CDP 读数是**二手证据**；主进程 trace 与 `debug:sessions` 之类的一手读数优先。
3. 结论按错-3 第 4 条处理：被推翻的判断**保留原文并就地标注**，不许当现状引用。

### 错-9 大范围区块替换波及相邻作用域（1 次，但后果重）

**症状**：把 `createWindow` 区块内的 `win.` 批量改成局部 `W.` 时，**区块取得过大**（一直取到 `app.whenReady`），
连带把区块外的 `second-instance` 处理器也改了 ⇒ 那里出现未定义的 `W`，**第二次启动直接抛错**。

**硬性**：
1. 区块替换必须用**明确起止锚点**（函数名 → 下一个 top-level 声明），替换后打印"改了几处、字符差多少"；
2. 改完**立刻** `node --check`，并对该区块 `git diff` 目视一遍（改动行数应与预期数量级相符）；
3. 批量改名类改动要**枚举受影响标识符**（`win.`、`W.`、`state.`、`S.`），并检查边界处的混用。
