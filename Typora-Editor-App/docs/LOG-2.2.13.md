## 三、归因

### ② 回绕陷阱：`patchHorizontalMathLine` 不看方向与入口侧

`typora-patches.js` 的 `patchHorizontalMathLine`（2.2.7 为"←/→ 走进整行只有一条行内公式的行"加的键后校正）
只判三件事：选区折叠、落点**隐形**（无矩形）、落点在"只有一条公式"的块里。
于是在**行尾**按 → 时：行内公式补丁先把光标放到段尾的元素级位置 `P@1`（正常插入点，Chromium 画不出矩形，
由合成光标补一条竖线），这一手紧接着把这枚隐形光标当成"从上一行**走进**公式行"，
把光标塞回**同一条公式源码的开头**。`probe-f9-trap.cjs` 抓到的写入口时间线（修复前，同一发按键）：

```
══ 第 72 步：{块3 前缀26/26 容器 TEXT "$" @1  盒 [200,264,0,16]}
   →→ {块3 前缀1/26  容器 TEXT「仅此独占一行的公式x+1」@0  盒 [59,266,0,13]}
     · 选区变   9090ms  TEXT@0「仅此独占一行的公式x+1」
     ✎   9086ms  collapse(P.,1)        ← selectPoint @typora-patches.js:69 ← …:831（出公式：落到段尾元素级位置）
     ✎   9087ms  removeAllRanges()     ← 拍 @typora-patches.js:1726      ← 键后校正把它当成"走进公式行"
     ✎   9087ms  addRange()            ← 拍 @typora-patches.js:1727      ← 落进同一条公式源码的第 0 位
     ✎   9087ms  removeAllRanges()     ← c @index.min.js:1:69493 | B @… | HTMLPreElement.<anonymous>
     ✎   9088ms  addRange()            ← c @index.min.js:1:69513 | …      ← Vditor 接着把它规范化到源码里
```

### ③ 行首 ← 光标隐形：`patchCaretWatchdog` 的"在块外"把编辑面自己算成块

IR 的编辑面是 `<pre class="vditor-reset">`，正好命中 `在块外()` 里那个 `pre` 选择器——
"光标停在编辑面上"（块与块之间的元素级位置）被判成"在块内"，而看门狗的设计本意是
"块内那些看不见但正确的位置一概不动，块外的病态位置要救"。实际上 IR 的编辑面**不是**内容块。

## 四、修复

1. `patchHorizontalMathLine`：新增 `入口侧(forward, selection)` —— → 只认"公式之前"（元素级 `P@0`）、
   ← 只认"公式之后"（偏移 > 0）。走进来的那一侧才进源码；从另一侧按同方向键是"**离开**这一行"，不拦。
2. `patchCaretWatchdog`：`在块外()` 里把 `root` 与编辑面本身一并算作"块外"，
   于是行首 ← 落到编辑面元素级位置时，看门狗按既有逻辑做**几何相邻行**校正，落到上一块（表格末格）的末尾正文上。

**试过又撤回的一条**（记下来免得再走一遍）：曾把"元素级落点在块内"也纳入救援（让 `P@12` 那种段尾落点换到文字节点上）。
撤回了，理由是 `patchSyntheticCaret` 的成文教训——那类位置**本身是正确插入点**（用户在那儿打的字就该落在段尾），
挪了等于改语义；实测过一次"隐形就救"把场景 107 从 15/15 打到 13/15、101 从 32/32 打到 30/32。
这类位置由合成光标补一条竖线（用户看得见），本次巡走判据据此把"原生矩形有高度**或**合成竖线可见"算作可见。

## 六、判据重写：134 的尺子为什么必须换

旧判据"块内字符前缀必须变大"抓得住 ② 但把 ① 误判成卡死。换成 DOM 顺序后，DOM 节点又过不了 CDP 序列化
（读数必须是纯 JSON），于是最终口径是**三件套**：

* **前缀**（块内 `range.toString()` 长度）判推进方向：变大=前进、变小=倒退；
* **像素**（原生矩形或合成竖线）判"同一个前缀但落点换了"——行内公式的"右 `$` 标记 → 紧随其后的文本节点"就是它；
* **块指纹**（块 `innerHTML` 长度 + 展开节点数 + 子节点数）判"展开/收起"这类 DOM 状态变化。

三件都不变才算**卡死**；跨块必须落到**紧邻**块（跳行/跳标题在这一条上变红）。
另加两条可见性不变量：光标必须看得见（原生矩形有高度**或**合成竖线可见）；
原生可见时合成竖线必须收起（**不许同屏两根**）。

## 七、同一批的第二条：F10「点块间空白出现两根光标」——判为尺子误报

> **【2026-10-01 更正】本条判定已被推翻：F10 是真缺陷。** 真屏连拍证明"矩形 0×0"不等于"原生没画光标"，
> 见本文 **§十二**（12.1 取证 / 12.5 更正）。下面保留原文以便追溯尺子是怎么错的。

133 的读数说"原生光标有效落在正文层折叠态，同时合成竖线 1 根"。探针
`scripts/acceptance/probe-f10-double-caret.cjs` 把**原生矩形高度**逐时刻读了出来：

```
t≈  40ms  块2 P.@1(元素级) 原生高0 折叠true  竖线=[{显示:block,框:[133,220,2,20]}]
t≈  80ms  块2 P.@1(元素级) 原生高0 折叠true  竖线=[…]
t≈ 200ms  块2 P.@1(元素级) 原生高0 折叠true  竖线=[…]
t≈ 400ms  块2 P.@1(元素级) 原生高0 折叠true  竖线=[…]
t≈ 800ms  块2 P.@1(元素级) 原生高0 折叠true  竖线=[…]
```

落点是**段落内的元素级插入点**（`P@1`）——Chromium 在那里根本画不出 caret（高度 0），
合成竖线是**唯一**看得见的光标。原读数的推论"`层:正文` + `折叠:true` ⇒ 原生可见"
对元素级落点不成立；这正是 `patchSyntheticCaret` 的成文契约（"三类位置位置合法、但画不出矩形，
不能靠挪光标消症状——挪了等于改语义"）。

**133 的不变量按契约改写（更严，不是放宽）**：合成 ≤1 恒成立；**原生矩形有高度时**合成必须收起；
**原生画不出时必须有一根**（否则用户什么都看不见）。突变验证：把 `BAR.style.display = "block"` 注掉，
"块间空白2"当场变红，读数 `原生高 0 + 合成 0`。

## 八、同一批的第三条：F4「长按 ↓ 丢步 24%」——不是吞事件，是到底不带滚动

交接件读数：17 发 ↓ 只走 13 行（76%）、30ms/60ms 同值、终点固定。探针
`scripts/acceptance/probe-f4-hold-steps.cjs` 逐发采样 + 打开纵向补丁自己的轨迹（`__vertTraceOn`）：

```
起点 块2 x=74  窗高713 面[0,713] 面滚0 面内容高821
第 1..12 发  块4..块15  x 74→72（每发一行；"首发跳 2 行"是采样时序：onEvery 在第 1 次 autoRepeat 后回调）
第13..17 发  块15 原地不动   面滚恒为 0
【假设验证】手动把滚动容器下滚 120px（面滚 0→107）后按一次 ↓ → 立刻前进到块 16
```

**根因**：纵向移动整段被 `patchVerticalMathLine` 接管（`preventDefault` + 自己算落点），
浏览器"把光标移进视口、顺带滚动"这个副作用一起丢了。`scan()` 的扫描被限制在编辑面框内，
下一行在框外就直接 break → 返回 null → 落到"到顶/到底"分支 → 既不移动也不滚动。
用户口径"按住方向键一顿一顿走不动"就是从这儿来的。

**修复**（都在 `patchVerticalMathLine` 内）：

1. `边缘滚动`：光标贴着可视区边、且扫描找不到下一行时，先把滚动容器滚一小步，再用**滚动后的新几何**重扫；
   滚不动（真的到头）或重扫仍无果 → **还原滚动**（只滚不动光标等于把光标推出视口，实测过一次：
   ↑ 回顶后光标停在 `y=-18`、越过了视口上沿）。
2. `滚进视口`：落点落在视口外（上下都可能）时把它带进来，留半行余量。
3. `scan` 拒绝"整行都在可视区外"的落点（那种命中是 Chromium 把点钳到最近一行的产物）。
4. **可视顶改成工具栏底边**：工具栏是绝对定位浮在正文上的（盒 `[0,0,922,71]`、`z-index:30`），
   正文滚上去之后最上面几行那一带**既看不见也命不中**（`caretRangeFromPoint` 拿回的是工具栏按钮，
   只有 x=0 掉到正文上），目标列于是被钳成行首——实测 `probe-f4-toprow.cjs`：
   `求[74,27]` 全部不可用、候选只剩 `[0,46,14]`，覆盖元素 `button.vditor-tooltipped … [69,1,25,35]`。

**实测效果**：↓ 17 发从块 2 一路走到文档末块（滚动跟着走，面滚 0→107）；
往返（↓ 到底 + ↑ 原路回顶）目标列**全程守住**（x=74，抖动 70–75）。场景 128 由 12/15 → **16/16**。

**突变验证**：注掉 `边缘滚动` 那一行，136 立刻回到 `生效 13/17 = 76%、终点块 15` ——
与交接件原始读数完全一致，反向证实归因。

**顺带校正两处场景算术**（旧口径在本素材上不可达，不是"为了过验收而放宽"）：

| 场景 | 旧口径 | 校正后 |
| --- | --- | --- |
| 136 ↓ 连发 | "生效/连发 ≥ 90%"——素材 18 块，从块 2 往下最多走 15 步，17 发里必然有 1-2 发落在文末 | "一路走到文档末块 + 目标列不丢"；比例仍进台账当回归读数 |
| 128 ② 回程 | 写死 17 发，修好 F4 前后两种实现下都算不平 | 按**实测下行步数**回程 |
| 128 ③ 连发 → | 写死 30 发（越过了行尾继续走到下一行） | 真人式长按：按住不放到行尾松手；另加断言"途中确实进过公式源码、没整块跳过去" |

## 十一、用户报告：「图片变成超长代码」——判定为 Typora 对 data URI 的尺寸上限

**报告**：`E:	emp1\新建 Markdown 文档.md` 打开后，图片显示成一整屏 `<img src="data:image/png;base64,…">` 源码。

**这份文件的实际形态**（`grep` 逐行读，原件只读）：6 张图是**内嵌 base64 data URI**（每张约 78 KB，各占一整行、HTML `<img>` 形式），
外加 1 张外链 URL；全文件 484288 字节、59 行。

**MarkPilot 侧（实测正常，无缺陷）**：

| 检查 | 读数 | 器具 |
| --- | --- | --- |
| 那一块实际画的是什么 | 源码 `<pre>` 宽高 **0×0**（收起）、预览 838×105、真 `<img>` 元素 **299×96** 在画 | `probe-repro-img-base64.cjs`（局部 2 倍图 `img-块-2倍.png` 就是那张照片） |
| 编辑区文本 | 长 3374、**不含原始 base64**、含短缓存 URL（`file+.vscode-resource…`） | 同上 + `probe-img-base64-fidelity.cjs` |
| 打开 → 保存 | 484288 字节 → 484288 字节，sha256 `46adbb4a…` **逐字节相同** | 同上（磁盘证人） |

编辑区能显示 base64 长墙的前提就不成立：`portable-images.cjs` 在打开时把内嵌图片**掩码**成短缓存 URL
（`'<img ... src="'` 那一路正则在名单里 ✓），保存时再原样展开回 base64。

**Typora 侧（对照实验，同机同一天）**：

| 对照素材 | Typora 显示 |
| --- | --- |
| `<img src="data:image/png;base64,…">`，base64 **2 KB** | 正常渲染成图片 ✓ |
| 同形式，base64 **112 KB** | **显示源码**（整条标签原文）✗ |
| `![](data:image/png;base64,…)`，base64 **112 KB** | 同样**显示源码** ✗ |

→ 是 Typora 对 data URI **尺寸**的限制（阈值在 2 KB 与 78 KB 之间），与 HTML/markdown 写法无关；
用户那份 78 KB 一张，正好落在限制之外。

**处置**：MarkPilot 不需要改（渲染正常、字节保真）。要在 Typora 里也看得见图片，把内嵌 data URI 换成图片文件 + 相对路径引用即可；
转换属于改内容，未擅自对原文件执行。

## 十二、用户报告（同日续报）：「公式后面多一根粗光标」+「点右 `$` 之后光标还插进公式」

素材还是那一行：`循环往返问题：对侧相向出发：$S=L(2n-1)$`（段末行内公式）。两件事一起收，
其中第一件**推翻了 §七 对 F10 的判定**。

### 12.1 尺子先换：真屏像素才是"原生光标画没画"的证人

`Range.getBoundingClientRect()` 在"元素级插入点"（`P@偏移`，如段末公式之后）上读回来是 **0×0**——
**但 Chromium 照画光标**。这一轮把两条通道摆到一起才看清：

| 通道 | 能不能拍到原生光标 | 本轮实测 |
| --- | --- | --- |
| 合成器 `webContents.capturePage`（DIP 矩形） | **能**（与旧笔记相反，见下） | `probe-accept-inline-math-caret.cjs`：合成线 `display:none` 的那一刻，同帧图里仍有竖线 |
| 真屏 GDI `CopyFromScreen`（DPI 感知，按 `getContentBounds × scale` 定位） | 能，但光标 ~500ms 亮/灭，**单帧会拍到"灭"** | `probe-caret-native-truth.cjs` 连拍 6 帧：把合成线节点从 DOM 摘掉后，真屏上那根竖线仍在亮灭交替（行高 25px），证明它是**原生**的 |
| 矩形读数（旧判据） | **不能**（0×0 不代表没画） | 同一位置：矩形 0×0 + 真屏有竖线 |

标定方法与两个坑（都写进了脚本）：`scripts/acceptance/probe-shot-calibrate.cjs` 用同一块区域三种抓法对比，
证明 **`win.getContentBounds() × displayScale` 才是准的**（按窗口句柄 `GetClientRect`+`ClientToScreen` 会差一条标题栏的高度）；
`win-screen-crop.ps1` 抓屏前必须把窗口顶到最前（否则拍到压在它上面的别的窗口），
`win-screen-crop-xy.ps1` 用 Electron 侧 `setAlwaysOnTop(true)+moveTop()` 顶窗。

### 12.2 第一条：公式之后"一根大而细 + 一根偏粗"＝原生 + 我们的合成线

用户截图里那两根：细而高的是**原生 caret**（行高 25px），偏粗（2 CSS px）而矮的是 `patchSyntheticCaret` 的合成竖线。
旧判据"原生矩形 0×0 ⇒ 画不出 ⇒ 补一根"在这里是**误判**——补出来的就是第二根。

**修法**（`patchSyntheticCaret`）：矩形照旧先用（true positive 不能丢），矩形为空时**改看版面**——
落点所在块里"光标之前/之后"任一侧能取到**有高度的行盒**，就说明它在一行有内容的版面上，Blink 自己画得出，
我们一根都不补；只有连内容行盒都取不到（版面级空白、空块）才落回兜底绘制。几何计算与日记（`__caretProxyLog`）
一概保留，只是**不渲染第二根**（用户口径："后台这个位置有关键作用，不变，只是不渲染第二个"）。

### 12.3 第二条：点右 `$` 之后那一带被 Blink 解进源码

命中几何（`probe-inline-math-click-band.cjs` 定点扫描，折叠/展开两态各 8 格）：

| 状态 | 点击位置 | 落点 |
| --- | --- | --- |
| 折叠 | 渲染字形内（`owner` 右缘 −2px 以左） | 源码 `TEXT("S=L(2n-1)")@6..8`（Typora 语义，保留） |
| 折叠 | 右缘 −0.5px 起往右 | 正文 `P@2`（本来就在外面） |
| **展开** | 右围栏之后（`owner` 右缘 **+0.5 … +12px**） | **源码 `TEXT@9`**（病象） |

机制：渲染结果 `protectPreviews` 挂了 `contenteditable=false`，Blink 的命中测试**跳过**它，
落在它下面那个 `code` 文本上；展开态里 `code` 是布局中的真实文本，于是"点公式右边"被解成"点源码末尾"。

**修法**（`patchInlineMathClickPosition`，同一支补丁内分两路）：
按下那一刻把**这一行所有行内公式节点的盒子**记下来（几何说话，命中元素让路），
点在盒子外面而光标被解进源码 → `selectOutside` 钳到公式外侧第一个正常文本位置（与 ←/→ 走出公式同一条路）；
点在盒子里面 → 原路不动（展开 + 按渲染像素精确定位）。拍要跑两趟（rAF + 60ms），
第二趟时节点已因光标离开而收起、几何变回折叠态（盒子更长），光凭几何会误判成"在盒子里"——
所以加了一个**本次手势**的闸门（`已钳`），钳过就不再让第二路插手（实测就是这个走势）。

### 12.5 §七 的更正（F10）

§七 把 F10「点块间空白出现两根光标」判成"尺子误报"，理由是"原生矩形 0×0 ⇒ 唯一可见的是合成线"。
12.1 的真屏连拍证明：**矩形 0×0 ≠ 没画**——那两根里细的那根一直是原生光标。**F10 是真缺陷**，
本轮 12.2 的修法同时把它收掉（同一类位置：块内/块间的元素级插入点）。
教训：判"看得见/看不见"这类**用户视觉**事实，只能拿用户看得见的那一层（屏幕像素）当尺子。
