## §2 §7.1 代码块行号：真缺陷（定位口径）+ 探针缺陷

### 2.1 现象与第一层误判

装机产物 80 项验收里 §7.1 判红，读数形如：
`普通块号=[]（空行号=?）；引用块号=[]；长行块号=[]`、`DOM 里像行号的元素 = 0 个`，
但**同一轮的 style 检查点却是绿的**：`content="1" align=right color=rgb(139,144,160)`、
`全文档带 data-mp-n 的 .cm-line = 7 个（样例 ["1","2","3","1","2","3","1"]）`。

2 倍截图（`accept\out\shots\7.1-mini-2x.png`）**肉眼可见**：正文块 `1/2/3`（空行占 2 号）、
引用区块 `1/2/3`，右对齐、灰色小字、左侧 1px 竖线全在。
⇒ **第一层结论：夹具里产品是对的，红的是探针的定位方式**。
（探针侧的修复见 §3；它把定位从 `posAtDOM` 换成"按已渲染行推断行号"。）

### 2.2 第二层：产品在**大文档**里真的漏挂属性

探针修好之后复跑，**仍然红**，而且更彻底（`[data-mp-n]` 一个都没有）。
不再靠推断，改为**直读现场**：临时插桩产物（每次 `apply()` 打一行 `[mp-lineno]`）

- 构建：`.mp-verify\checklist\build-instr.cjs`（源码副本 + 插桩 → 产品同一条 esbuild 命令 → 解包/换 `renderer/cm6/app.js`/重打 `app.asar`）
- 直读：`.mp-verify\checklist\diag-lineno.cjs`（起插桩包、装夹具、读 `lineStylesField.codeLines` + 逐行 DOM + 控制台插桩）

**小夹具（整段可见）**：`codeLines` 6 条齐全、`Map` 6 个键、`from` 全有效，
逐行 `domAtPos` 结果：`{from:42,nodeType:3,hops:1,cls:"cm-line mp-code"}` …… 属性**全挂上**。

**清单大文档（3.97MB）**——同一个函数、同一份代码：

```
probe: [{"from":22971,"n":1,"nodeType":1,"nodeName":"DIV","hops":7,"cls":null},
        {"from":26060,"n":1,"nodeType":1,"nodeName":"DIV","hops":7,"cls":null}, ...]
```

⇒ **`domAtPos(codeLinePos)` 在有块 widget 的文档里会解析到 widget 内层的 DIV**（实测 `hops=7`），
一路 `parentElement` 上溯**根本遇不到 `.cm-line`** ⇒ 属性静默挂不上（旧代码那句 `catch` 把它吞了）。
小夹具没有 widget ⇒ 全对。**这就是"夹具里有号、真实文档里没号"的全部原因。**

### 2.3 第三层：时机（`apply` 挂错了钩子）

插桩还抓到一个**独立**问题：`apply()` 第一次跑（构造函数里）时，视图**还没挂上 DOM**——
`view.domAtPos` 直接报 `Cannot read properties of undefined (reading 'domAtPos')`。
旧代码把属性写入只挂在 `update()`（事务）上 ⇒ 属性全靠"之后**撞上**一次事务"补；
CM6 在没有事务时也会自己重建/补渲染行 DOM（视口渲染、行高重排），那些时刻没有任何 update 可挂
⇒ **该挂的属性整批漏掉**。

### 2.4 修法（`src-cm6/main.js` 的 `codeLineNoPlugin`）

1. **定位口径换成"结构对位"**：不再猜位置。
   `.cm-line` 是 `contentDOM` 的直接子元素且**按文档顺序**（CM6 结构契约），于是行号可推：
   普通行 = 已数行数 + 1；围栏行 = 围栏序号 + 1（占一行）；代码行 = 围栏序号 + `data-mp-n`（块内号）。
   推出号之后只在 `codeLines` 的号集合里查表写属性；**不在集合里的行顺手清掉属性**（反向清理）。
   代价：一次遍历**已渲染行**（视口规模），不是全文扫描。
2. **写入挂点补 `measure()`**（`ViewPlugin` 的 measure 阶段）：每轮布局后跑，此时 DOM 与文档已对齐。
3. **三输入门控**（measure 每轮都跑，不能每轮全量扫）：`lineStylesField` 换新对象（文档变）、
   `view.viewport.from/to` 变（视口变）、已渲染行数变——三者都没变就直接返回，零重扫。
4. 保留一条 `domAtPos` 补腿兜"结构对位推不出号"的极端情形，**失败即放弃**（不制造错号）。

## §2c 一个必须写进纪律的现场：`requestMeasure` 每键跑 = 每键两轮完整布局

行号插件的"补挂"一开始写成 `update(u) { this.apply(u.view); u.view.requestMeasure(); }`
（想保证 DOM 一变就补属性）。实测在 8.5MB 文档上把**每键 p50 从个位数抬到 93.4ms**——比历史
"全文重扫"还差。改成"**只有视口真的换了才请求一次测量**"（`lastVp` 比较）后回到 87.4ms（与对照臂同）。

> 口径：`requestMeasure()` 是"再跑一轮布局"的请求，**不是**"顺手刷新一下"。凡打算在 `update` 里调它，
> 先问一句"这一轮布局真的必须重跑吗"。同一族的还有"在 measure 里改 DOM 会不会引发新的 measure"
> ——本插件的 measure 只写属性、不改结构，不会自激。

## §3 2.15 / 3.1 / 4.10 / 5.1：同一根因的探针缺陷（并纠正上一轮的"抖动"归类）

**现象**：这四条在首跑与复跑中都会出现 `夹具未渲染进 DOM（找不到容器）`。

**根因（`probe-checklist.cjs` 的 `containers()`）**：它只用 `posAtDOM(el, 0)` 给容器定位；
而 `posAtDOM` 对**某些已渲染行**给不出位置（§2.2 同族：带行内公式的引用行、表格 widget 行、标题行）。
拿不到位置的容器被 `continue` 丢掉 ⇒ `picked(f,t)` 空集 ⇒ 判成"夹具没渲染"。
`bring()` 的收敛判据也吃同一个亏：目标行"没能被认出来"⇒ 以为还没到 ⇒ 继续滚 ⇒ 越滚越远。

**修法（两处）**：

1. `containers()` 增加**第二腿·结构推断**：`.cm-line` 按文档顺序编号（普通行计数 +1；
   代码行 = 围栏序号 + `data-mp-n`），并用第一腿**成功**的行号作锚点**校准偏移**（只在众数 ≥2 时采信）。
   推断只**补洞**，不覆盖已有位置。附 `TALLY`（`direct` / `inferred` / `calibrations`）当"尺子自证"读数。
2. `bring()` 增加一条**不看估算、只认已渲染元素**的判据：目标行元素真在 DOM 里且有高度才算"到了"。

**验证**：`--only=2.15,3.1,4.10,5.1` 复跑 **4/4 全绿**（同一产物、同一清单）。

## §4 §5.12 零宽字符占宽 5.5px：**§4-a 当时的结论已被推翻，§4-b 是真因与修复**

### §4-a 当时的结论（**错的，留档以免重犯**）

- 两条**独立**量法同值（`coordsAtPos` 5.5px、DOM `Range.getBoundingClientRect()` 5.5px）
  ⇒ 当时推断"是本机字体对 U+200B 的度量"，**并据此判定"非缺陷、不改"**。
- 同机同尺的 3.0.8 对照产物同样红 ⇒ 当时推断"与 3.1.0 的改动无关"（这一条**仍然成立**）。
- **它错在哪**：把"两条量法同值"当成了"与实现无关"的证据。实际上两条量法量的**是同一个渲染结果**，
  同值只能说明"测量一致"，**不能说明"这个宽度不是我们渲染出来的"**。

### §4-b 真因（2026-10-09 查到并修复）

1. **平面 DOM 对照**：同一个字符放在编辑器外的 `span` 里、用**同一个字体栈**量，宽 **0.01px**
   （CJK 上下文 0、拉丁上下文 0.01；`Arial/SimSun/Consolas/monospace…` 十一种字体全是 0 或 0.01）
   ⇒ **与字体无关**。
2. **真实 DOM 里它是被替换过的**：把那一行的节点逐个打出来，字符位置上是
   `<img class="cm-widgetBuffer">` + **`<span class="cm-specialChar" title="Control character zero width space">•</span>`**
   ——占宽 5.5px、高 16px，里面是一个**看得见的圆点**。
3. 结论：这是 **CM6 `highlightSpecialChars`（随 `basicSetup` 引入）的默认行为**——
   把不可见控制字符画成可见占位字形（默认红色）。**是产品行为，不是字体度量，也不是探针偏差。**
4. **视觉证据**（Lead 亲自看图，本会话无视觉子代理路由）：
   `shots\zwsp-before.png` 里 `零·宽·字符` 之间各有一个**红点**；
   `shots\zwsp-after.png` 里红点消失、两字紧贴、**行高不变（25.2px）**。

### §4-c 修法与复核

- 修法（`src-cm6/main.js` 的引擎 CSS，仅一条规则、只针对这一个控制字符）：
  `.cm-content .cm-specialChar[title="Control character zero width space"] { font-size: 0; }`
- 候选实测（页内注入后量）：`font-size:0` ⇒ 占宽 **5.5 → 0**、行高 25.2 **不变**、光标两侧差 0；
  `display:inline-block;width:0` ⇒ 占宽 0 但**行高被顶到 33.73px**（否）；`display:none` ⇒ 也可，
  但会把该节点从行盒里摘掉，改动面更大（否）。
- **其它控制字符保留默认红点提示**——软连字符、双向控制符出现在正文里通常是事故，看得见比看不见好。
- 复核：`§5.12` 转绿；**全量 80/80 通过**（产物 `4c8f127f7bcd9240`）。
- **脆弱点（必须知道）**：选择器靠 CM6 写的 `title` 文案精确匹配；CM6 改文案则规则失效、
  观感回到"有红点"——**拦住它的是 §5.12 本身**（它直接量那个 span 的实占宽），文案一改那条就会红。

## §5 工具链缺陷：`accept-310.cjs` 自锁

**现象**：`node accept-310.cjs ...` 会先取一次 app-slot 锁，然后**再把自己包进 `app-slot` 重入**
（`MP_ACCEPT_SLOT=1`），而外层 app-slot 与内层抢**同一把锁** ⇒ 双方各等对方、永久挂住
（实测日志：`已取得（…）` 紧跟 `等待中（第 N 轮，持有者 …）`，N 一直涨）。

**规避（本轮用）**：**直接跑** `accept-310.cjs`，不要再在外面套 `app-slot`（它自己会套）。

### 8.4 ★ 我引入的回归（对抗复核抓到，已修）——本轮最该记的一条

改动 1 的第一版**不等价**：引号态里直接 `indexOf(quote, j + 1)`，当值是**空串**
（`<img src="a.png" alt="">`）或闭引号紧邻另一个引号时，闭引号**就在 `j` 本身** ⇒ 跳过它 ⇒
引号态奇偶错位 ⇒ 一路"未闭合"到行尾、`gt = -1` ⇒ **图片整张不渲染（显示字面 HTML）**，
且同一行后面的 `<img>` 一起丢。

- **严重度（对抗腿结构枚举）**：属性三元组形态 **70.4% 分歧**；全枚举 **212,580 / 2,441,406 不等价**；
  13 条真实写法 **10 条中招**。
- **为什么我没发现**：改动上线前我只跑了 20 万条**随机** fuzz —— 随机串撞不出"空值 + 相邻引号"，
  **0 命中**。⇒ 教训：**`indexOf`/跳步型改写必须配"空值 · 空字段 · 连续分隔符"的定向枚举**，
  随机 fuzz 对相邻分隔符系统性欠采样。
- **修法**：引号态里**先自检紧邻闭引号**再跳步。复验：全枚举 **2,441,406 样本 → 0 不等价**，
  9 类最小触发全部恢复；`p50` 不受影响（新分支只在遇引号时多一次比较）。
- 证据：`.mp-verify\a1-red\FINDINGS.md` 的 `# EX-2` 节；复跑 `harness\ex-severity.mjs` /
  `ex-min.mjs` / `ex-bug1.mjs`。

**顺手对齐一处既有缺口（OPEN-2）**：markdown 路径 `![图](a&amp;b.png)` 以前**不解字符引用**
（裸 `<img>` 路径解）⇒ 远程图会带着 `&amp;` 去打真实地址。现已在 markdown 分支套同一个
`mpHtmlUnescape`（无 `&` 时早退，零成本）。

### 8.5 ★ 对抗复核还查出：**已落地的 `a1ScanMath` 本身就是错的**（已修）

对抗腿用**真实 `ChangeSet`** 做单步编辑穷举（6 种形态 × 9 种插入串 × 全部位置 = **1539 例**），
**5 例与全量扫描不一致**，最小复现是同一份 6 行文档 `$$\na\n$$\n$$\nb\n$$`：

| 操作 | 全量 | 修复前增量 |
|---|---|---|
| `{from:7,to:7,insert:'x'}` | 一条 span | **整条丢失** |
| `{from:4,to:4,insert:'$'}` | 一条 span | **整条丢失** |
| `{from:1,to:1,insert:'$ '}` | `7-12:""` | `10-17:"b"`（位置与内容都错） |

**根因**：窗口（`dirty ± 1` 行）**两端可能切在多行结构中间**；而它用来判"入口干净"的
`a1LineStates` 是"看行首"的**粗状态机**，与 `scanMathSpans` 真实的开合口径**不等价**——
尤其 `scanMathSpans` 对**未闭合**的 `$$` 会整块不认（当行内文本），于是"窗口里那块产出为空"
被误判成"没被切断"，前缀/后缀照旧复用 ⇒ **静默错**（公式块消失、注释尾部露出）。原实现也
**没有**"行数变化兜底"那条（设计与注释里承诺过，代码里不存在）。

**修法（两处）**：
1. **窗口自洽扩张**：用**扫描器自己的产出**判断窗口有没有被切断——有 span 触到窗口末尾
   （`to >= sliceDoc.length`）就把 `endLine` 往后扩；有 span 从窗口首字符起就把 `start` 往前扩；
   扩不动或超上限 ⇒ **全文重扫**（`reason: 'window-not-closed'`）。
2. **脏区邻域保守门**：邻域（±2 行）出现 `$` / 反引号 / `~` / `<!--` 即判"结构不确定"⇒ 全文重扫
   （`reason: 'math-chars-nearby'`）。纯文本/大图文档不受影响，增量照常生效。

**复验（三个 runner 全绿）**：单步穷举 **1539 例 0 不一致**；最小复现 6/6 ✓；
随机多步 fuzz **2000 步 0 不一致**。

### 8.6b 消融实验：这 13~40ms 里**引擎数据层占多少**（2026-10-09 追加）

**方法**（`ablate-layers.cjs`）：做一份**可切换**的引擎——五个产出函数
（`scanMathSpans` / `scanLineStyles` / `scanTables` / `scanInlineMarks` / `buildBlockMath`）开头各插一行
`if (globalThis.__MP_ABL) return <空>;`。同一份产物跑两次：页面加载后置 `__MP_ABL=true` 再 reload
（= 数据层整体停摆），与不置位（= 全量）逐枪对比。**两臂用同一支尺子、同一顺序**。

| 位置 | 引擎全量 | 扫描器停摆 | 数据层占比 |
|---|---|---|---|
| 文档末尾（第 192 行行尾） | **16.3 ms** | **15.9 ms** | **0.4 ms（2%）** |
| 巨行中部（第 20 行，91.6 万字符） | 40.8 ms | 46.5 ms | ≈ 0（差值落在噪声里） |
| 纯选区对照臂 | 0.3–0.5 ms | 0.3–0.5 ms | — |

⇒ **按键代价不在我们四个扫描器上**。它按**"改动的那一行有多宽"**付费，属 CM6 自己的视图层工作：
① 改动行的 **DOM 文本重写**（一行 = 一个文本节点，91.6 万字符的节点重写）；
② **Lezer 重解析**该行（`markdown()` 语言层）；③ 高度图/视口/测量。

**两条必须记住的方法学（本轮都踩了）**：
1. **`state.update()` 是 0ms** —— CM6 的 `StateField` 是**惰性**的：字段值在**第一次被读**时才算，
   而读它的是视图更新 ⇒ 真实开销全在 `view.dispatch()` 里。
   （⇒ 想"逐字段计时"就必须在视图读它的时刻量，绕开视图去包 `field.update` 是量不到的。）
2. **顺序会污染读数**：`ablate-layers.cjs` 第一版**先**在巨行里连打 15 次、**再**量文档末尾，
   读数 46.1ms；把顺序倒过来（先量末尾）立刻回到 **16.3ms**，与独立探针 `perf-dispatch.cjs` 的
   **13ms** 对上。原因：每次在巨行里插入都要重写 91.6 万字符的行，留下的延迟测量/重排落进了下一次计时。
   ⇒ 纪律：**"同一把尺子"不只是同一个脚本，还包括同一个测量顺序**。

### 10.2 ★ 幻觉一：验收 §7.8 的 `1.4ms/1.5ms` 是**尺子假象**（已修尺子并重测）

### 10.3 ★ 遗留一（真产品缺陷，已修）：光标停在开围栏行 ⇒ 代码块行号整块错位

`--only=7.1,…` 复跑暴露：`普通块号=[null,null,"2",null,null]`、`byBlock` 号序 1..N=false，
而同一份清单在别的跑法里是绿的（**只有光标停在开围栏那一行时才红**）。
现场 dump：开围栏那行的类名是 `cm-line cm-activeLine mp-code` —— **`.mp-fence` 不见了**（该行切源码态）。

**两层根因**（都在 `codeLineNoPlugin.apply()`）：
1. **对位靠 `.mp-fence` 计数**：开围栏丢类 ⇒ `fenceNo` 少算 ⇒ 5 行里只有空行拿到号；
2. **三输入门**（字段对象 / 视口键 / 已渲染行数）在"光标移动导致行 DOM 被重建"时**三个都没变** ⇒ 直接早退
   ⇒ 新元素上的号永远补不回来（现场：4/5 行缺号）。

**更隐蔽的第三层（查了三轮才定到）**：CM6 的行属性是**它按自己的模型写**的；某一行的装饰集变化时它会
**重新应用该行属性**，于是**我们自己挂的 `data-mp-n` 被就地抹掉**——而**元素对象没换**，
旧代码"处理过就跳过"的缓存认为没事 ⇒ 永远不补。
现场证据：同一次滚动里**刚滚过去读到 `[1,2,3]`，1.2 秒后变成 `[null,2,null]`**；
而 1.2 秒窗口内 `apply()` 一次都没跑（埋点的现场记录为空）⇒ 坐实"被就地抹掉"。

**修法**（`apply()` 重写）：
- 不猜结构：每个已渲染行用它**自己的位置**换文档行号（`view.posAtDOM(el, 0)`），拿行号查
  `lineStylesField.codeLines` 的表；**可见行 `posAtDOM` 可用性有探针自证**（抽样 30 条成功 30、抛错 0）。
- **WeakMap 记住"这个元素写到什么值"**：元素没换 ⇒ 一次查表；DOM 重建 ⇒ 新元素自动重算；
- **"跳过"的条件加上"属性仍然正确"**：多读一次 `getAttribute`（纯属性读取、不触发布局），
  被抹掉就按缓存值补写回去 —— 这一条才是治第三层的那一刀；
- **解析失败什么都不做**（不写、不摘、不缓存，下一轮再试）：改前"失败当非代码行 ⇒ 摘号"会把**已经写对的号摘掉**；
- 摘号另加一道确认（DOM 文本与该行源码一致）⇒ 引用区代码行的源码带 `> ` 前缀、DOM 里被隐藏，不会被误摘。

**复验**：光标停在开围栏上，`[1,2,3]` 在 1.2 秒后仍在；`--only=7.1…` 从 7/8 → **8/8**。

### 12.2 引擎侧（`kpTypesetPlugin`，三条闸门写在文件头）

- **不在键入路径上**：仅"阅读模式 + 用户显式开启 + 文档 ≤ 30 万字符"三条同时成立才跑；且只处理**视口内已渲染**的行。

- **尊重用户 CSS**：测量用**该行自己的 computedStyle**（font-style/weight/size/family + `letter-spacing`），
  渲染产物**继承同一套样式**、不写死字体 ⇒ 用户自定义 CSS 改字号/字体后断行会重算。

**视觉复核**（Lead 亲自看图，本会话无视觉子代理路由）：
`shots/typography-css.png` 与 `shots/typography-kp.png` 同一段落对照——两种模式都渲染干净、无重叠无溢出；

所以 KP 的增益表现为"各行更匀"而不是"天差地别"；正因为如此它**默认关闭**，由用户按需开。

### 12.4 ★ 接线过程中查出的两个真 bug（都不是"新功能没写对"，是既有代码的问题）

**（一）`knuth-plass.js` 对纯中文是坏的——而中文正是它的主用例**

- 症状：139 个汉字（16px、行宽 732）被断成 **133 行**；45 字（恰好一行）断成 **39 行**；西文（有 glue）正常。
- 根因：活跃窗口按**节点个数**限——`for (let a = Math.max(0, nodes.length - maxLagNodes); …)`。
  可节点数是 **O(i²)** 增长的（每个 i 对每个可行起点都生成节点）⇒ 到段尾时
  `nodes.length - maxLagNodes` 早已越过"起点 0"那个节点 ⇒ **整段一行的解被挤出窗口**，
  只剩"起点头部几个字"的解。
- 修法：窗口改成按**位置**限（`pos ≥ i − maxLagItems`），节点按 `pos` 分桶索引。
- 复验（`kp-selftest.mjs` / `kp-selftest2.mjs`）：139 字 **133 → 5 行**、45 字 **39 → 2 行**（含一个空收尾行，调用方会滤掉）、
  90 字 → 3 行、西文对照仍 4 行；调 `tolerance`（200→1e9）与行宽（200→1200）都不再改变结论。

**（二）装饰振荡：自己的产物把自己的判据否掉**

- 症状：快照里 `kpParas=0`，而引擎日志里那些行的孩子是 `1,1,1`（widgetBuffer + widget + widgetBuffer）——widget 明明在。
- 根因：幂等判据写的是"孩子必须恰好是一个文本节点"，而**我们自己套上的 widget 也是元素** ⇒
  第二次 build 把已排好的行判成"非纯文本" ⇒ 装饰被清空 ⇒ 下一轮又排上……来回振荡。
- 修法：判据改成白名单（文本 / `cm-widgetBuffer` / `.mp-kp-para`），并从**文档行文本**取内容而不是 DOM 文本。

**顺带两条 CM6 硬约束（都踩过，写下来免得再来一次）**：
1. **只改 `this.deco` 不会让视图重读装饰**——必须发一笔空事务（`view.dispatch({})`）推视图一次；
   否则"按钮文字变了、排版没变"。
2. **块级替换装饰不能来自 ViewPlugin**（`block: true` 会让整批装饰被拒：`kpParas` 8 → 0）。
   也试过"inline widget + 块级子元素"，会多撑一层 leading（同样 4 行 187px vs 125px）；
   最终解是 **inline 内容 + `<br>` 断行**，行盒模型与普通段落完全一致。

### 12.5 工具链：加了一个 fail-fast 构建脚本

`build-engine.cjs`：① 先做"CSS 模板字符串里反引号配平"体检（这个坑**连踩三次**：注释里写反引号会提前结束模板字符串）
② esbuild 失败**立即停止**，不同步、不打包 ③ 同步后校验壳里的 `app.js` 与引擎产物 sha 一致 ④ 可选打包。
起因：我先前把"esbuild 失败"和"打包+探针"串在一条命令里，结果**拿旧包出了新读数**（读数与代码不对应）——这类"尺子与对象不一致"是本项目反复吃亏的地方。

## §13 §7.8 在"排版美化"那轮全量里判红：**断言抓到了真问题，不是回归**

**读数**（产物 `a42b87814f8480c5`）：

```
① 视口无巨行 → p50=1.6ms（样本 30；打字结束时引擎文档 60 字符 ✗ 已被换成别的文档；落点=第 1 行第 59 列）

- 60 / 120 = **30 键 × 每键 2 字**（keyDown 的 `text` 触发一次输入，随后的 `char` 再插一次）

- 基座套件 72 项全绿；§7 其他 26 项全绿 ⇒ 只有这一项红，且红的原因是**测量对象被换掉**，不是性能回归
  （1.6 / 1.8ms 正是"空文档上打字"的速度）。

**意义**：这正是 §11.2 那道断言存在的理由——**它把一次"假绿"变成了一次"红"**。
在断言落地之前，同一情形会报 1.3~1.8ms 并判绿（§10.2 记的就是那次）。

**归因进展**：已交 `clobber-hunt` 队友做定点复现（A 组独占实例 / B 组故意并发两组对照），

### 13.1 归因结论（clobber-hunt 队友，证据在其 `FINDINGS.md` 与 `v2\` dump）

### 15.1 拍板：选 C（保持 20ms 阈值 + 三采样取中位）

**为什么不选 A（放宽到 30ms）**：那会把"将来真回归到 25~28ms"也放过去——标准一松就回不来。
**为什么不选 B（保持单次采样）**：同一产物时而 80/80、时而 79/80，验收变成看运气，
排查时还得靠复跑区分"运气"与"回归"。
**C 的意图**：阈值不动，只把"单次运气"消掉——同一条件连测 3 次，判**三次的中位数** <20ms，
三次读数全部写进报告（可复核是否只是被中位数掩盖）。

**实现**（`probe-310.cjs` §7.8）：两个条件**各连测 3 次**（共 6 轮 `typeKeys(30)`）；
每轮之间把视口/光标复位到该条件的同一口径（条件① 回文档开头与第 1 行行尾；条件② 重新把光标放到

## §16 导出链接上 Knuth–Plass（PDF），顺带修掉两个"字段被静默截断"的缺陷

### 16.1 为什么是"PDF 而不是 HTML 导出"

README 对用户的承诺是「**导出**采用 TeX 同源的 Knuth–Plass 整段最优断行 ✅（部分）」。核对下来：
- **2.x 线（已发布）**：`Typora-Editor-App/app/shell/export-render.js:2` 确实 import 了 `knuth-plass.mjs`，
  但**只在 PDF 分支**跑（`article.dataset.pdf` 为真时调 `typesetArticle`）；HTML 导出保持 CSS 两端对齐。
  README 那个"（部分）"指的就是这件事。
- **CM6 线（3.1.0）**：导出链里**一处都没有** —— 全仓唯一引用是本轮为阅读模式新加的那处。

⇒ 本轮的落地口径与 2.x **完全对齐**：**只有"导出 PDF"做整段最优断行**，HTML/文件夹导出仍走 CSS 两端对齐。

### 16.2 实现（三处小改，一个真源）

| 位置 | 改动 |
|---|---|
| `build-engine.cjs` | 新增一步：把 **2.x 那份 `knuth-plass.mjs`** 直接打包成 IIFE（`MarkPilot-CM6/renderer/pdf-typeset.js`，暴露全局 `MPKP`）。**不复制源码**：两条线共用一个真源，断行行为改一处两边一起变 |
| `export-pdf.js` | 新增**阶段 3.5**：打印窗口加载完、样式注入后，先按纸面宽度压 screen 布局，再注入排版包并调 `typesetArticle(body, 'p, li, blockquote p')`；统计进结果与阶段流水 |
| `main.js` / `host.js` | 预算参数 `sourceBytes` 透传；超预算/出错时给用户一句明说（与 2.x 同款文案） |

三条硬约束（写在 `export-pdf.js` 文件头，别来"优化"掉）：
1. **磁盘 HTML 一个字节都不改**：排版只发生在**这一趟打印的内存 DOM** 里 ⇒「导出为文件夹」的产物与 PDF 用的 HTML 仍逐字节相同。
2. **必须按纸面宽度量**：隐藏窗口是屏幕布局，`printToPDF` 是打印布局。排版前先把 body 压到纸面正文宽
   （A4 8.27in − 0.59in×2 ⇒ **680.64px**，user origin + !important），否则按屏幕宽算出的断行贴到纸上就是错版。
3. **预算与 2.x 同口径**：源 ≥300KB 或可排块 ≥1800 ⇒ **整体跳过**、回退 CSS 两端对齐（不做部分降级——同一文档里两段式排版肉眼可辨）。
   失败一律降级：`typesetArticle` 逐块 try/catch + `restoreBlock`，出错只是"这块不排"。

### 16.3 ★ 顺带查出的两个既有缺陷（同一类：**字段在管道里被静默截断**）

`main.js` 的 `export:htmlDone` 处理器此前只把 `{ok, file, error, mode}` 透传给启动器，**渲染侧一起送来的字段被丢掉**：

1. **`mathCss` 被丢 ⇒ PDF 里的公式只有结构没有排版**。打印层读的是 `html.mathCss`，永远读到 `undefined`
   ⇒ `session.mathCssSource` 恒为 `'none'` ⇒ KaTeX 类样式从未注入打印窗口。
   （文件里那段注释担心的"公式印成 dPdQ"就是这个后果。）**这是用户可见的既有缺陷，本轮一并修掉。**
2. **`sourceBytes` 被丢 ⇒ KP 的"源 ≥300KB 跳过"闸门形同虚设**（只剩块数闸门）。本轮新加的参数正好撞上同一个坑，顺手修正。

修法：把需要的字段**显式列全**（不整体透传，避免渲染侧多送的东西无声进入打印流程），并把
`mathCss.source/bytes` 放进导出结果 ⇒ 探针能直接断言"引擎的公式样式确实进了打印窗口"。

**另一处口径错位**：渲染侧送的是**字符数**，打印层的阈值是**字节**（2.x 口径）。中文文档按字符比字节会宽松约 3 倍
（首次取证读数：`sourceBytes: 1029` 对应的其实是 2901 B）。已按最坏 3 字节/字符折算，字段名写成
`sourceChars`/`sourceBytes`（折算上界）避免再混。

### 17.2 用户数据迁移（不改这一条就"设置全丢"）

产品名一改，Electron 的 userData 目录就从 `%APPDATA%\MarkPilot CM6` 变成 `%APPDATA%\MarkPilot`，

- 触发条件：新目录**没有** settings.json 且旧目录**有**；
- 动作：整目录拷一次 + 写一条留痕 `migrated-from-cm6.txt`（含来源目录、时间、**拷贝后 settings.json 的字节数**）；
- **旧目录原样保留**（新版万一有问题，退回旧版本设置还在）；
- 失败一律放行启动——迁移是便利，不是启动前提。

### 17.3 ★ 顺带查出的缺陷：settings.json 可能在**载入之前**就被默认值写盘

迁移落地后探针立刻报"设置没活下来"，诊断留痕是决定性的：

```
migrated-from-cm6.txt → copiedSettingsBytes: 354
settings:load        → {"bytes":332,"theme":"system","keys":["theme","recent","winBounds"]}
```

拷贝成功（354 B）而 25 ms 后载入读到的是默认值（332 B）。修法不是逐点抓写入者，而是**状态守卫**：
`loadSettings()` 完成前 `saveSettings()` 一律直接返回（并留痕 `settings:save-blocked` + 调用栈），
这样"谁想提前写"都会留下证据、且永远写不进去。

### 17.4 ★ 另一条教训：Windows 上 `APPDATA` 环境变量**不能**隔离 Electron 的 appData

第一版探针用 `APPDATA=<临时目录>` 来做隔离测试，结果留痕写着
`migrated from: C:\Users\…\AppData\Roaming\MarkPilot CM6` —— 迁移实际读的是**这台机器的真实旧目录**
（那里的 theme 本来就是 `system`，所以我的期望值 `dark` 当然对不上；我一度把它读成"迁移没生效"）。

原因：Windows 上 Electron 的 `app.getPath('appData')` 走 shell API，**不认子进程的 APPDATA 环境变量**。
修法：产品侧留一个**测试缝** `MP_MIGRATE_FROM`（只在迁移源目录这一处生效），探针用它指到假目录，
并**断言留痕里记的就是那个假目录**——即"断言隔离真的生效"，而不是假设它生效。

## §18 紧急三件：块公式围栏、引用区选中高亮、弹层关闭按钮（+ 缩放步进 5%）

### 18.1 块公式：引用区里的 `$$` 围栏永远配不上对（真 bug）

**现象**：笔记里「`> $$` / `> 公式` / `> $$`」这种写法整段当普通文本露出（用户截图：`$$` 与公式源码三行原样显示）；
把空隙去掉写成单行 `$$公式$$` 才渲染。

**根因**（用"把引擎里真实的 `scanMathSpans` 抠出来跑纯函数"的方式钉的，比读代码快且不会读漏）：
围栏判据是 `t.trim() === "$$"` —— 带 `> ` 前缀的行**永不匹配** ⇒ 该行不进 fences ⇒ 配对循环拿不到成对的围栏
⇒ 整块没有 span ⇒ 不渲染。**空行夹着的非引用形态本来就是好的**（对照：最简围栏对产出 display span ✓）。

**修法**：围栏判据改用**剥掉引用前缀后**的文本（`qText.trim() === "$$"`），并在配对时**逐行剥前缀**再拼 tex
（否则 KaTeX 会吃到 `>`）。前缀正则 `/^[ \t]*(?:>[ \t]?)+/` 兼容 `> > ` 与 `>\t`。

**取证**（`probe-urgent3.cjs` + 截图 `oom-hunt/urgent3/shots/math-shapes.png`）：

| 形态 | 修前 | 修后 |
|---|---|---|
| A 空行夹着的 `$$` 围栏对 | 渲染 ✓（一直正常） | 渲染 ✓ 居中块公式 |
| B 引用区 `> $$` 围栏对 | **不渲染**（三行原样露出） | **渲染 ✓ 居中块公式** |
| C 单行 `$$公式$$` | 渲染 ✓（行内） | 渲染 ✓ 行内 |
| D 引用区单行 `> $$公式$$` | 渲染 ✓（行内） | 渲染 ✓ 行内 |

判据（DOM 信号，因为引擎 KaTeX 走 html 输出、没有 annotation 节点）：块级 `.katex-display` ≥2、
行内 `.katex` ≥2、且四段源码**不再以字面量出现在行里**（leaks: []）。

### 18.2 引用区选中高亮看不见：底色盖住了选区层

**现象**：在引用块里拖选，看不见高亮（正文里正常）。
**根因**：引用底色是**行元素上的不透明背景**，而 CM6 的选区层是 `z-index:-1` ⇒ 被底色盖住。
**修法**：底色挪到行元素的 **`::before`**（`z-index:-2`）——选区层（-1）在它之上、文字仍在最上层；
边框/内距仍留在行元素上，横向位置逐像素不变（不碰 CM6 的选区层机制）。
**取证**：真实鼠标拖选引用正文 → selRects:1 + 截图 `quote-selection.png`：蓝底高亮**可见**（覆盖在引用底色之上）✓。

### 18.3 弹层右上角常住 ✕ + 缩放步进 5%

- **弹层 ✕**：此前只有 `dialog()` 自带关闭按钮，**弹层（`.mp-pop`）只能点空白处关闭**。
  修法：在**唯一的弹层构造点** `openPop()` 里统一插入 `.mp-pop-close`（✕，右上角），
  十几个入口（更多/表格/主题配色/表情…）自动全部生效。
  取证：点「更多」→ hasClose:true（位于面板右上 1140,46，面板 862..1176 × 40..483）→ 点它 → closed ✓。
- **Ctrl+滚轮步进**：`MP_ZOOM_STEP` 10 → **5**（键盘 Ctrl+=/- 与状态栏同一个常量）。
  取证：`mpZoom.get()` 100 → 105（一档 +5）✓。

### 18.4 ★ 过程中的自伤与教训：`String.replace` 把 `$$` 吃掉一个 `$`

给 18.1 落码时用的是 `s.replace(needle, text)`，而 **JS 的替换串里 `$$` 表示一个字面 `$`**
⇒ 落进源码的是单个 `$` 的比较 ⇒ **所有 `$$` 围栏识别全废**（连 A 形态都不渲染了），
而代码"看着像对的"、构建不报错——是靠"块公式又不渲染了"的**截图**才暴露的。

⇒ 已并入 `AGENTS.md` 错-5 第 4 条：**替换串含 `$` 一律用 replacer 函数** `s.replace(needle, () => text)`；
自证方式是"对含 `$` 的行数一遍 `$` 个数 + 跑一次行为探针"。

## §19 Typora 社区主题可直接安装（konayuki dark 验收）+ 全应用面板常驻关闭键

### 19.1 用户自带 Typora 主题：安装 → 改写 → 注入（验收素材 konayuki dark）

**为什么能这么快**：2.x 线早就有一份**纯函数**实现 `app/renderer/js/user-theme.mjs`
（`adaptTyporaTheme(source,{scope,surface})`：`#write`→写作区、`:root` 变量挂到作用域属性、
带相对 `url()` 的 `@font-face` 丢掉、`@media/@supports` 照留）。CM6 线**直接复用同一份真源**
（esbuild 打包，传 `surface: ".cm-content"`）——两条线的改写行为因此永远一致（AGENTS 错-4）。

**落地的三件事**：
1. 壳层通道 `theme:pickCss`（默认打开 Typora 的主题目录；上限 4MB）；
2. 引擎侧 `installTyporaThemeFromText`（核心，对话框与探针同源）/ `installTyporaTheme`（选文件）/
   `removeTyporaTheme` / `userThemeInfo`；设置面板新增「Typora 主题」一行（安装 / 当前 / 移除）；
3. **变量桥接 + 内联覆盖**：Typora 的 `--bg-color/--text-color/--code-bg-color/…` 映射到引擎的 `--mp-*`。
   注意内联覆盖是必需的——引擎的调色板把 `--mp-*` 写在 `documentElement` 的**内联样式**上，
   内联优先级高于任何样式表规则，只写一条桥接规则**改不动颜色**（实测：装完 bg 还是引擎自己的值）。

**★ 版式守卫（实测踩到才加的）**：Typora 主题是给 Typora 的**富块结构**写的（`#write` 上写着
`padding:60px 20px 120px; max-width:90ch; margin:0 auto`，正文是 `<p>`、行内是 `<strong>`），
而我们的编辑器是**逐行**结构（一个源码行一个 `.cm-line`）⇒ 直接套用会抢版式：
实测一段正文被拆成三行、行距被拉到 200px（截图存证）。
现在的口径：**主题只负责外观**（颜色/底色/字体/字重/字形/圆角/边框/阴影），
版面（display/position/宽高/内外边距/浮动/溢出/层叠/网格）一律剥掉——konayuki dark 实测剥掉约 3.6KB 声明。

**验收读数**（`probe-typora-theme.cjs`，主题文件取本机 Typora 主题目录里的 `konayuki-dark.css` 44.9KB）：

| 判据 | 读数 |
|---|---|
| 安装 | ✓ 改写后 80 条规则 / 113 个选择器（丢弃 274 个不相干选择器、保留 1 个 `@media`） |
| 变量接管 | ✓ `--mp-bg` `#1f2126` → **`#1a1b26`**、`--mp-fg` `#d7dae0` → **`#e5e9f0`**（正是 konayuki 的值） |
| 版式未被破坏 | ✓ 截图：段落/引用/列表/代码块/表格/块公式全部正常，行内标记不再被拆行 |
| 移除干净 | ✓ 样式表移除、作用域属性摘掉、`--mp-*` 回到引擎调色板值 |

**已知取舍（如实写在设置面板的提示里）**：主题自带的字体/图片文件**不会**跟着走（CSS 里的相对引用被中和，
否则整页 404）；标题样式暂未映射到引擎的 `.mp-h1…`（引擎标题不是 `<h1>` 元素），后续可加映射表。

### 19.2 全应用面板常驻关闭键（大纲除外）

用户报「设置的右上角关闭 ✕ 没做」——查下来是**关闭键会跟着面板内容滚走**：
`.mp-dlg` 自己是 `overflow:auto` 的滚动容器，而关闭键是 `position:absolute; top:10px` ⇒ 往下滚就出可视区。

修法分两层：
1. **钉住**：`.mp-dlg .close` 与 `.mp-pop-close` 都改成 `position: sticky; top: 0; float: right`，
   滚到哪儿都在（配一层底色，避免内容从下面穿过时糊在一起）；
2. **全应用单点保证**：不再逐个构造点去补（面板容器不止 `openPop`/`dialog` 两条路，表格菜单等自己造 `.mp-pop`），
   改成 **MutationObserver 兜底**：DOM 里一出现 `.mp-pop`/`.mp-dlg` 而它没有关闭键，就补一个 sticky ✕。
   例外只有大纲浮层与大纲停靠（用户明确排除）。**规则写进机制里，不写在记忆里。**

**验收**（`probe-panel-close.cjs`，10 个用例 / 8 个受判）：

| 面板 | ✕ 在 | 滚到底仍在可视区 | 点击能关 |
|---|---|---|---|
| 更多菜单 | ✓ | ✓（可滚动面板） | ✓ |
| 设置 | ✓ | ✓（可滚动面板） | ✓ |
| 导出…/ 关于 / 帮助 / 从浏览器打开… | ✓ | ✓ | ✓ |
| 工具栏·表情 / 工具栏·主题 | ✓ | ✓ | ✓ |

（表格菜单与图片对话框需要文档里有表/图才会弹，夹具里没有 ⇒ 跳过，不算失败。）
视觉存证：`oom-hunt/panel-close/shots/settings-scrolled-bottom.png`——设置面板滚到底，✕ 仍在右上角。

### 19.3 ★ portable 起不来的真因：**C 盘满了**（不是改名、也不是打包器）

改名后 portable 一直起不来（改名前的能起、干净重打也不行、桩退出码 2、TEMP 无残留、unpacked 正常）。
最后量出来的是环境问题：**C 盘只剩 0.10 GB**，而 `%TEMP%` 里堆了 **79.4 GB**
——235 个陈旧的 `ns*.tmp`（NSIS 残留）与便携桩解包残留 `3KS*`。
便携桩要把约 300MB 解包到 TEMP，磁盘满 ⇒ `ExecWait` 失败 ⇒ 退出码 2，看起来就像"桩坏了"。

清理后（`ns*.tmp` 64.5 GB + `3KS*` 0.93 GB）C 盘回到 65 GB，portable **10 秒内正常启动** ✓。
**教训**：这类"构建/启动莫名其妙失败"先量三条：磁盘余量、TEMP 体量、进程占用——
我把它们排在"怀疑改名/怀疑打包器"后面，白绕了两小时。
