## 0. 先说清楚：`）` 那个像素我没能复现，但**同一类缺陷在公式上是确定性的，已复现并修好**

`）` 本身我用两条输入通道、把能想到的变量都扫了一遍，**一次都没点出你说的现象**（下面第 3 节列了原始数字，

但你这句话把范围指对了——**"只是数学公式的问题"**。顺着这条线索，我在**公式自己的渲染结果**上复现了
一模一样的形状，而且是**确定性的**（同一段代码同一份文档，每次必现）：

> **点在公式渲染结果的某些像素上，光标会跑到这条公式源码的最前面。**

量出来的比例不低：在你文档第 227 行那条 `$f=f^+-f^-$` 上，沿渲染框每 4px 取一点、共 23 点，
**6 点**（26%）会跑到公式最前面，**右半也有 1 点**；光标偏移序列是
`[0,0,0,0,1,1,1,0,2,2,2,4,4,0,5,5,5,5,6,6,6,8,8]`——两处**回退**。

## 1. 根因（有取证，不是推测）

`js/math-source-map.js` 接管"落在公式渲染结果上"的点击，按落点把光标映射进源码。问题是**时机**：

| 时刻 | 同一个落点算出来的源码偏移 |
| --- | --- |
| `mousedown`（按下那一帧） | **1**（版面正是你瞄准的那个） |
| `mouseup` / `click` | **null**（算不出来） |

因为按下之后，产品自己的 `refreshMathEditing` 立刻把这条公式翻成**展开态**（源码顶上来、渲染结果退场），
渲染结果上的字形矩形随即量不出来（`scripts/acceptance/probe-paren10.cjs` 在同一事件序列上逐帧取证）。
旧实现只在 `click` 时算映射，于是**经常算不出来**，兜底那一行是：

```js
else placeCaret(root, code, 0);   // 一律扔到源码第 0 位
```

**"点公式中段、光标跑到公式最前面"就是这么来的。** 它还有一个更隐蔽的伴生毛病：KaTeX 的字形之间有空隙、
上下有 strut 留白，点进这些缝里本来就映射不到任何字形（实测占渲染框内取样点的 13~26%）。

## 2. 修法（两处，都在 `js/math-source-map.js`）

1. **落点在按下那一刻就映射一次**（`pointer.offset`），`click` 时直接用这个值，不再重算。
   理由就是上面那张表：按下时的版面才是你瞄准的版面。
2. **字形缝隙退到"最近的那个字形"**：落点既然在公式框里、又不落在任何字形上，就按离它最近的字形算，
   而不是返回"算不出来"。语义与浏览器"点空白处夹到最近位置"一致，也让"点哪儿光标在哪儿"是单调的。
3. 兜底那条 `placeCaret(code, 0)` 改成**按落点在公式框的哪一半决定贴哪一边**——即使前面两步都失败，
   点右半也不会再跑到公式最前面。

并在探针里改成**直接报错**，免得再骗自己。
