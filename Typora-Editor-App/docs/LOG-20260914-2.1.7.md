# 2.1.7 开发纪录（2026-09-14）

本轮起点是用户的一条报告与两条追加描述：

> 「至少我就知道一个，新开一个无文档载入的开始界面，里面的打开文件夹和打开文件的功能就是坏的。你继续查，不到下一组 10 个不许停。」
> 「再给你补 2 个 bug：1. 图片多选后无法使用退格键/del 键集体删除。2. 公式点击积分符号时光标落点正确，
> 但同时激活补全框，框的顶部远高于光标处，导致点击会误键入快捷公式。」

于是本轮的口径：**日常真人操作**里能碰到的缺陷，逐条排除探针自身误差后修好，并补上回归断言。

## 一、先解决"这类功能以前根本测不了"

被用户点名的两个功能——开始界面的「打开文件夹/打开文件」——走的是**操作系统原生对话框**。
渲染层的 CDP 事件送不进原生窗口，所以这整类日常操作（打开/另存为/导出/未保存确认/外部冲突/删除确认）
在仓库里**一条断言都没有**：不是没测，是测不了。

本轮补的基建（都在 `scripts/acceptance/harness.cjs`，不进产品）：

| 能力 | 做法 | 解锁了什么 |
| --- | --- | --- |
| `launch({inspect:true})` | 给 Electron 主进程开 Node 调试器（`--inspect=0`），解析 stderr 里的 ws 地址接上 | `session.main.js()` 主进程求值；`dialog.*` 换成脚本控制的替身（只顶替"用户选了什么"）；`shell.*` 换成"记录调用"（不点用户桌面） |
| `session.main.menu()` / `clickMenu(path)` | 直接读/点应用菜单项，绕过助记符与括号差异 | 菜单类日常操作（enabled 状态、勾选项、弹窗入口）首次可测 |
| `session.attachWindow(recId)` | 让主进程给目标窗口的页面打 `location.hash` 标记，再按标记挑 CDP 目标 | 往**第二个窗口**发真实输入、读它的 DOM |
| `inspectBrk: true` | `--inspect-brk=0` 在入口停住 → 装替身 → `Runtime.runIfWaitingForDebugger` | **启动路径**上的对话框（一次给 6 个文件的确认框） |
| `send()` 超时 | 60s 无回应直接报错 | 目标一关就永久挂住整个探针（被 Ctrl+W 卡死过一次） |
| 确定性会话绑定 | 启动后把会话钉在"第一个窗口"的页面目标上 | 多窗口时 `/json/list` 顺序不保证，曾把"在窗口一里打字"打进窗口二，整批断言全歪 |

两条探针纪律，本轮又各栽了一次，记在这里：
- **日志是追加写的**：主进程调试器地址必须只从**本次追加的那段**里取，否则会连到上一次运行的死进程。
- **"读数变了"不等于"东西动了"**：这个编辑器的滚动容器不是 `window`，`window.scrollTop = 2000` 会让
  读数变成 2000 而正文一动不动。滚动的判据要用"目标元素自身的视口位置"。

## 二、修掉的缺陷（按发现顺序）

1. **开始界面「打开文件夹」零反馈**（用户报告）。侧栏可见性是持久化偏好；收起来时文件树长在隐藏侧栏里，
   屏幕上没有任何变化。侧栏开着时，欢迎页那句提示只在启动时就带工作区才显示。
   修复：`ws-open` 带 reveal 标记 → 展开侧栏 + 补提示；启动恢复仍尊重偏好。
2. **正常退出清空会话**（对照实验证明：正常退出 windows 2→0，强杀保留 2）。
   修复：`quitting` 标记 + "只剩一个窗口"判据。
3. **文件树「删除（回收站）」不生效**：`window.confirm` 在 Electron 外壳页恒 false。
   修复：主进程原生确认框。同一类问题顺带修掉新建/重命名失败的 `alert`（同样不可见）。
4. **菜单「在此窗口打开文件…」开新窗口**：`chooseFile` 丢了 rec。修复：走 `openPathSmart`。
5. **文内锚点点不动**：主进程忽略 `#`。修复：渲染层 `scrollToAnchor`。
   踩坑：IR 里 `<h3>` 的 textContent 是 `### 第三节`，第一版逐字比对全部落空。
6. **Ctrl+多选图片后删除无反应**（用户报告）：两层原因——多选集合没被处理 + 多选后编辑区丢键盘焦点。
7. **矮窗口下补全面板压住被编辑行与鼠标**（用户报告）：钳位把面板推到行上。
   修复：两侧候选 + 评分，放不下就压高度（内部可滚动）。

## 三、验证

- 新场景 `79-daily-ops-2.1.7`：31 断言 / 8 证人，dev 全绿。
  关键证据：state.json 的 windows 条数（退出前后）、磁盘上文件是否还在（删除）、
  标题的视口位置（锚点）、图片元素个数（多选删图+撤销）、面板/行/鼠标三者的矩形是否相交（补全落位）。
- 回归：renderer 全套 **354 PASS**、media **28 PASS**、windows 套件全绿
  （含既有的"关闭的窗口从会话移除，不会下次又被恢复"与"退出时逐个确认未保存"两条断言）。
- 教训：`test:renderer` 里的 repairs 套件曾因 `.perf/图片 演示 (#1).md` 被上一次运行残留的进程短暂占用
  而失败一次（`UNKNOWN errno -4094`），单独重跑即通过——属于环境瞬时锁，不是产品问题。

## 四、仍然没覆盖到的

- **原生对话框的实际外观**（标题栏文字、按钮顺序）只能由人眼确认；替身只保证"交给系统的参数"正确。
- **拖放文件进窗口**（真实 OS 拖放）没有可靠的无头驱动方式：合成 `DataTransfer` 里的 `File` 拿不到真实路径
  （`webUtils.getPathForFile` 会返回空），测出来的失败是假失败，所以没有纳入。
- **导出 Word/PDF 的排版质量**只断言了"产物落盘 + 正文命中 + 页数"，版式仍需人眼。
- 本轮**只找到并修好 7 条**（用户要求的是 10 条），继续扫。
