# 2.1.10 取证与实施日志（2026-09-14）

承接 `LOG-20260914-2.1.9.md`（那一版修的是"按下落在公式上拖不动"）。这一版修的是用户第二次报的同一条
需求的**反方向**：从段尾往回拉到段首。

## 一 用户原话与线索

> 「目标, 从末尾拉到本段首个词"原命题",复制再粘贴, 只能贴出来最后一行. 且目前的交互没有任何选中区提示」
> 「只有现在这行下面加一个空行,才能从当前位置拉起复制整段. 貌似是文件末尾行」

第二条是关键线索：把"落点在公式渲染结果上"换成了"落点在段落空白上"，所以看着像文档末尾的问题。
核对源文件末尾：`数理逻辑1(1).md` 只以一个换行结尾（后面没有空段落）——用户的观察成立，但根因是落点，不是文档结尾。

## 二 两个真正的坏点

1. **兜底选区被规范收塌**。2.1.9 加的兜底（原生拖拽没做出来时自己建选区）用 `Range.setStart/setEnd`
   拼范围。DOM 规范规定：`setEnd` 的终点若在起点之前，起点会被挪到终点（等于把选区收塌）。
   "从段尾往回拉"正是反方向（探针读数：`anchor` 在源码 offset 15、`focus` 在段首 `text@0`、
   `why: "range-collapsed"`、`done: false`）→ 兜底从未生效。
   **改用 `Selection.setBaseAndExtent(...)`**（Selection API 自己处理方向），方向不再是问题。
   注意：**不要**先用一个 Range 试一遍来判断"是不是空选区"——那一步本身就把它收塌了（我踩过）。
2. **落点必须落在可选内容上**。命中测试发生在 mousedown 监听器之前，那一刻落点若还是
   `user-select:none` 的渲染结果，Chromium 不把这次按下当成可以起选区。所以**行内公式的渲染结果
   改为 `user-select:text`**（只发行内；块公式的点击/退格语义仍走 Vditor 的 rawblock 路径，未改动）。
   代价与护栏：光标可能落进 katex 子树，但"渲染结果内部不许编辑"由既有的
   `beforeinput` / 退格 / 粘贴守卫兜着（它们判的是"选区在不在预览里"，不依赖任何属性）。

## 三 兜底的三条分支（math-select-reveal.js 的 recover）

| 情况 | 锚点取法 |
| --- | --- |
| 按下落在公式渲染结果上（`grabbed`） | 把落点映射成源码字符偏移，并把这条翻成源码（拖拽已结束，这时顶掉渲染结果不会让锚点失效） |
| 按下落在正文里 | 用 `caretRangeFromPoint` 解析落点；若解析进了某条公式的渲染结果，就吸到那条公式的源码上 |
| 原生拖拽做出来了、但被"关在这条公式内部"（按下在公式上、指针已走远 >24px、整条选区还在同一条公式里） | 用我们自己的选区替掉它（这是 `contenteditable="false"` 围栏留下的症状） |

观察面：`window.__typoraMathRecover`（iframe 内）记录每一次兜底的 `why` / `anchor` / `range` / `text`，
探针与场景都靠它读数（与项目既有的 `window.__typoraScrollRestore` 同一种做法）。
