# LOG-2.2.4：Home/End 四个键的落点校正 + 合成光标（画不出来的光标，由我们补一条）

本轮起因是上一轮遗留清单里的"← 在个别行首会落到正文隐形位置"。查下去发现两件事：
一是**Home / End / Ctrl+Home / Ctrl+End 这四个键此前没有任何人管**，实测三条都错；
二是"光标看不见"其实分两类，其中一类**不能用挪光标的办法修**。

## 一 四个导航键的实测病象（`probe-real-ops --section=endkeys`，doc A）

| 按键 | 落点 | 用户看到什么 |
| --- | --- | --- |
| Home（标题行） | `SPAN.vditor-ir__marker[data-type="heading-marker"]`，层=围栏 | 光标跑到 `###` 里面，接着按 ← 完全不动 |
| Ctrl+Home | 同样落进第一块的标题标记 | 同上 |
| Ctrl+End | `P` 的元素级位置（偏移 1），矩形 0×0 | **光标没了** |
| Home（折行段落） | 上一行行尾（实测 x=876） | 光标跳到上一行末尾，不是本行行首 |

## 二 形态选择：接管按键 → 事后校正（走过一次弯路）

第一版写成"按键接管"（`preventDefault` 后自己算落点），代价是**把场景 75 的
「Ctrl+Home 到文档头再按退格」打红**，Vditor 那边还抛 `getRangeAt: 0 is not a valid index`——
接管按键等于把 Vditor 整套语义接管过来。改成**事后校正**：按键照旧交给 Vditor，
只在**落点明显坏了**的时候纠偏。`patchHomeEndCaret`：

- 坏位置＝隐形（0×0）／落在公式预览里／落在**非公式**标记里；
- **公式围栏（`$`、`$$`）不算坏位置**——"围栏当普通字符"是场景 101 钉着的契约，
  插一脚 101 就由 32/32 掉到 3/12；
- Home 在折行段落上按 Typora 习惯纠到**视觉行首**（连按第二次保留逻辑行首）；
- ←/→ 也接同一套校正，但**只认标记/预览**、隐形一律不碰；
- 记账改为"任意按键 + 鼠标点击后"都刷新锚点（原来只在 Home/End 里记，点一下再按 Home 会用旧锚）。

## 三 "光标看不见"分两类：一类该救、一类救不得（pitfalls §31）

用 `--section=navdetail` 在 doc A 的 `**非整数解**…` 那段取 5 个点，**2 个点光"点一下"就已经是隐形落点**：

| 落点 | 容器 | 画得出来 | 处置 |
| --- | --- | --- | --- |
| 段落内的元素级边界（`P` 第 N 个子节点之间） | 元素 | 否 | **不挪光标**（挪了＝改插入点） |
| 块里的空白/零宽哨兵文本（长度 1） | 文本 | 否 | **不挪光标** |
| 折叠态公式源码（`display:none`） | 文本 | 否 | **不挪光标**（合法落点，101 钉着） |
| 标题标记、公式预览里 | 标记/预览 | 是 | 该救（Home/End 校正做的就是这个） |

"挪光标"这条路的代价有实测：把"隐形就救"放宽后，
**107 由 15/15 → 13/15**（它断言"点在段落末尾打的字要落在**公式外面**"，挪了之后字跑进公式源码里）、
**101 由 32/32 → 30/32**。所以那类位置**只能从显示层解决**。

## 四 合成光标（`patchSyntheticCaret`）

位置、选区、DOM 内容一概不动，只在光标该在的地方画一条竖线：

- 颜色取主题 token `var(--textarea-text-color)`（与原生 caret 同源），2px、跟着闪烁（CSS 动画）；
- 只在"折叠 + 编辑器有焦点 + 原生 0×0 + 不在公式源码里"时显示；非折叠选区（有高亮）、
  失焦、滚动、IME 组字中一律不画；
- 几何：**只在本块内**找最近的可绘兄弟取其右缘/左缘，高度**限一行**
  （兄弟矩形可能是整块，实测 41px，照它画会跨到下一行——这条是看图发现的）。

**视觉验收**（用户令：光标必须靠截图看清）：`--section=shotproxy` 3 倍无标记截图。
实测 doc A 的 (700,458)：原生矩形 0×0，合成光标显示于 `{x:882, y:432, 高:25}`，
图上就是行尾"4 ×"之后那条与文字行同高的竖线。

## 八 三个遗留的本轮进展（2026-09-19 下半场）

### 8.1 #2 段间干扰：已修（探针侧）

给电池加了**段间隔离**：每段开跑前重新滚一次、点一个可编辑点、等布局稳定，且这一段不计入任何判据。
原因：`keys` 段会用 Ctrl+End 把光标留在文档末尾，下一段的第一次读数就撞在别人留下的状态上。
复验：doc A `--section=keys,vertical` 全绿（V1 60/60、V2 11/11、V3 49/49、V4 42/42）。
doc B 的组合跑单次超 10 分钟（工具上限），留待下一轮分批复验。

### 8.2 #3 跨块 `shift+→` 选区偶发重置：**成因未定，但排除了一个嫌疑**

复现（doc A，`--section=selstep --startx=52 --starty=415 --presses=60`）：
选区长度单调 2 → **37**，第 38 步塌成 **0**，随后从 **2** 重新长起来——锚点被换了。
频率：7 次跑里抓到 1 次（其余 6 次一路单调到 60），**时序相关**。

本轮试过的假设与结论：

| 假设 | 验证方式 | 结论 |
| --- | --- | --- |
| `math-select-reveal` 的 `onKey` 在每次按键 `dropAll()`（把展开的公式源码收回），选区盖着源码时被浏览器夹回 | ① 在 `hide` 上埋点记录"隐藏时的选区长度 / 是否被选区盖住"；② 把该分支注掉做 A/B | **排除**：整趟 shift+→ 走查（40 次按键）里 `hide` 埋点**一次都没触发**；注掉分支后 A/B 无差异（30/40 字两档都"选区保住"）。据此**撤回了**那处改动（未证实的修改不入库） |
| 探测/读数把选区改坏 | 同上（探针只读不写选区） | 排除（读数不改选区） |

下一轮的做法（已想好，只差实施）：**选举区改写者的埋点**——把 `removeAllRanges` / `addRange` /
`setBaseAndExtent` 三个 API 换成带栈记录的代理，跑同样那趟走查，抓一次塌陷就能看到"是谁写的"。
（同一个手法在本项目里用过：`probe-math-keys2.cjs` 的 Selection-API 代理 + selectionchange 时间线。）

### 8.3 #1 ← 在行首落到正文隐形位置：症状已被合成光标盖住

doc B 上 `←` 偶尔把光标放到"合法但画不出来"的位置（1/3）。
现在这类位置会显示合成光标，用户**看得见**；落点本身是否合理仍未定论——
