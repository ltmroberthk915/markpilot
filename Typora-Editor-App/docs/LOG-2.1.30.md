# LOG-2.1.30：未闭合 `$$` 围栏吃掉后续内容

## 一 用户报告

在真实笔记（`新建 Markdown 文档.md`，"线性规划-有约束/整数解"那段）上，`$…$` / `$$…$$` 少收尾时，
泄漏的数学区把周围内容一起带走：`**加粗**` 的星号不再渲染、复制出来的也是数学源码。
用户要求"彻底改用 Typora 处理这种 fence 的方法，不要再搞固定的块、代码区域"。

## 二 复现与根因

用真产物取证（`scripts/acceptance/probe-fence-leak.cjs`、`probe-lute-dollar-forms.cjs`），
把两条**互不相干**的机制分开：

**根因 1（本轮修）——Lute 的行首独立 `$$` 一旦没有闭合，会建成吃到文件尾的数学块。**
喂给 Lute 的每个样本都以非 `$` 开头、`normalizeMathFences` 完全没动手，Lute 照样把后续
`**加粗丙**` 收进 TeX（KaTeX 把星号画出来），`<strong>` 消失：

| 样本 | 输入 | `<strong>` |
|---|---|---|
| 9 | 行中未闭合 `甲$$a=b 乙` | `**加粗丙**` 正常加粗 |
| 10 | 行中未闭合 + 后有空行 + 加粗 | `**加粗丙**` 正常加粗 |
| 11 | **行首独立 `$$` 无闭合** + 后有空行 + 加粗 | **加粗丢失，整份文档并成一个 math-block** |

`normalizeMathFences` 原来在"找不到闭合"时**原样透传**，等于把这条漏洞放行——这是缺陷所在。

**根因 2（本轮不改，只记录）——`$$…$$` 变成块是 Lute 的既有行为，不是那段改写造成的。**
该文件注释断言"Lute 只认行尾的收尾 `$$`"，据此把 `$$公式$$` 文本化拆成独立块。实测**该前提不成立**：
样本 1–8 全以非 `$` 开头、改写分支根本没进，Lute 依然把行中的 `$$…$$` 建成块级 `div`
（`甲$$a=b$$乙` → `p / div / p`）。即 **Lute 没有行内 `$$` 的表示法**。
用户说的"固定的块、代码区域"来源在这里，属于另一轮的事（见第五节）。

## 三 修法

`math-markdown.js` 的 `normalizeMathFences`：块围栏开到文档结束仍未闭合时，在**第一个空行**处收尾
（没有空行则收到文件尾，与 Lute 一致）；收尾行沿用该块的引用/缩进前缀。
已闭合的块**一个字节都不动**——只在 `math` 仍开启时才插入，因此正经文档走不到这条分支。

### Step 1 · 非 UTF-8 文件不再被静默损坏

修前行为（变异测试复现）：`doc.js:244` 是 `fsp.readFile(file,'utf8')`，无 BOM 判定、无合法性校验；
非 UTF-8 字节被有损解码成 U+FFFD，默认开启的 1.5 秒自动保存把乱码写回原文件。全程零提示。

做法与守卫位置见提交信息。四个读盘点统一到 `readDiskText()`——**这是必须的**：监听器若按 UTF-8
读、而文档按 UTF-16 解码，两者一比会被判成"外部修改"，再用 UTF-8 乱码覆盖正确内容。

### Step 3 · 崩溃/异常退出的内容保护

修前：脏文档的快照间隔是 **5 分钟**，硬崩最多丢 5 分钟输入，而且**没有任何启动恢复入口**——
用户得自己知道去「文件 → 版本历史… → 恢复为副本」，否则不知道有东西可恢复。
`state.js` 用 `fs.writeFileSync` 非原子写 `state.json`，写到一半崩溃就截断成半截 JSON，
下次启动解析失败被**整个吞掉**、静默重置全部偏好（连 autoSave / snapshots 都被悄悄翻回 true）。

做法：
- `snapshots.js` 增 `atomicWriteSync`（同步版：state 的保存发生在退出/关窗路径上，`saveNow()`
  是被同步调用的，改异步会把"退出时最后那一下写盘"变成竞态）与 `full(file,id)`（整份快照正文）。
- `state.js`：改用原子写；解析失败时把损坏文件另存为 `state.corrupt-<时间>.json` 并记录
  `loadError`/`corruptBackup`，不再静默重置。
- `doc.js`：脏文档快照间隔 5 分钟 → **60 秒**（同哈希去重，无变更不落盘）；
  新增 `offerRecovery()`——打开文档时若存在"比文件新、且内容不同"的快照，问一句是否生成恢复副本。
  恢复只**生成副本**（`wx` 独占创建，永不覆盖），磁盘原文件不动。
- `main.js`：偏好损坏的提示放在**窗口建好之后**。

两个在实现里踩到并修掉的坑（都写进了注释，免得后人重踩）：
1. `snapshots.list()` **有意不带 hash**（UI 用的），不能拿它比较内容——改用 `full()` 读整份正文。
2. 判定必须**归一化行尾后比内容**：快照正文可能是 `diskText` 写过行尾的版本（CRLF），而编辑区
   一律 LF，比哈希会把"同一个内容"判成"有东西可恢复"。
3. 判定不能只看 `list()[0]`：打开时本函数之前就会写一条 `reason='open'` 的快照（内容==磁盘），
   它必然最新，只看最新就会被它挡掉、真正的崩溃残留永远问不出来（实测踩到，磁盘证据：同目录下
   `14:30:59` 那条 open 快照排在 `14:28:50` 那条 save-failed 之前）。改成**往回找第一条与磁盘不同的**，
   遇到 `reason='discard'` 则停（用户当时明确放弃过，不该下次开机再问）。

### Step 4 · 保真预言机（打开 → 改一个字 → 保存，除那个字外不许有任何变化）

这是"系统级"最关键的一招：此前所有"打开过我的文件之后它就被改了"的问题都靠手写探针逐个取证
（probe-file-fidelity、场景 77/78…），新出现一种就成一次用户报告。现在换成一条**通用**判据，
把这类问题的暴露从"用户报告"提前到"验收变红"。

期望值**从素材自身推导**（铁律 13）：原文件用什么行尾就还用那个行尾，原本末尾有没有换行就保持
原样——期望字节 = 去掉末尾那**一整个**行尾终结符（`\r\n` 或 `\n`）+ 'Z' + 原本的终结符，逐字节比对。
两档：**exact** 必须逐字节相等；**declared** 是已知损失，判据是"损失仍是声明过的形状"+"损失确实还在"
（被修好或被改成别的形状都会红，提醒升级成 exact）。

素材：13 个生成素材（含 CRLF/LF/无末尾换行/BOM/缩进代码/行尾两空格硬换行/软换行/围栏信息串/
行内 `$$`/块公式收尾后接正文/引用式定义/表格转义竖线）+ 2 份**真实素材**（受保护目录，只读复制，
原素材一个字节不动）。

验证数据：

| 项 | 结果 |
|---|---|
| 场景 `106-fidelity-oracle`（dev 产物） | **38/38 断言，15 证人** |

### Step 5 · 验收体系变真闸门（结构漏洞部分）

摸底时在本套体系里查出三处结构漏洞，它们让"机械上很强"的验收在关键处是空的：

**① `--accept` 没有通过判定。** 原代码是 `if (has('accept')) { 写基准 }`——**无条件写盘**。
一次红的跑、甚至一次 `--only` 的局部跑，都能把基准覆盖掉，退化从此无人拦。
现在只有"全场景通过"的一轮才允许写，否则拒绝并打印原因，同时 `exitCode=1`。
验证：`--only=restore-position --accept` → 打印"拒绝写入基准：本轮 0 个失败、未跑全场景"，
基准文件的 label/acceptedAt/指标数（`2.0.18|2026-09-11T07:46:35.216Z|45`）前后一字未变。

**② "独立证人"闸门实际上是空的。** 判据是 `witness.kind !== 'self'`，而全部 307 个调用点
传的都是一句中文描述，条件恒真、永远不触发——通道独立性只剩人工约定。
现在 `witness(kind, data, channel)` 支持第三个参数，通道取
`disk|clipboard|process|geometry|dom|self`，其中**只有前四个算"在产品之外"**；
场景**声明了**通道时，至少一条必须是这四个之一，否则当场红。
未声明通道的旧场景不在此列（**加法迁移**，不破坏现状），但每轮都会打印"待补见证通道"清单，
不至于被忘掉。

验证：场景 40 迁到 `disk`+`dom` → 11/11 通过；把那条 disk 临时改成 dom →
**11/12，新增失败** `独立见证通道（声明的通道里至少一条在产品之外） — ["dom","dom","dom"]`。
闸门确实会红，不是摆设。

**③ 最小自动触发**：新增 `npm run gate`（跑两个无 GUI 的守卫：`scripts/disk-encoding.test.cjs`
与 `scripts/verify-typora-themes.cjs`）。目前本仓库仍**没有任何 CI / git hook**，
40 个 GUI 场景与 20 多条 npm 测试全靠人手触发——`gate` 只是把"最该在提交前跑的两条"固化下来，
真正的自动触发（CI）不在本轮范围内。

**本步未做（如实记录）**：当前两条红的场景（`73-mixed-editing-stress` 的粘贴/剪切/撤销三条、

### Step 5（续）：`73-mixed-editing-stress` 结案 —— 是断言口径错，不是产品缺陷

这条从 2.1.24 起每一轮都红、每轮都被记为"既有问题、待单独排查"，共挂过五个版本
（LOG-2.1.24-2.1.25 §、LOG-2.1.25-2.1.26 §、LOG-2.1.26-2.1.27 §、LOG-2.1.27-2.1.28 §、
LOG-2.1.28-2.1.29 §"待单独排查"）。

**定位过程**：先看到三条失败指向同一根因（粘贴 2 次 → 剪切掉一个还剩 1 → 撤销回到 2），
读起来像"粘贴会把内容复制一份"这种严重缺陷。但场景把磁盘断言写在 `if (pasted === 1)` 里面，
失败时**恰好跳过了唯一能定性的证据**。于是做了一个聚焦探针（`probe-paste-double.cjs`）：
在一份两段的小文档上走同一条页面内菜单粘贴路径，三个口径分别量——DOM / `getValue()` / 磁盘
**全都恰好 1 次**。说明不是粘贴机制本身。

再把这个口径修进场景（磁盘读数一律取、并新增"文档口径与磁盘口径一致"断言），一次运行就拿到
决定性读数：

```
粘贴后：DOM 命中 2、文档(getValue) 命中 1、磁盘命中 1
落点：第 1 段：…包含中文与公式 $a_{0} 粘贴进来的验收字符串甲乙丙+ b_{0} = c_{0}$ …
```

**真因**：粘贴落进了**行内公式的源码**里；公式源码与 KaTeX 预览各含一份该字符串，于是
`surface.textContent` 数出 2，而文档与磁盘都只有 1。三条断言用的是同一个错误口径
（`surface.textContent.split(TEXT).length - 1`），所以三条一起红。
**产品行为是对的**——粘贴没有重复插入。

改法：三处计数改成数**文档**（`vditor.getValue()`），DOM 读数保留为证人（口径再次分叉能看出来），
并新增"文档口径与磁盘口径一致"的硬断言。

验证：`73-mixed-editing-stress` → **20/20 断言、6 证人**（此前 15/18）。

**顺带发现的真实问题（未修，另行记录）**：那次粘贴的落点确实**在行内公式源码内部**，
而不是公式之后。这与 Step 1 调查里"行尾外侧点空白落进上一处公式源码"属于同一类
落点缺陷，属 Step 6（输入层收口）的范围，本轮只记录、不改。

### Step 5（续）：`76-rightclick-and-caret-edges` —— 断言全过，红在验收工具的收尾竞态

读数：**105/105 断言通过、70 证人**，但场景被判失败，异常是
`Error: CDP 无响应（Runtime.evaluate，60000ms）：目标可能已关闭`。

这是**验收工具的收尾竞态**，不是产品缺陷：`harness.cjs` 的 `close()`（第 651-664 行）关 socket、
杀进程树，但**没有把仍在飞行中的 CDP 请求拒掉**——那个请求只能等 60 秒超时，而它的 rejection
在会话已经关掉之后才浮上来，于是把一条断言全过的场景判成失败。场景本身没有未等待的抓取调用
（`shot` 被 await 且在 try 里），三个会话各自 release，走的是正常收尾路径。

**修法（下一步）**：`close()` 在关 socket 之前，把该会话 `pending` 里的请求全部以
"会话已关闭（收尾时仍在飞行中的 CDP 请求）"拒掉；`run.cjs` 见到这个**特定**标记时，
若该场景断言已全过，就记为一条 `note`（收尾竞态）而不是 `error`，并在报告里明写出来。
不许静默吞掉——但也不该让工具的收尾问题冒充产品失败。

这是"让整轮变绿、从而能刷新基准"的**最后一个阻塞项**。

### Step 5（续）：76 的收尾/目标问题——加固验收工具，并把它从"中止"降级为"一条断言"

第一次读数是 `105/105 断言全过 + 异常 CDP 超时`，看着像纯粹的收尾竞态。按这个思路加固了三处，
再跑一次就露了真相：**105/106**，多出一条 `素材副本（305,561 字符）在产物里打开且图片已进 DOM — ready=false`。
也就是说那个会话**根本没就绪**——之前这条被"CDP 超时中止整条场景"整个盖住了。

**三处加固（都是"传输超时不该冒充产品失败、也不该静默"）：**
1. `harness.cjs` 两条 socket 的 `close()` 先把在飞请求以 `TEARDOWN_REJECT` 拒掉再关 socket——
   否则它们只能等满 60 秒超时，而 rejection 在会话关掉之后才浮上来。
2. `until()` 的轮询包 try/catch：等待就绪时目标没了，语义就是"没就绪"，返回 `false` 并把原因
   记进 warnings（此前 `jsSoft` 不吞 `send` 的拒绝，一次死目标挂满 60 秒再抛）。
3. `edge-helpers.saveAndWait` 的兜底保存同理：记下 `fallbackError` 而不抛，让"没落盘"由调用方的
   磁盘断言去说。
4. 附带：CDP 超时错误里带上**发送时刻的调用栈**——只报"60000ms 无响应"曾让我无法指认是哪个
   调用点发出的请求（这次就是靠它才认出是 `jsSoft` 这一路）。

**对 76 本体的结论（未结案，证据留档）：**
- 渲染进程**没有崩**：诊断日志无 `render-process-gone`/`unresponsive`/`fatal`，stderr 无崩溃输出；
- 那份素材**本身没问题**：独立探针 `probe-material-open.cjs` 实测 315,027 字节的素材
  **1.0 秒就绪**（imgs=3、134 块），全程最长无响应 **0.0 秒**，诊断日志里 unresponsive 计数 0；
- 所以是**那条会话的 CDP 目标消失了**，而 76 会操纵窗口、连续 launch 三个会话——
  嫌疑落在 harness 的窗口绑定/目标选择上（`bindToFirstWindow` 按 hash 标记挑目标），
  与产品无关。这条留作下一步：写一个只做"三次 launch + 两次窗口操作"的最小复现来钉它。

按"写最小复现"的思路往下追，一路把可能性排除掉，记录如下（都可复跑）：

### Step 6a · 落点缺陷定位：**不在我们这层**，是 Vditor/浏览器的兜底在决定

缺陷（用户文档上稳定复现，`probe-user-doc-click.cjs`）：在段落**行尾及其右侧的空白**处点击，
光标跑进**上一处行内公式的源码**里（`inMath: true, container: "CODE", offset: 101`）。
而同一时刻浏览器**原生命中测试**给的答案同样不可用：行尾 -4px 处给的是段落内一个靠近**行首**的
位置（`offset 5`），行外 +40px 处直接给 `none`（那里没有任何文本位置）。

**逐层摘除（每次都跑同一个探针，读数完全一致才继续摘）**——把"是不是我们的处理器干的"钉死：

| 摘掉的东西 | 位置 | ③ 行尾 / ④ 行外 的落点 | 结论 |
|---|---|---|---|
| （基线） | — | `inMath:true, offset:101` | 缺陷复现 |
| `installMathSourceNavigation` | `math-source-map.js` | **完全相同** | 不是它 |
| `fenceClick` 捕获期 mousedown | `math-edit.js:876` | **完全相同** | 不是它 |
| `installMarkerCaretGuard` + `installMathSelectionReveal` | 两个模块 | **完全相同** | 都不是 |

四次读数逐字相同（`{"index":5,"inMath":true,"inPreview":false,"offset":101,"container":"CODE"}`）。

**结论**：这条缺陷**不由我们任何一个光标模块产生**——是我们这层之下的兜底（Vditor 的 IR 点击
解析 / 浏览器的最近位置夹取）在"落点后面已经没有字形、没有可选文本位置"时，把光标放进了最近的
**可编辑元素**，而那个元素恰好是行内公式的 `<code>`。

**这条结论改变了修法**，也正好印证了 Step 6b 的前提：既然不是某个处理器算错，就**没有一个处理器
可以改对**——必须**新增一个权威的落点解析**去覆盖它："落在某一行最后一个字形之后 → 光标落到这一行
的文本末尾"。这与 Step 6b 要做的"视觉位置→源码偏移的唯一权威"是同一件事，所以合并进 Step 6b 一起做，
不在这里打补丁。

摘除全部用 `npm run sync` 还原，`ABLATED` 残留计数 0。

### Step 6b（第一件）：行尾空白点击的权威判定 —— 已实现，但**没有套件覆盖**（如实记录）

**做了什么**：新增 `installLineEndCaret`（`typora-patches.js`，与 `selectOutside` 同一模块）——
落在"某一行最后一个字形右侧"的点击，按几何找出落点所在行，把光标放到这一行的末尾；行末若是
行内原子（公式/图片），用 `selectOutside` 落在它**外侧**（与方向键走出公式同一条路径，避免落到
零宽 `$` 标记上）。只管单次左键、无修饰键、且没有拖拽的手势。

**实测效果**（用户文档素材 `probe-lineend-typing.cjs`，同一落点对比）：

| | 修前 | 修后 |
|---|---|---|
| 公式状态 | **被展开** | 不展开 |
| 光标 | 公式源码 **offset 0**、1.6s×8 次采样**无可见矩形** | 段落正文位置，有可见矩形 |
| 打字落点 | 写进公式源码 | **落在公式外面**，公式源码一字不变 |

**回归**：101（32/32）、83（10/10）、85（11/11）、91（26/26）、92（44/44）、74（41/41）全绿，
其中 92 的 `inline-box.click-offsets-match=4` 说明像素→偏移映射仍然精确。

**没做到的事（关键，不许含糊）**：**没能为它写出一个会失败的验收场景**。试了两版素材：
1. `$a+b$` 单独成段 —— 摘掉修复后场景**照样全绿**（反假通过把它抓出来了：那是个**假测试**）；
2. 一条长公式 —— 行内公式**溢出而不折行**（实测 1537px、`lineCount:1`），复现不了缺陷的几何。

缺陷需要"某一行的最后一个字形**略早于**容器右缘结束"这种几何（用户文档里是 883 vs 894，10px 余量），
这个条件取决于具体文字与版心，没法用固定素材稳定造出来。所以**该场景已被删除**——
留一个"通过但空洞"的场景比没有更糟，它看起来像有覆盖。

**当时的空白**：这条规则只有**探针级**证据（对用户文档素材跑出来的上表），**没有常驻套件守着**。
下一节把它补上了。

### Step 6b（第二件）：触发条件钉清 + 场景 107 常驻守住（已闭合）

**先把"到底什么几何才会发病"问清楚。** 三条探针按顺序做，每一步都排除掉一个假设：

1. `probe-lineend-synth.cjs`：把"行末余量"（本行最后一个字形右缘 → 段落右缘的距离）当成参数扫。
   一屏铺 `第 n 段：A…A $x+1$`（k 逐段递增 → 余量从 738px 递减到 7px，再跨折行跳回 799px），
   每段在「公式右缘 +4px / 段落右缘 -3px / 段落右缘 +40px」各点一次，然后**真的打一个字符**再读回
   段落源码与公式源码。**结果：修前修后逐字节相同**——说明这条几何里我们的规则要么没触发、
   要么触发后落到跟兜底同一个位置。**结论：余量不是触发条件。**
2. `probe-lineend-dom.cjs`：把两张素材对齐，沿公式右缘逐点问**浏览器自己**（`elementFromPoint`
   + `caretRangeFromPoint`），并把公式节点的 DOM 子树连盒子倒出来。差别当场现形：

   | | 合成段（`$x+1$`，不折行） | 用户文档（末条公式**折行**，盒高 41px / 行高 25px） |
   |---|---|---|
   | 公式右缘 +4px 处原生 caret | 段落里的正常位置 | **预览子树里的位置**（`inPreview: true`，文本 `4×`） |
   | 命中元素 | `<p>` | `<p>`（但 caret 被夹进预览） |

   **触发条件是"公式在视觉上折行"**：KaTeX 把公式拆成多个 `.base`，在行间断开；折行后公式的
   包围盒是一个**矩形**，把"上一行尾部右侧那块空白"也盖在里面。在那一小块空白上点，浏览器的
   原生命中测试给的是**预览子树里的位置**——那不是可编辑位置，Vditor 的兜底于是把公式展开、

**显式补偿**（需要量几何时把该块临时切回 `visible`）。所以无论上游那句话成立与否，我们的用法都是有界

### 追记 · 75/76 的"目标丢失"结案：两件事叠在一起，都已处理

之前一直挂着的"76（以及 75）会间歇性丢掉页面目标（`存活页面目标=[]`）"，本轮钉清了，**是两件事叠在一起**：

**① dev 模式下打开受保护素材，浏览器进程会哑掉一两分钟（这是迭代环境的成本，不是产品缺陷）。**
`probe-target-timeline.cjs` 逐秒记时间线（素材副本 315,027 字节，dev 冷 profile）：

| t | `/json/list` | 页面求值 | 素材状态 |
|---|---|---|---|
| 0.0s | 200，1 个页面目标 | 1ms | 未开始 |
| 1.0s – 28s | **超时（请求本身 4s 不答）** | 超时 | —— |
| 28.1s | 超时 | 1037ms | 编辑面在、内容还没上屏 |
| 34.2s | 200，1 个页面目标 | 1ms | **已完整渲染（295 条公式、3 张图）** |

子进程退出码全程 `还活着`，应用自己的 stderr 干净（只有沙箱告警），说明**不是崩、不是死**——
是打开的这几十秒里主/渲染线程都在忙。同一份素材在**安装版**里一次都不哑（见下表），
所以这是 dev（未打包、未压缩、冷代码缓存）的启动成本。**推论：素材类场景要在 installed/packaged 上跑**。

**② 验收工具自己错杀：`until` 在第一次传输错误就放弃，把剩下的整段预算作废。**
旧实现 `catch { …; return false; }`——180 秒的等待预算，第一次"目标暂时不答"就当场判失败。
dev-76 那一轮的红断言 `素材副本…在产物里打开 — ready=false`、以及被误读成"目标选择有问题"的
`存活页面目标=[]` 警告，都是这么来的（警告里 `主进程窗口=null` 也在提示：那一次根本没开 inspect）。
**改法**：传输错误记一条现场（第一次）后**接着等**，只在整段预算里一次都没读到就绪时判失败。

**结果**（`installed`，2.1.29 产物）：

| 场景 | 结果 | 耗时 |
|---|---|---|
| 76-rightclick-and-caret-edges | **114/114 断言，78 证人** | 64s |
| 75-edge-ops-not-covered | **50/50 断言，85 证人** | 55s |

**如实记一笔**：这两次安装版运行里**一次传输错误都没有**（警告 0 条），所以②那条改动
**不是这两次变绿的原因**——变绿的原因是①（换成安装版跑）。②的价值只体现在"目标短暂不答"
这一种情形上，证据是上面的 dev 时间线，不是这两次绿。dev 下同一场景仍然会红（180 秒预算不够
撑过那个哑窗），这是**迭代方式**的问题，不是产品的。

### Step 6b（第三件）：映射"代号化 + 重算"——**实测后判定不做**（附数据），另记一处真实分叉

计划里这一件是"把映射做成 `{源码, 映射表, 渲染代号}` 三元原子事实；代号变了就用**冻结的落点**
在新代号上重算，而不是返回 `null` 掉进兜底"。做之前先量了这两件事，结论都是否：

**① "预览落后于源码"这个窗口，可点中，但**不是**计划设想的那种形态。**
`probe-stale-map.cjs`：每轮把光标放到公式源码末尾 → 敲一个字符（触发重渲染）→ **立刻**点公式中段
的一个字形；页面内观察器在 mousedown 捕获阶段（早于产品处理器）记下那一刻的 `data-math` 与
`<code>` 源码。12 轮：

| 点击那一刻的预览状态 | 次数 | 落光标的结果 |
|---|---|---|
| **预览此刻不存在**（`data-math` 读不到，提交换 DOM 的瞬间） | **9 / 12** | 5 次停在原处（源码末尾）、2 次落到点中的字形、2 次到别的偏移 |
| 预览存在但落后于源码 | **0 / 12** | —— |
| 已同步 | 3 / 12 | 全部落到点中的字形（正确的那个） |

**"预览存在但落后"一次都没出现**，而代号化重算只在那种形态下才有东西可重算：预览不存在时
**根本没有任何映射表**可用，"冻结落点在新代号上重算"无从谈起。可复现的那 9 次里，代价是
"这一下点击被吞掉（光标留在原地）"——比接一个猜测（贴到公式最前/最后，正是用户抱怨过的那类）
更轻。所以**这件不做**，不是"来不及"，而是**实测证明它解决的问题不存在于用户能触发的形态里**。

**② 三个消费方其实早就共用同一套映射，不需要"逐个迁移"。**
`math-select-reveal.js`（拖拽）与点击路径都走 `sourceOffsetAtPoint` / `targetOffset`；
`split-navigation.js` 也 `import {mappedMathNodeAtPoint}`。

**但发现一处真实分叉**（记账，不在本步改）：`split-navigation.js:199` 与 `:544` 拿到共享命中测试
给的**符号节点**之后，自己去读 `symbol.dataset.typoraSourceStart` **取偏移**——绕过了
`targetOffset` 的三条规则（末字形→源码末尾、命令→反斜杠之后、右半边→字形之后）与那条一致性
校验。于是"点哪儿"和"在分栏/大纲里导航到哪儿"对同一个字形可能给不同偏移。
**为什么本步不改**：分栏（split）是**零覆盖**子系统（`grep split scenarios/*.cjs` 只命中
`String.split`），在零覆盖的地方改行为等于造一个没人守的改动——按纪律先补覆盖再动它，
所以这条挂到 Step 7 的"分栏冒烟"里一起做。证据：`scripts/acceptance/probe-stale-map.cjs`、
`.perf/repro-stale-map/stale.json`。
