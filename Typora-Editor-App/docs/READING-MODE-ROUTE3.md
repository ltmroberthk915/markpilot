# 阅读模式（融合路线 #3）设计与实测 — 2026-09-10

> 代码：`extension-src/render/js/reading-mode.js`、`css/reading-mode.css`，
> 接线在 `typora-patches.js`（安装）与 `toolbar.js`（工具项）。
> 证据：`.perf/reading-mode-probe.json`、`.perf/recon-reading-mem.json`；
> 探针：`scripts/reading-mode-probe.cjs`、`scripts/reading-mode-edge.cjs`。

## 1. 目标与做法

大文档（34.8 万字符 / 2576 顶层块 / 5689 公式）在编辑态必须保完整 DOM（contenteditable
的硬约束），所以"砍 DOM 提性能"只能落在**只读面**上。阅读模式复用 Vditor 自带的
预览面（`toolbar.elements.preview` 工具项 → 全宽只读渲染面），只对它做**窗口化**：

- 顶层块维持"一个位置一个元素"：挂载时放真实节点，卸下时放**等高占位盒**；
- 占位盒是 `div` + 逐块实测的 `height` 与复制过来的 `margin-top/bottom`（→ 与相邻块
  的外边距折叠行为一致），因此换出/换入不改总高；
- 占位盒里放该块的**纯文本**（去掉 KaTeX 的 MathML 注释层与复制按钮），
  `color: transparent` + `overflow: hidden` 裁掉：Ctrl+A / 跨未挂载区拖选时浏览器
  原生复制仍然拿到完整正文，不需要伪造剪贴板载荷（实测全选文本 217899 vs 全文纯文本 216945）。

编辑面完全不动：进入阅读模式时 Vditor 把编辑面 `display:none`，编辑 DOM、撤销栈、
选区、序列化一条都不碰。

## 2. 成本模型订正（重要）

立项时的三点拟合给出"边际 2.5–4.5KB/DOM 节点"，据此预估 27.2 万节点 950MB →
150–250MB（省 70–80%）。**实测没有复现这个比例**，原因是 privateBytes 的大头不是 DOM
节点数：

| 配置 | 预览面节点 | 全页节点 | renderer privateBytes |
|---|---|---|---|
| 编辑态基线 | 0 | 272411 | **1011–1101 MB** |
| 原生预览面（Vditor preview-only，未窗口化） | 129005–135706 | 400818–407519 | **954 MB** |
| 预览面窗口化 | 2881 | 274701 | **711–768 MB** |
| 再把编辑面 DOM detach（仅测，不落地） | 3045 | 5924 | 700 MB |

- 把编辑面 `display:none` 本身就释放了它的布局/绘制对象（1052 → 954MB）；
- 窗口化再把预览面 13.5 万节点降到约 2.9 千，privateBytes 再降到 ~750MB；
- **detach 编辑面 26.9 万节点只释放约 2MB**——节点被引用着就不会被回收，
  真正释放必须重建（代价是退出时整篇重新解析渲染，不可接受）。
  这也是为什么"点开编辑面时再重建"没有落地。

**结论（本机、教材合订本.md）：阅读模式把渲染进程 privateBytes 从约 1011MB 降到约 750MB
（−26%），预览面 DOM 从 13.5 万节点降到约 2.9 千（−98%），滚动 59.9fps / 最差帧 16.9ms。**
不是 70–80%，但可重复、方向一致；立项目的仍是成立的（阅读大文档更省内存、更顺）。

## 3. 关键实现决策与实测学费

1. **进出复用 Vditor 自带的 preview 工具项**（`button.click()`），不自己复刻
   `preview.element.style.display` / 工具栏禁用 / outline 重排那一套。工具项缺失时
   才走等价的兜底路径。注意 `preview.render` 的第一道门是
   `"none" !== this.element.style.display`，且渲染在 `preview.delay` 之后异步发生。
2. **绑定必须早于窗口化**：窗口化后渲染面里只剩占位 `div`，`previewBlocks` 认不出块种类，
   实测绑定只剩 95/2576 条。先绑定 → 再窗口化。
3. **一次 `replaceChildren` 取代逐块 `replaceWith`**：2576 次 replaceWith 的样式自失效
   累计实测 **5.1s**，整份子节点列表一次替换后 **234ms**。退出同理（还原顺序表一次替换）。
4. **占位盒必须复制外边距**：占位是 `div`，若只给高度，相邻块的外边距折叠结果就变了；
   复制 `margin-top/bottom` 后总高偏差 <0.5%（与 CV 同口径的一次总量校准兜底）。
5. **窗口化等公式队列清空**：未渲染公式的块更矮，提前量高度会系统性偏小（CV 同款坑）。
   代价是公式极多的大文档要等公式渲染完才窗口化；这段时间阅读面已可用，只是还在全量 DOM 上。
   （另一条路是提前窗口化 + 挂载时重新排队渲染公式，但 `commit` 会丢弃已断连节点的作业，
   重挂后公式会停在源码态，所以没走。）
6. **落点/大纲依赖"块↔源码区间"绑定**：`RenderJSON` 是大头（12 万字 **2.25s**，
   `markdownLocations` 只占 20ms），因此只在源码变化时算一次，窗口缩放只重量高度。
7. **大纲跳转按标题 id 查绑定表**，不用文档 `querySelector`：目标标题几乎总在窗口外
   （未挂载），文档里查不到；也不能用"大纲条目序号"，因为大纲只列 470 条而标题有 385 个
   顶层块（含嵌套时更多），序号不是一一对应。
8. **退出时清空预览面**（源码视图除外）：否则这次阅读会把十几万节点留在编辑态常驻
   （Vditor 原生预览模式的既有行为）。清空后源码视图仍会自行重渲染预览（已断言）。
9. `prioritizeViewport` 的根选择器补上 `.vditor-preview .vditor-reset`：源码视图与阅读模式下
   预览面才是可见渲染面，否则视口内公式会退到 FIFO 队尾。
10. `previewBlocks(coarse)` 跳过程序块的高度/宽度读取：粗绑定不需要"源码还是预览可见"，
    而每次 `getBoundingClientRect()` 都是强制布局（5689 个公式块实测秒级）。

## 4. 已知边界（v1 明确不做）

- **查找**：Ctrl+F/H 在阅读模式里**退回编辑态**再打开查找栏。查找栏与高亮建立在编辑面
  DOM 上，窗口化后未挂载的块既搜不到也高亮不了；与其做半个实现，不如明确交接。
- **点击进编辑的落点是块内按比例**（源码偏移 ↔ 渲染文本长度并不同构），不是逐字符精确。
- **切到其它块才渲染**：阅读面里未挂载块的公式在挂载时才可见（不是问题，但意味着
  "滚动时会有极短的渲染延迟"）。
- 预览面的 Desktop/Tablet/Mobile 预设按钮在阅读模式里隐藏（切宽度会让占位高度失效）。

## 5. 门槛（未过不许改渲染层）

进入阅读模式必须过：`reading-mode-probe.cjs`（12 万字，含窗口化生效、总高不变式、
全选复制完整、任意滚动位置无空白、大纲跳转、点击进编辑落点、二次进出、Esc 清场、
外部重载安全、阅读后源码视图仍正常、控制台零项目级报错）；
`reading-mode-edge.cjs`（小文档不窗口化、空文档、表格/公式点击、缩放重排、连点、
销毁、打字不改文档、查找交接）。小文档（顶层块 < 1200）完全不窗口化，零规则命中。
