# MarkPilot 2.1.26 → 2.1.27 工作记录

本轮只做一件事：修「大文档撤销把离屏跳过的占位高度冲掉」这个缺陷（用户问"大文件带公式编写还有没有优化空间"，
测量时撞出来的）。② 给 Vditor bundle 打补丁（选区复位/DOM 查询占打字成本约 57%）留作专门一轮；③
收窄 `refreshMathEditing`（视口内条件约 4.3%）按用户决定不做。**本轮没碰 ② ③。**

## 一、缺陷与触发条件（钉死的证据）

现象（`scripts/acceptance/probe-cv-loss-timeline.cjs`，145,176 字符 / 1843 块 / 2371 处公式）：

| 步骤 | 内联 `contain-intrinsic-size` 块数 | 文档总高 |
| --- | --- | --- |
| ① 刚上屏（离屏跳过已启用） | 1843 / 1843 | 75,745 px |
| ② 连打 10 个字（公式队列仍在渲染） | 1842 / 1843 | 75,753 px |
| ③ **连撤 10 次** | **0 / 1843** | **606,128 px（8.0 倍）** |
| ④ 之后静置 90 秒 | 0 / 1843 | 606,128 px（**不自愈**） |

机制：撤销是 HTML 快照恢复（实测每次 Ctrl+Z 整篇 `innerHTML` 重写 1,024,210 字符、解析约 10ms）。
当撤销走回「离屏跳过启用**之前**」的那份初始快照时，内联占位高度随旧 DOM 一起被换掉；新元素既没有内联值、
浏览器也没记住它们的高度，跳过块退回 `large-doc.css` 的兜底 320px（1843×320≈590k，与实测 606k 吻合）。
后果：滚动条比例失真、跳过的块按错误高度占位、"阅读位置记忆"漂移，且**不会自己恢复**。

## 二、修法（`extension-src/render/js/large-doc.js`）

1. 量高抽成 `measure()`，并把「每块高度 + 真实总高」缓存下来。
2. 子节点被换掉时按缺失规模分两档补回：
   - **少量缺失**（正常编辑重建的那一块）：只补那几块，读它自己的 `offsetHeight`；读到兜底值 320px 说明它
     还没被渲染过，跳过不写（避免把兜底值当成真实值记下来）。实测 **1–3ms/次**。
   - **大面积缺失**（撤销/重做/setValue 的整篇快照恢复）：**先用缓存值铺回**（写一趟 + 读两次 `scrollHeight`
     做总量校准），实测 **10ms**；只有当块数与缓存相差超过 2%（内容结构真的动过）才退回「摘掉 CV、重量全篇」。
     —— 这一步是有实测依据的：直接摘 CV 重量全篇在公式密集文档里要 **430ms**，一次可感知的卡顿；
     缓存铺回把同一个修复压到 10ms，且总高误差 0.01%（75,753 vs 75,753）。
3. 走 `requestIdleCallback`（1.5s 兜底）+ 120ms 去抖，不与打字抢主线程；补完自检一次，没补干净接着补。
4. 新增自证字段 `window.__typoraCv = {enabled, repairs:[{mode, ms, ...}]}` 供验收与排查读取。

## 三、验收

新场景 `scripts/acceptance/scenarios/97-large-doc-cv-repair-2.1.27.cjs`（11 断言 / 4 证人）。
判据不用"产品自报"，用**每块平均占多少像素**：真实约 41px、坏掉时约 329px（≈320px 兜底签名），阈值 100px/块。

A/B（同一份素材、同一套判据）：

| | 安装版 2.1.26（未修） | 安装版 2.1.27（已修） |
| --- | --- | --- |
| 打开后 | 1843/1843、41.1 px/块、75,745 px | 同 |
| 打字 5 次后 | 1842/1843、41.1 px/块 | **1843/1843**、41.1 px/块（每次 1–3ms 补回被重建的那一块） |
| 连撤 8 次后 | **0/1843、328.9 px/块、606,128 px** | **1843/1843、41.1 px/块、75,753 px**（`full-cached` 10ms） |
| 之后继续编辑 | 一直坏（不会自愈） | 正常，且不再触发全量补回 |
| 场景结论 | 4/11（撤销那几条红） | **11/11** |

副作用对照：
- **打字延迟不变**：视口内 20 键均值 40.0ms（2.1.26） → 39.8ms（2.1.27）；p95 54ms 不变；每键那 1–3ms 的补回没体现出来。
- **滚动不变**：帧间隔 16.7 / 16.8ms、掉帧 0（场景 60 通过）。
- 相邻场景子集（40 / 60 / 72 / 80）全绿；大文档滚动编辑（72）16/16。

## 四、过程中的自证与纠错（如实记录）

1. 我第一版修复走的是「摘掉 CV 重量全篇」，实测 430ms —— **没有接受**，改成缓存铺回（10ms）。这是"先量再收"。
2. 场景 97 初版把状态读在**外壳页**的 `window.__typoraCv`（守卫挂在编辑器 iframe 的 window 上），
   于是 `enabled:false`、`repairs:[]` 同时出现，看起来像"修复没跑"。改正读数作用域后才看到真实记录
   （`full-cached`）。教训：自证字段要连"读的是哪个 window"一起写清。
3. 40-restore-position 在一次 dev 子集批量跑里出现 38px 偏差（基准 3px）；**单独重跑两边各 2 次全过**
   （dev 4px / 旧版 3px），安装版全量跑里 11/11 —— 判为批量跑的抖动，已留记录，若再现再查。
4. 第一版断言里"每次编辑都会补回 1 块"被写成了"不允许出现补回"，属判据写错，已改成"只拦额外的全量补回"。
