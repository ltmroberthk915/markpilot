## 3. 根因与修复（两处）

### 3.1 【冷启动 1.1s】asar 内文件不能用 `open`/`createReadStream` 服务

**证据链**

1. 现象：安装版页面内 1218–1261ms，开发树 234ms（同一份 index.html/index.js/素材）。
2. 拆解：`fs.openSync(<asar>/…/lute.min.js)` **868ms**、`readFileSync` **1.1ms**、`promises.open` **0.4ms**；
   耗时与文件大小成正比（290KB→93ms、44KB→1.3ms、package.json→4.9ms），且**只有第一次付**。
3. 定位：`app/main/server.js` 的 `sendFile` 用 `fs.createReadStream(file).pipe(res)`，内部走 `open`。
4. 决定性 A/B（生产代码 `startServer`，`rendererRoot` 指向已安装 app.asar）：

   | 服务方式 | lute.min.js(3.8MB) | index.min.js(290KB) |
   |---|---|---|
   | `createReadStream` | **1161ms** | 78ms |
   | `readFile`+`res.end` | **13ms** | 1.0ms |

**修复**（`app/main/server.js`）：`sendFile` 改 `fs.readFile` 整读后一次回写（带 `Content-Length`，
HEAD 走对），注释里写明"不要再改回 createReadStream"。

**永久防线**
- 单测 `scripts/acceptance/external-resource.test.cjs`：`server.js` 里不许出现 `createReadStream|openSync|fs.open(`（注释不算）。
- 场景 `00-static-audit`：asar 内 `app/main/server.js` 与开发树/源仓逐字节比对。
- 可复用探针：`probe-serve-ab.cjs`（HTTP A/B）、`probe-asar-io.cjs`（读法微基准）。

### 3.2 【真功能缺陷】右键菜单「剪切」只复制不删正文

**证据**（`probe-cut2.cjs`，打包产物）：

```
剪切前: selectionText=第一段要剪切的文字甲, collapsed=false, occurrences=1
剪切后: occurrences=1（文字还在）, 剪贴板里确实有这段文字
cmdLog: [{command:'delete',result:false}, {command:'cut',result:true,atCall:'…文字甲',collapsedAtCall:false}]
对照：同一选区按 Ctrl+X → occurrences 1 → 0（真的删掉）
```

**根因**：Electron/Blink 的 `document.execCommand('cut')` 会返回 true、也写剪贴板，**但不删正文**；
而 `cutSelection()` 原来是 `if(ok)return true;` 直接放行。

**修复**（`extension-src/render/js/media-tools.js`）：以"选区是否塌掉"为准；还在就用
`Range.deleteContents()` 自己删，并先 `execCommand('copy')` 兜一次剪贴板（`cut` 已写过时幂等）。
选区不在编辑面内时保留原 cut 事件回退。

**判据**（场景 73 钉住）：粘贴后**出现 1 次** → 剪切后**0 次** → Ctrl+Z 后**1 次**（数出现次数，不是"包不包含"）。

  没有证人直接判失败；场景清单固定，少跑一个不算通过（`--only` 只用于排查）。

```js
function tableBlock(text, anchor = '甲') {
  const lines = String(text).split('\n');
  const at = lines.findIndex(line => line.trim().startsWith('|') && line.includes(anchor));
  if (at < 0) return [];
  let start = at, end = at;
  while (start > 0 && lines[start - 1].trim().startsWith('|')) start--;
  while (end + 1 < lines.length && lines[end + 1].trim().startsWith('|')) end++;
  return lines.slice(start, end + 1);
}

async function saveAndWait(session, file, { timeout = 6000, interval = 120 } = {}) {
  const before = fs.existsSync(file) ? fs.readFileSync(file, 'utf8') : null;
  const started = Date.now();
  await session.chord('s', 'KeyS', 83);
  let chordTook = false;
  while (Date.now() - started < timeout) {
    await harness.sleep(interval);
    const now = fs.readFileSync(file, 'utf8');
    if (now !== before) { chordTook = true; break; }
  }
  if (!chordTook) {
    // 键盘通道没送到就退到主进程的同一条保存命令（用户菜单里的"保存"），
    // 并且如实记账：这一步不是按键路径。
    await session.jsSoft(`hostApi.invoke('save')`);
    const deadline = Date.now() + timeout;
    while (Date.now() < deadline) {
      await harness.sleep(interval);
      if (fs.readFileSync(file, 'utf8') !== before) break;
    }
  }
  return { before, after: fs.readFileSync(file, 'utf8'), chordTook, waitedMs: Date.now() - started };
}
```

```js
  const length = Math.max(a.length, b.length);

      return { at: index, expected: JSON.stringify(a.slice(Math.max(0, index - 40), index + 40)), actual: JSON.stringify(b.slice(Math.max(0, index - 40), index + 40)) };
```

```js
/** 第一处字节差异（用于把"不一致"变成可读的证据，而不是只报 false）。 */
function firstDiff(a, b) {
  const length = Math.max(a.length, b.length);
  for (let index = 0; index < length; index++) {
    if (a[index] !== b[index]) {
      return { at: index, expected: JSON.stringify(a.slice(Math.max(0, index - 30), index + 30)), actual: JSON.stringify(b.slice(Math.max(0, index - 30), index + 30)) };
    }
  }
  return { at: -1 };
}
```

```js
 *
```

```js
 *
```

```js
 *      → 说明你的代码里有 open/createReadStream 在读 asar，是 bug 不是"asar 慢"。

function window_read(fd, size) {
  const buffer = Buffer.allocUnsafe(size);
  let offset = 0;
  while (offset < size) offset += fs.readSync(fd, buffer, offset, size - offset, offset);
```

### 5.8 probe-serve-ab.cjs（服务方式 A/B） `scripts/acceptance/probe-serve-ab.cjs`

```js
#!/usr/bin/env node
/** 静态资源服务方式 A/B：同一个 asar 文件，`createReadStream` 与 `readFile` 各要多久。
 *
 *  这是 2.0.18 定位冷启动 1.1s 时的决定性实验。两种模式必须**各起一个全新进程**跑，
 *  否则第二次会命中 Electron 的"抄出去"缓存，把差距抹平（第一次实验就踩过）。
 *
 *  用法：
 *    ELECTRON_RUN_AS_NODE=1 node_modules/electron/dist/electron.exe \
 *      scripts/acceptance/probe-serve-ab.cjs stream|read [--asar=...] [--file=app/renderer/...]
 *
 *  2026-09-11 实测（lute.min.js 3.8MB + index.min.js 290KB）：
 *    stream  lute#1 1161.4ms | lute#2 9.9ms | index.min.js 78.5ms
 *    read    lute#1   13.3ms | lute#2 5.5ms | index.min.js  1.0ms
 */
'use strict';
const http = require('node:http');
const fs = require('node:fs');
const path = require('node:path');

const mode = process.argv[2] || 'stream';
if (!['stream', 'read'].includes(mode)) {
  console.error('用法：probe-serve-ab.cjs stream|read [--asar=...] [--file=...]');
  process.exit(1);
}
const argOf = (name, fallback) => {
  const hit = process.argv.find(value => value.startsWith('--' + name + '='));
  return hit ? hit.slice(name.length + 3) : fallback;
};

const secondary = path.join(asar, 'app/renderer/cdn/vditor/dist/index.min.js');

const server = http.createServer((req, res) => {
  const file = req.url === '/secondary' ? secondary : target;
  const headers = { 'Content-Type': 'text/javascript; charset=utf-8' };
  // 与生产一致的头部（关键点：asm 内文件不能用 open 系路径）
  if (mode === 'stream') {
    fs.stat(file, (error, stat) => {
      if (error) { res.writeHead(404); res.end(); return; }
      res.writeHead(200, {...headers, 'Content-Length': stat.size});
      fs.createReadStream(file).on('error', () => res.destroy()).pipe(res);
    });
  } else {
    fs.stat(file, (error, stat) => {
      if (error) { res.writeHead(404); res.end(); return; }
      fs.readFile(file, (readError, data) => {
        if (readError) { res.writeHead(500); res.end(); return; }
        res.writeHead(200, {...headers, 'Content-Length': data.length});
        res.end(data);
      });
    });
  }
});

server.listen(0, '127.0.0.1', async () => {
  const port = server.address().port;
  const get = requestPath => new Promise((resolve, reject) => {
    const started = process.hrtime.bigint();
    http.get({host: '127.0.0.1', port, path: requestPath}, response => {
      let bytes = 0;
      response.on('data', chunk => { bytes += chunk.length; });
      response.on('end', () => resolve({ms: Number(process.hrtime.bigint() - started) / 1e6, bytes}));
    }).on('error', reject);

  } catch (error) {
    console.error('请求失败：', error.message);
    process.exitCode = 1;
  } finally {
    server.close(() => process.exit(process.exitCode || 0));
  }
});
```

**`app/main/server.js` — `sendFile`（本轮性能修复核心）**

```js
  // 打包后 rendererRoot 落在 app.asar 里，而 **Electron 对归档内路径的 open() 会把
  // 整个文件先抄到临时目录**（实测同一份 3.8MB 的 lute.min.js：createReadStream 走
  // open→1161ms，readFile 走归档区间读→13ms，约 4MB/s 对 300MB/s）。这条路径正好在
  // 冷启动的关键链上——编辑器页要等 lute 才能解析文档，用户看到的就是"装完版比开发版
  // 慢 1.2 秒"。readFile 把整个文件读进内存再一次性写回，代价可忽略（最大也就几 MB），
  // 换来每次启动少 1.1s。**不要再改回 createReadStream。**
  const sendFile = (res, file, head = false) => {
    fs.stat(file, (err, st) => {
      if (err || !st.isFile()) return send404(res, file);
      fs.readFile(file, (error, data) => {
        if (error) { res.writeHead(500, { 'Content-Type': 'text/plain; charset=utf-8' }); res.end('server error'); return; }
        res.writeHead(200, {
          'Content-Type': mimeOf(file),
          'Content-Length': data.length,
          'Cache-Control': 'no-store',
        });
        res.end(head ? undefined : data);
      });
    });
  };
```

## 6. 经验教训（SKILL 规则 39–45 全文）

> 这七条已写入 `.agents/skills/marcopilot-md-editor/SKILL.md`，这里再留一份，方便单文件复用。

**39.【本轮最大一条】asar 内的静态文件绝不能用 `open`/`createReadStream` 服务**
Electron 对归档内路径的 `open()` 会把**整个文件先抄到临时目录**（耗时与大小成正比、约 4MB/s、只有第一次付）。
实测同一份 3.8MB 的 `lute.min.js`：`openSync` 868ms、`promises.open` 0.4ms、`readFileSync` 1.1ms；
生产 `startServer` 的 HTTP A/B：`createReadStream` **1161ms** vs `readFile`+`res.end` **13ms**。
它正好在冷启动关键链上，于是"安装版比开发版慢 1.2 秒"的真凶就是它——**不是** asar 读得慢，
也不是需要"预热编辑器宿主"。修法：`sendFile` 用 `fs.readFile` 整读回写。效果：页面内 1218ms → 214ms。
防线：单测禁止 `createReadStream|openSync|fs.open(`；审计比对 asar 内 server.js 字节。
**推广**：任何"让浏览器/外部进程去读"的产物内文件，先问一句"这个路径在 asar 里吗"。

**40. 剪贴板类动作的验收必须轮询证人，不能点完就读**
写剪贴板走 PowerShell（首次 `Add-Type` 要 1–2s），点完立刻读会读到**用户原来的内容**——"复制表格失败"
的第一版就是这么假失败的。用 `readClipboardUntil(dir, predicate)` 等目标内容出现（`waitedMs` 进证人）。
凡"产品→外部进程→外部状态"的链路，都按"最终状态出现"来等，而不是固定 sleep。

**41. 右键菜单类验收的两个坑**
① **右键必须落在选区内部**：落外面 Chromium 先把光标挪过去、选区塌掉，复制/剪切就变成对空选区的操作
（会给产品扣一顶"不工作"的假帽子）。用 `selectionPoint`（选区中心的顶层页坐标）右键。
② **表格行列增删别只数行数**：删掉的可能是另一行。改成"插一行 → 删掉**刚插的那一行**（空行/空列是天然锚点）
→ 磁盘字节必须回到插之前"。锚点格要用**内容**定位（如"含公式源码"），不要用索引（索引会随插行漂移）。

**42. 含表格的文档保存时表格会被重排，所以"字节保真"必须在没有表格的素材上量**
Lute 在 IR→Markdown 时按列宽对齐：`| 项 | 值 |` → `| 项 | 值             |`、`| --- | --- |` → `| -- | -------------- |`。
**实测重新打开仍能正确解析为表格（行/列/内容一字不差），是对齐归一不是数据损坏。**
口径：`math-only.md` 上做严格字节往返保真；含表格素材验"表格语义往返不变"。

**43. `document.execCommand('cut')` 的返回值不可信，要以"选区是否塌掉"为准**
Electron 实测会**返回 true、也写了剪贴板，但不删正文**——右键剪切看起来"没反应"，再粘贴就是重复内容
（同一选区 Ctrl+X 正常）。判据用**出现次数**（粘贴后 1 次 → 剪切后 0 次 → Ctrl+Z 后 1 次），不是"包不包含"。

**44. 构建链路：GitHub 不可达时 electron-builder 会挂在 electron 分发下载上**
连续三次 `Timeout awaiting 'request' for 600000ms`（`connect ETIMEDOUT 20.205.243.166:443`），
`ELECTRON_BUILDER_BINARIES_MIRROR` **对 electron 本体不生效**（只管 builder-binaries）。
修法：`--config.electronDist=node_modules/electron/dist`。winCodeSign 需要时从
`https://registry.npmmirror.com/-/binary/electron-builder-binaries/winCodeSign-2.6.0/winCodeSign-2.6.0.7z`
预先放进 `%LOCALAPPDATA%\electron-builder\Cache\winCodeSign-2.6.0\`。

**45. "没收益就回退"，并把否掉的证据留在代码注释里**
本轮试过"外壳先上屏、两帧后再装 iframe"（假设 iframe 抢主线程让窗口晚 220ms）。安装版实测
窗口可见 496/497/481ms 与改前 513/488/479 **没有差别**，而内容进 DOM 被推迟约 60ms → 整段回退，
三行实测数字写进 `shell.js` 注释防重做。同轮还被否掉：预置 lute/katex 脚本（asar 修复后取回只剩
10–17ms）、warmup 片预算 8→4ms（无新证据）。

（`/api/jinxi/markpilot`、`/latest`、页面均 200；把线上 VSIX 下回来算哈希与本地一致 `7e2846e9…`，
即"发布出去的就是验收过的那份"）。之前查不到只是**读取端索引延迟**，不是发布失败。

**发现的坑（重要）**：商店（Open VSX / VS Marketplace）**优先读 `vsix-meta/extension.vsixmanifest`**，
而不是 `extension/package.json`。这份清单里的 `DisplayName / Description / Tags / Categories` 从没被同步过，
于是：
- 我把 package.json 的 keywords 加到 22 个 → **商店里查到的 Tags 仍是 4 个弱词**（`md,markpilot,markdown,typora`）；
- 商店页描述仍是旧的中文一句话、分类仍是 `Programming Languages`。
**这条会静默削弱整轮"可被搜索"的工作**，如果不是把线上 VSIX 下回来逐字段对，根本发现不了。

**修法**：
1. `pack.py` 的 `sync_manifest()` 现在同步 5 项：Identity 的 `Version`/`Publisher` + `DisplayName`/`Description`/`Tags`/`Categories`
   （从 package.json 生成，含 XML 转义；找不到元素会补插）；
2. `verify-vsix-chain.cjs` 加了**永久闸门**：清单的 Publisher / DisplayName / Description / Tags / Categories
   必须与 package.json 一致，不一致直接断言失败。

**暂时无法刷新已发布版本的元数据**：`ovsx unpublish` 报
`The registry at https://open-vsx.org runs version v1.1.2, but deleting extensions requires version 1.2.0 or later`
→ 服务端还不支持删除；重新发布同版本则报 `already published`（版本不可变）。
**结论：元数据修正要等下一个版本（2.0.19）随包带出去**——因为本仓铁律要求 EXE 与 VSIX 同版本，
届时需一并做：改版本 → 重打包 EXE/VSIX → 重装 → 全套验收 → 刷新 GitHub → 更新 winget（新版本号需新 PR）。
本次先不动，避免为一段商店文案付出一次完整发版。

### 13.8 微软市场：本账号的付费卡点与免费替代

用户实测：新建 Azure DevOps 组织会被引到 Azure 门户并要求**绑定订阅（付费）**，于是经典 PAT 路径被卡住。

## 14. 截图高清重制（2026-09-11 深夜，用户反馈"太糊、分辨率太低"）

**反馈原文**："本次截图，重新再截上一回，截的太糊了，分辨率太低了。我要高清的"

**病灶**：`docs/screenshots/` 里 6 张是由 `shots-probability.cjs` / `shots-mapping.cjs` 拍的，
`deviceScaleFactor` 写死 **1**，CSS 版心宽 780 → 出图就是 **780×900 / 780×760 / 780×560**。
而同一目录下 `hero-en.png`(1770×1200)、`ui-light-cjk.png`(1770×1200)、`ai-completion-models.png`(1749×1106)
本来就是高清——所以 README 里高清与低清混着，一放大就露馅。

**做法**：构图、版心宽度、换行逻辑一个字都不动，只把光栅密度提到 **3×**。
两个拍照脚本各加一个 `--scale`（默认 1，保持旧行为）：

```js
const SCALE = Number(argOf('scale', '1'));
await session.send('Emulation.setDeviceMetricsOverride', {width: WIDTH, height, deviceScaleFactor: SCALE, mobile: false});
```

```bash
node scripts/shots-probability.cjs --scale=3   # prob-hero / prob-body / prob-toolbar-70 / prob-menu-70
node scripts/shots-mapping.cjs    --scale=3    # prob-map-omega / prob-map-n
```

**"只变清晰、不变内容"的机器证明**（`scripts/acceptance/shot-diff.ps1`）：
把新高清图缩回旧图尺寸后逐像素比，再做一次 1/10 粗结构比（换行点挪一个字、抗锯齿换算法
这类光栅化差异在这一档会消失，只有真改了版式才会留下差异）：

| 仓库路径 | 旧 | 新 | 逐像素平均差 | **粗结构平均差** | 粗结构>32 占比 |
| --- | --- | --- | --- | --- | --- |
| hero-light-serif | 780×900 | 2340×2700 | 5.25 | 2.23 | 0.47% |
| body-dense-wrapping | 780×900 | 2340×2700 | 10.52 | 5.04 | 1.72% |
| toolbar-translucent-70 | 780×560 | 2340×1680 | 3.94 | 1.75 | 0.21% |
| menu-translucent-70 | 780×900 | 2340×2700 | 5.07 | 2.17 | 0.44% |
| math-map-omega | 780×760 | 2340×2280 | 4.46 | 1.88 | 0.27% |
| math-map-subscript | 780×760 | 2340×2280 | 5.57 | 2.34 | 0.81% |

六张长宽比全部一致，粗结构差 0.21%–1.72%；肉眼核对：滚动位置、那张空的三列表格、
状态栏「字数5,899 字符13,857 行319 约15分钟」全部同值。
**如实披露**：1×→3× 会让字形度量精度变化，`body-dense-wrapping` 里有 2–3 处换行点挪了一个字，
这是光栅化差异而不是内容差异（粗结构差 1.72% 就来自那几行的整体位移）。

**上架方式**：文件名与路径**一个都没改**，所以 GitHub README、VSIX 的商店页 README
（两者引用的都是 `raw.githubusercontent.com/.../docs/screenshots/<同名>.png`）自动吃到高清版，
**无需改任何 README 文字、无需重发 VSIX、无需动版本号**（也就绕开了铁律 11 的整链发版）。

**核验**：
- 逐张从仓库 contents API 取回，sha256 与本地高清文件**逐字节一致** ✓
- raw CDN 已提供新文件（`hero-light-serif` Content-Length 606736 / `body-dense-wrapping` 1128780，
  `Cache-Control: max-age=300`）→ 旧图最多再活 5 分钟
- 受保护素材：拍摄脚本自带"先复制、拍完删副本、核对原件 md5"，
  本轮两次拍摄前后原件 md5 均为 `14373f2e9a7c0f498790ebc735e121b7` ✓

## 15. 对 Typora 的同口径性能对照（2026-09-10，用户提问"目前的性能是否比 Typora 强了？"）

用户中途把 Typora 从 1.14.9 更新到 **1.14.10**（更新弹窗打断了第一轮测量），之后全部重测。
完整报告见 **`docs/PERF-VS-TYPORA-20260910.md`**，这里只留结论与经验。

**结论（分项，不是一句话）**：

| 项目 | 结论 |
| --- | --- |
| 打开小文档 1.7 KB | MarkPilot 快 ~195 ms（正文进 DOM 514 对 709） |
| 打开中文档 67 KB | MarkPilot 快 ~140 ms（612 对 753） |
| 打开大文档 240 KB | **打平**（913 对 895，差 18 ms 在噪声内） |
| 窗口出现 | MarkPilot 更快（289 对 332；像素尺子 175 对 318） |
| 大文档文末点公式 → 展开进 LaTeX 源编辑 | **MarkPilot 24 ms 对 Typora 156 ms（6.5 倍）** |

**两把尺子互为独立见证，排序完全一致**：
1. 屏幕像素尺子（`acceptance/win-peer-witness.ps1`，`PrintWindow` 渲染，量"用户真的看见了什么"）——24/24 样本通过闸门；
2. CDP 尺子（`probe-open-cdp.cjs`，走 DevTools 协议，与遮挡/前台/焦点无关）——18/18 有效。

**本轮最大的一次路线修正：Typora 的 CDP 只能走管道。**
`--remote-debugging-port` 它收下但**不监听**（`DevToolsActivePort` 不出现、端口不开）；`--remote-debugging-pipe` 正常。
突破口来自 Node 侧 `stdio: ['ignore','ignore','ignore','pipe','pipe']` 拿到 fd3/fd4。
在此之前，因为用户同时在使用电脑（另一个窗口长期居最前层），屏幕抓图被遮挡搞废了三轮：
抓到的是遮挡物窗口、`PrintWindow` 返回纯色（连续 3249 帧色量 0）、
"检测到纯色就激活并提到最前"的抢救对"本身也是 topmost 且活动的窗口"无效
（`SetWindowPos(HWND_TOPMOST)` 对已 topmost 的窗口是空操作）。

**注入输入的两个真坑（都写进 SKILL 了）**：
1. 窗口成为前台 ≠ 编辑器拿到键盘焦点。MarkPilot 的编辑器在 iframe 里，实测 `document.hasFocus()===false`、`activeElement===BODY`，
   此时 `Ctrl+End` 送到外壳、文档一动不动（点击前的抓图还停在文档开头，这才暴露了它）。
   先在正文里点一下建立焦点，`Ctrl+End` 立刻生效（scrollTop 0 → 75085）。激活后还要留 ~250 ms 再发输入。
2. `SendInput` 的返回值必须看：它是真正塞进队列的事件数。本轮实测都是正常插入（chord 4/4、click 3/3），
   所以问题不在"没送到"，而在"送到了没人理"——第 1 条才是真因。**任何输入注入之前必须确认前台属于被测应用，拿不到就整段跳过。**

**本轮新增的验收项与素材**：
- `fixtures.largeTailMath()`：240 KB / 1843 块 / 2320 个行内公式，**公式块刻意放在文末之前**——
  这样 `Ctrl+End` 才能成为两个应用共用的确定性锚点（滚轮格数在两边走的距离不同，不可比）。
- 「点公式展开」的判据写死成表达式：MarkPilot `--expand` + 源码 `code` 占位可见；
  Typora `md-expand` + `script[type="math/tex"]` 从 `display:none` 变可见（实测点击确实变成 `inline`，选区落在源码上）。
- 两个新脚本：`scripts/peer-cdp.cjs`（CDP over pipe 客户端）、`scripts/probe-formula-click.cjs`（对照驱动）。

**过程中被推翻的三个中间结论**（留档避免重犯）：
1. 一度以为"点击/按键没送到应用"——实测 `SendInput` 全部插入成功，真因是焦点。
2. 一度以为 Typora 没打开我的素材（中/大档像素色量完全相同）——其实是抓到了遮挡物窗口。
3. 一度以为 MarkPilot 打开大文档只要 228 ms——那是"空白编辑器 + 上一帧残留像素"被门限误判成正文；
   修法是给"安静"加一个**绝对色量下限**（空白页也是安静的），正文判据改为"达到本轮最大色量的 25% 且不低于下限"。

Bug 修复区仍在文末，未被扰动。

**本地报告补全**：`docs/PERF-VS-TYPORA-20260910.md` 增加"零、去工程腔版"与"九、逐轮原始读数"
（每个样本的原始值、台账文件名、中位数与散布的关系）。原始值也如实暴露了抖动，
例如 MarkPilot 中文档"正文进 DOM"三轮是 612 / **1721** / 611——中位数取 612；
点公式展开 MarkPilot 16–27 ms、Typora 145–161 ms，两边散布比两者差距小一个量级，所以差距不是抖动造成的。

**SKILL 规则 50–52（差点翻车的三件事 + 两条方法论）**：
1. **最严重**：注入的输入打进了用户正在用的另一个应用（缺"每次发送前复核前台"这道闸门）。红线：任何输入注入**每一次发送前**都要复核前台归属，不成立就整段跳过；能不用系统级注入就优先用 CDP 的 `Input.dispatch*`。
2. 抓图抓到遮挡物，且因"两个素材读数完全相同"差点得出"对照应用没打开我的素材"的错误结论。像素证据必须配内容同一性证人；遇到反直觉的相同读数，先怀疑测量。
3. 把"空白页"判成"文档已就绪"，差点写出"打开大文档只要 228 ms"的假数字。所有"安静"判据必须带内容下限。
4. 方法论一：怀疑"产品没反应"之前，先证明"动作到底有没有发生"（`SendInput` 返回值 / `GetCursorPos` / 应用自报状态），否则会把"我没点到"写成"产品有 bug"。
5. 方法论二：对照类测量必须两把独立尺子；**口径依赖的指标（如"画面彻底安静"）只在报告里并列写明，不进结论也不进宣传**。
