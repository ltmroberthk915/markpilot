## 二、多核：10 扇窗完全并行，16 扇开始争用

标定方法：让**每一扇窗同时**做同一份纯 CPU 活（整篇 `vditor.setValue(getValue())` = 全量重解析 +
重渲染），先测单扇窗耗时，再测 N 扇窗同时做的总耗时。

| 窗口数 | 单窗耗时 | N 扇同时总耗时 | 比值 | 含义 |
| --- | --- | --- | --- | --- |
| 10 | 5003ms | 4756ms | **0.95×** | 完全并行（若串行会是 ~10×） |
| 16 | 5486ms | 7200ms | **1.31×** | 仍是并行，但出现约 31% 的互相挤压 |

- 压测峰值 CPU：10 窗口 **61%**、16 窗口 **77.2%**（`app.getAppMetrics()` 进程组汇总）
- 16 窗口那次的逐窗耗时很有意思：10 扇各 ~5.7〜6.6s、6 扇各 ~2.8s —— 套件分批发起，
  后半批是在前半批已占满 CPU 的情况下跑的，所以 1.31× 这个数是"最坏情况"的诚实读数
- 结论：**"重文档并行窗口数"大致在 10〜16 之间触顶**，约等于核数的一半到四分之三。
  这是硬件边界（每个正在重排的渲染进程要占一个核以上），不是实现缺陷

## 五、跨窗口剪贴板的开销（同一轮的另一组证据）

- 图片跨窗口走的是系统剪贴板 `CF_HDROP`，实测一次复制 → 目标窗口落盘为内嵌图，**字节与源图一致**
  （`windows-clipboard` 套件 15 步 PASS；PowerShell 直读 CF_HDROP 取证）

- 这一条没有做吞吐标定（不是什么重活），只做了正确性与字节一致性

## 六、没测过的（如实列出，别当默认成立）

1. **> 16 窗口**：套件默认上限 10，`STRESS_WINDOWS` 可调；没测过 20/32 扇
2. **异构文档**：全部是 700KB 同构文档；没测"1 个 10MB + 9 个 1KB"这类混合
3. **长期稳定性**：没有小时级的 RSS 曲线（只测了打开→压测→关闭这一条短链）
4. **磁盘 IO 竞争**：多窗口开在同一目录、同时保存大文件时的相互影响没有标定
5. **空闲 CPU 是 Electron 自报的进程组平滑值**（`app.getAppMetrics()`），不是 perfmon 逐核采样，
   所以它适合看"有没有异常增长"，不适合当作绝对占用率引用
6. **首次冷启动**：本次记录里的首窗 2084ms 是"套件启动后的第一个窗口"；整应用冷启动
   （含 Vditor 初始化与字体/补全预热）另有 4.4s 的记录，两者不是一回事

## 七、还能改进的方向（按"收益 ÷ 风险"排序）

下面每条都写了**预期收益、代价、怎么验证**。标了"待测"的是我还没有测量、只是从代码结构推断的。

### 7.1 每窗口内存体量（现在 ~453〜479MB/窗）——最值得做的一条

拆开看，每窗口的内存主要是这几块（**待分段测量**）：渲染层资源（`app/renderer` 22MB 的
Vditor/KaTeX/主题/补全/字体，每个窗口各加载一份）、Vditor 的文档模型与 IR DOM、
内嵌图片在内存里的 data URI 副本、每窗口的导出器与补全会话。

可行做法与预期：

| 做法 | 预期收益 | 代价 / 风险 | 怎么验证 |
| --- | --- | --- | --- |
| 重子系统按需加载（补全、导出、KaTeX 字体子集、非当前主题 CSS 延后） | 每窗口 **40〜120MB**（待测） | 要动的是已经稳定、被 20 个套件盯着的启动路径；加载时机错了会表现为"功能偶尔不响应" | `windows-scale` 的 rssMB 列 + `windows=1 openMs` 不得退化（基线 2.2s/4.4s 冷启）；`completion` / `export*` / `math-*` 套件回归 |
| 内嵌图片不再在内存里留 data URI 副本（只留磁盘路径，按需读） | 多图大文档每窗口 **几十 MB**（依赖图片总量） | 保存时要重新读盘拼回 data URI，保存路径变慢；断链要能优雅降级 | 含 20 张大图（每张 2MB）的文档：每窗口 RSS + 保存耗时对比 |
| 给渲染进程设 `--max-old-space-size`（例如 512） | RSS 下降，GC 更早介入 | 用 CPU 换内存；并发重排的 0.95× 可能变差 | 同一轮 `windows-scale`：rssMB 与 parallelScaling ratio 一起看，ratio 变差就回退 |

**不建议**的方向：让多个窗口共享同一个渲染进程（Electron 早期的 `affinity`）。它能省内存，
但已被新版 Electron 移除，而且会同时牺牲崩溃隔离与上面那条 0.95× 的并行——与"一个文件一个
独立窗口"的目标相悖。

### 7.2 16 扇之后的争用（1.31×）——把上限守住，别硬扛

- 默认上限保持 10 是对的（10 扇实测 0.95×）。若将来要放开，正确做法不是优化内核，
  而是**在重文档超过 N 扇时做降级**：被遮挡的后台窗口暂停 KaTeX/Mermaid 全量重排、
  暂停滚动锚点采样与自动收纳的几何测量，等它被激活再补算。
- 预期：16 扇的 ratio 从 1.31× 回到 1.2× 以内（待测）
- 代价：后台窗口的"切回来第一眼"会有一次补算延迟（本来是隐藏文档，用户看不到）
- 验证：`STRESS_WINDOWS=16` 重跑对比 ratio 与 `stressedEditMs`

### 7.3 冷启动 4.4s → 热开 2.1s 的那 2s 差

首窗慢在 Vditor 初始化、KaTeX 字体与补全预热。可行做法：先渲染出空白编辑器（可交互）再分帧挂
补全/KaTeX/主题；或把补全预热挪到 `requestIdleCallback`。
预期首窗 **−1〜1.5s**（待测）；代价是"打开后一两秒内补全还不灵"。
验证：`windows-scale` 的 `windows=1 openMs` 与 `perf-runner` 冷开基线，同时确认
`completion` 套件的自动建议断言仍然通过。

### 7.4 打开一扇窗的 2.2s 里，主进程与渲染各占多少——先量再优化

目前只有端到端的 2.2s，没有分段。可加的分段计时：主进程读盘 → `images.mask`（含图片写盘
`flush`）→ 建窗 → `doc-load` 推送 → 渲染层 Lute 首次解析 → 首帧。
**先把这几段量出来**再决定动哪里（如果 `mask` 的图片写盘占比高，可以让它与建窗并行）。
现在不做任何猜测性改动。

### 7.5 空闲 CPU（10〜16 扇窗时 4〜5%）

主因是每个渲染进程都有常驻定时器/监听（数学调度、输入防抖、`ResizeObserver`、自动收纳的
`mousemove`）。注意我们现在**刻意关掉了 `backgroundThrottling`**（为了不被系统降频、
保证压力测试里测到真实性能）——这是个取舍。折中做法：只对"被遮挡的窗口"降频，
可见窗口不受影响。预期空闲 CPU 减半（待测）；验证：空闲 CPU 列 + 被遮挡窗口切回后的
首帧延迟。

### 7.6 需要更长时间才能回答的问题

- 小时级 RSS 曲线：判断有没有"缓慢爬升"型的泄漏（本记录只覆盖分钟级）
- 同一目录多窗口并发保存：`fs.watch` 共享 hub 已经把 watcher 数压到 1，但磁盘写竞争没量过
- 混合尺寸文档的抢占行为：大文档重排会不会把同机小窗口的交互拖到不可用

## 八、一句话结论

**在"该由架构决定"的几件事上已经到位**：一个窗口一个渲染进程（1:1）、10 扇窗并发做同一份
CPU 活为单窗的 0.95×（真并行）、打开耗时对窗口数平坦（~2.2s）、关窗后内存回落到基线+一扇窗、
每窗口约 0.45〜0.48GB。剩下的都是"单窗口自身的内存体量"与"硬件核数边界"，不是多窗口机制的漏洞；
真要继续压，§7.1 那三条（按需加载 / 图片不留内存副本 / V8 堆上限）是收益最大的一档，
每一条都要用同一套数字回验，改差了就回退。
