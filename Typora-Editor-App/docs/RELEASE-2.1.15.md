## 一 ①：点行末跳过末尾那个逗号

### 复现（在**你的原文档**上，第 195 行那条 `$$…$$`）

把映射函数按 **1 像素网格**铺出来（`scripts/acceptance/probe-math9.cjs`，不改产品代码、只调产品函数）：

```
字形盒： «=»@75 x 571..584   «0»@76 x 589..598   «,»@77 x 598..602
y=398 行： x 587..597 → 76 (落在 `0` 之前)   x 598..885 → 77 (落在逗号之前)
```

也就是说：**行末那条 288px 宽的空白带，任意一点都停在末尾逗号之前**（这一带本来就是对的）；
真正会"跳过逗号"的是 `0` 的右半边那 4px（x=594..597）——它给出 76，看起来就是"光标跑到了要点的
字符再往前一格"。你说的"点渲染行的最后"，落点就在这附近。

### 根因

`targetOffset` 一律返回**字形起点**（外加"命令落到反斜杠之后"那一条）。所以点在一个 9px 宽的
数字格子的右半边，光标也会停在它**前面**——离落点两格之差。

### 修法（`render/js/math-source-map.js`）

- 落在字形**左半边** → 停在它之前；**右半边** → 停在它之后（`after`）。
- **公式最后一个字形**除外：点在它身上（含右半边）仍然停在它之前——这样"点行末"永远停在最后
  一个字符之前，不会跑到公式外面去。这一条正是你 ① 的判据（"正常应该出现在逗号前"）。
- 字形之间的**缝**里也认左右半边：否则缝里会退回上一格，形成"点着往右走、光标却往回跳一格"的
  非单调（这个坑是第一版修复做完之后用同一张像素网格量出来的，残余 2px 缝隙已消掉）。
- 命令（`\sum`/`\int`/`\lim`/`\frac`…）左右半边都落到反斜杠之后——与行内公式的既有语义一致，
  也是你 ② 要的行为。

## 二 ②：点 ∑/∫ 落进第一个参数

### 复现（真产物，`probe-math6.cjs`）

```
显示模式： <span class="mop op-limits" data-typora-source-start="0">      ← 映射挂在这一层
             └ <span class="mop op-symbol large-op">∑</span>              ← 字形自己没有映射
点 ∑ 字形正中（iframe 397,240）→ 映射值 7 → 光标落在 \sum_{i|=1}
```

对比行内公式：`$\sum_{i=1}^{n} a_i$` 的 ∑ **有自己的映射**（`∑@0-4`），点它是 `\|sum`（offset 1）
——这就是你说的"行内是对的"。

### 根因与修法

旧实现三级判定里的第三级是"离落点最近的**映射字形**"；∑ 自己没映射，最近就选中了下标里的 `=`。
现在在第二级与第三级之间加一条：落点压在**自己没有映射、但这一层确实画着字**的元素上时，用它
**外层映射元素**的位置。命令一律进到反斜杠之后，于是点 ∑ → `\|sum`、点 ∫ → `\|int`。

> 为什么"这一层确实画着字"（无子元素、文本非空）这个条件是必需的：KaTeX 的 vlist/strut 空壳会
> 横向盖到相邻字形上（你的公式在 y=398 处 x=410 那 1px 就是），拿它当依据会把光标退回上一格。
> 这是加了这条判定之后、用同一张像素网格复查出来的。

## 三 ③：提示栏避不开预渲染框

`render/js/completion.js` 的 `position()` 原本有两条规则（不压正在编辑的那一行、不压鼠标）。
现在加第三条：**不盖住展开态的预渲染框**（`.vditor-ir__node--expand > .vditor-ir__preview`），
排序权重排在"不压鼠标"之后、"能显示更多条目"之前——即**宁可面板矮一点，也要让你看得见
这条公式渲染成什么样**。

场景 86 的证人数（真 DOM 量测）：面板 `top 8..173`、预渲染框 `top 201..232`、源码行 `top 177..203`，
面板与预渲染框**横向本来就重叠**（自证非空），而纵向不重叠。

## 四 ④：删除图片要按两次 Ctrl+Z

### 复现（`probe-img4.cjs`，真产物，你那张 1167×1264 的截图）

把 `undo.addToUndoStack` 包起来逐次记录（一次"点选图片 + Delete"）：

```
t=4289 栈 1→2 **推入**（beginDocumentEdit：光标移动被算成一次差异）
t=4297 栈 2→3 **推入**（commitImageEdit：真正的删除补丁）
```

一次用户动作推了**两条**历史，第一条的 markdown 与上一条完全相同——按 Ctrl+Z 撞上它时"什么都
不发生"，看起来就是要按两次。

### 根因

Vditor 的历史快照是**带光标位置**的（`addToUndoStack` 内部先 `addCaret`），所以"点选图片把光标
搬到图片所在块"这种**纯光标移动**也算一次差异。我们在这两个位置（`beginDocumentEdit` 与
`commitImageEdit`）无条件补历史点，就把它固化成了"一条什么也不发生的撤销"。

### 修法（`render/js/media-tools.js`）

新增 `pushHistoryIfChanged()`：**只有 markdown 真的变了才补历史点**（判据与 `typora-patches.js`
的 `flush` 完全一致：拿历史快照换算出的 markdown 和当前 markdown 比）。两处补历史都换成它。

修后：删除只推 1 条（栈 1→2），**一次 Ctrl+Z 图片就回来**，撤销栈也回到删除前的长度（不留死历史）。
这条修复对所有走 `beginDocumentEdit` 的操作（剪切/粘贴/表格/缩放等）都生效。

## 五 ⑤：删除"顶边已经滚出上沿"的图片

**先回答你的"好不好实现"：好实现，已经做了。**

- **条件**：图片盒的 `top` 在可视区上沿之上（只剩它下半截和下方文字看得见）才走新规则；
  图片整体在视口里时**保持原行为**（下方文字上移一格），就是你说的镜像情况。
- **补偿多少**：按**内容总高的变化量**（`scrollHeight` 差）算，而不是按图片盒或那一块的几何——
  实测图片盒 881px、图片所在块 `getBoundingClientRect()` 906px、而内容总高实际少了 **920px**
  （块级图片那一块还带着外边距）；按几何量算会差 39px，下方文字仍然跳一格。
- 效果：删除后下方文字**原地不动**（场景 87 实测三段位移 ≤ 3px），滚动位置整体上移 920px，
  上方内容下移进视野。

## 八 请你手验这 5 处

1. **①** 一条 `$$…$$` 公式渲染好后，点它**行末**（末尾逗号附近、以及逗号右边那片空白）→ 光标应停在
   末尾逗号之前；点末尾字符的**左半边**应停在它前面、**右半边**停在它后面。
2. **②** 块公式开头是 `\sum`/`\int`/`\lim` 的，点那个大符号 → 光标应插到 `\` 和后面那个字母之间
   （与同类**行内**公式的手感一致）。
3. **③** 在公式里敲 `\` 让提示栏弹出来 → 提示栏不该盖住那条公式的渲染结果。
4. **④** 点选一张图片、Delete，然后**一次** Ctrl+Z → 图片应当立刻回来（不再需要第二次）。
5. **⑤** 把一张比窗口还高的图片滚到"只剩下半截在屏幕上"（上方内容已滚出上沿），删掉它 →
