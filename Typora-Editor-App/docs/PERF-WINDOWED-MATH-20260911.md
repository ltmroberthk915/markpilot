# 视口窗口化公式渲染 + 队列吞吐（2.0.13，2026-09-11）

> 目标（用户本轮指认的三项）：① 常驻内存（渲染进程 ~1GB）② 稳态输入 77–113ms ③ 打开到"全部公式
> 完成" 26s / 阅读模式首次准备 98s。本轮把 ①②③ 的量级都改了，并给出了同机同素材、同方法的
> Typora 对照；同时如实记录两处变差与本轮**没有**解决的首屏问题。

## 1. 归因：钱花在哪（先测，再改）

测量脚本 `scripts/math-perf-probe.cjs`（新增，可复跑），素材 `.testws/教材合订本.md`
（531KB / 30.4 万字符 / 2,576 顶层块 / 5,634 个公式），口径：交错 A/B、每次读数前 `gc()`、
内存取渲染进程 `privateBytes`（`app.getAppMetrics()`），另单列整棵进程树。

| 归因问题 | 结论 | 证据 |
|---|---|---|
| 1GB 里有多少是公式？ | **热加载对照：有公式 1,131MB / 无公式 591MB ⇒ 约 540MB 是 KaTeX 树** | `math-perf-a5.json` vs `b5.json`（交错 4 次可复现） |
| 能否"先渲染再释放"？ | **不能**。把已渲染的 224,561 个节点全部换成源文本后，`privateBytes` 1048→1080MB **反而略升**——Chromium 分配器把池留在进程里，不还给系统 | `P1-after-placeholder-gc`（每次运行都有） |
| 打开到"全部公式完成"卡在哪？ | **调度节奏，不是 KaTeX**。215 个分片合计 CPU ≤1.1s、89 次提交 ≤0.8s，而墙钟 14.3s；KaTeX 引擎实测 0.059ms/公式（5,634 个共 0.34s）。每批 64 个公式要等一次 `requestIdleCallback`，回落 120ms 超时 ⇒ 89 批 × ~160ms | `a5.json`：`slices 215 / maxSliceMs 5.3`、`micro.htmlSourceMap 0.059` |
| 输入为什么慢？ | 输入路径成本随**整个编辑 DOM 的规模**走：DOM 272,411 节点时 426ms，DOM 48,673 节点时 27ms | `f1/f4` vs `f2/f3`（交错） |
| KaTeX 输出里有 MathML 吗？ | **没有**。`js/math-scheduler.js` 一直用 `output:"html"`；MathML 只在导出面（`office-render.mjs` / `shell/export-render.js`）单独生成 | 代码 + `micro` 微基准 |

## 2. 两个杠杆

都在 `extension-src/render/js/math-scheduler.js`（`npm run sync` 到 `app/renderer`）：

1. **队列吞吐**：主线程没有待处理的真实输入时，用 `setTimeout(0)` 串接分片，而不是等
   `requestIdleCallback`（后者会回落到 120ms 超时）；分片预算按"是否有输入待处理"在 4ms/8ms 之间
   自适应，条数 32/64；提交批次改为按时间（6ms）而非固定 64 条封顶。输入让路逻辑原样保留
   （`isInputPending` 即断、按键后 180ms 暂停、组合输入期间不工作）。
2. **视口窗口化渲染**：≥1500 顶层块的文档，只渲染"文档顶部到视口下方 2 个视口高度"这一带；**这条线
   以上的内容永不被撤走**（单向推进的 frontier）。两个性质直接来自"单向"这条规则：
   - 视口以上每个块的高度都是真实的 ⇒ `util.js` 在 `after()` 里还原的滚动偏移仍然落在同一内容上
     （frontier 会一路追到还原点）；
   - 不会有任何内容在读者眼皮底下被撤走而跳动。

   逃生开关：`localStorage.mathWindow = 'off'`（回到全量渲染）。

**读法（不要过度解读）**

- **用户"目测 Typora 出首页更快"是对的，且差距很大：1.6s vs 5.2s（约 3.2×）。** 这**不是本轮引入
  的**：两条臂的"打开解析"都是 3.7s（Vditor 的 IR 模式要等 Lute 把整篇 30.4 万字符解析完建好 IR DOM
  才可能上屏），窗口化没有改变这一步。**这是本轮暴露出的、下一个该打的目标。**
- 内存：本轮把我们**从 1.35× Typora 拉到 ≈1.04×**（1,283 → 972MB，Typora 922MB）。
- 滚动/编辑"更快、不卡"**没有得到数据支持**：同样的 24 格滚轮我们 CPU 更高（1.03 vs 0.78s，且我方
  窗口更大、每格渲染内容更多，口径未完全对齐，见 §5）；同样的 30 次按键我们 CPU 是它的 **约 5×**
  （2.2s vs 0.4s）。输入后回到静默的墙钟两侧基本相同（≈5.0s / 3.5s）。
- Typora 的口径提醒：它 5,634 个公式是在首屏出现后继续渲染完的（6.2–7.3s 才静默）；我们窗口化后
  只渲染可见带，其余按需——**"总共要渲染多少公式"这件事两边已经不是同一个工作量**，上表的 CPU
  与内存才是同尺度可比的部分。

## 5. 如实记录的变差项与未解决项

1. **首屏仍要 5.2s**（Typora 1.6s）。瓶颈是 Lute 全量 IR 解析（3.7s，改动前后一致）。要打它需要
   "边解析边上屏"或分块解析，属于架构级改动，本轮不碰。
2. **首次滚过某个区域的帧率变差**：p95 16.8→33.3ms（60→30fps）。原因是公式在接近视口时才渲染，
   渲染工作发生在滚动过程中。**同一区域第二次滚过不再有这笔成本**（那时已渲染）。这是懒渲染的
   固有代价（CodeMirror 6 的视口化也有同类代价）。若不可接受，可用 `mathWindow='off'` 换回。
3. **静止时文档总高少 4.1%**（193,934→185,983px）：视口以下的公式是源文本占位，比渲染后矮。
   它是**自校正**的——滚到哪一块，`contain-intrinsic-size: auto` 就记住那一块的真实高度；整篇滚过
   一遍后回到真实总高。视口**以上**恒为真实高度，所以不影响阅读位置的正确性（§3 回归）。
4. **稳态输入的优势只覆盖"尚未读过的区域"**：未读区域 27ms，整篇滚过一遍后回到 ≈365ms（略差于
   改动前的 281–352ms，属同量级）。根因是输入路径成本 ∝ 编辑 DOM 规模，窗口化只是让 DOM 变小；
   真正的修法是"输入重解析收窄到当前块"（2026-09-05 的 P1，仍未做）。
5. **30 次按键 CPU 是 Typora 的 5×**：同样是输入路径问题，见上。

## 6. 复跑方式

```bash
# 归因 / A/B（同一构建，单变量：mathWindow=off 即回到改前行为）
node_modules/electron/dist/electron.exe scripts/math-perf-probe.cjs --label=x --scroll=1
node_modules/electron/dist/electron.exe scripts/math-perf-probe.cjs --label=y --flags="mathWindow=off"

# 对手对照（外部同方法；两边都需要前台窗口 + 同一窗口几何 + 干净起点）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/peer-live.ps1 \
  -Exe <Typora.exe|MarkPilot.exe> -File <fixture.md> -Profile <isolated dir> -Label <name> -Work idle|scroll|type
```

`mathWindow=off` 在套件里由 `scripts/perf-runner.cjs` 按模式设置（`math-boundaries` 需要全量渲染
才能断言 5,634/5,634，其余套件跑默认=窗口化，两条路都有覆盖），也可用 `MATH_WINDOW=on|off` 覆盖。

## 7. 未修好的一项：阅读模式首次准备仍是 ~97.5s（如实记录）

`scripts/reading-mode-probe.cjs`（未接入 perf-runner，手工跑）实测：**prepare 97,551ms**，改动前
97,992ms —— **基本没动**。而它自己的分解量都很小：`parseMs 2,350.9`、`bindMs 2,362.4`、
`windowMs 235.1`、`blocks 2,576`、`mounted 19`。也就是说这 97 秒**不是渲染/解析/窗口化的吞吐**，而是
**在等一个永不成立的条件**：`reading-mode.js:254`

```js
const settled = count > 0 && stable >= 2 && !window.__typoraMathStats?.pending;
if (settled || performance.now() - started > 90000) { … }
```

它同时要求「预览面顶层块数连续两次不变」且「公式队列清空」。队列吞吐本轮已经 15.0s→2.13s，但
prepare 每次都撞到 **90s 兜底**才继续，说明 `pending` 在阅读面的那条路径上始终非零（疑似
`preview.render` 反复重建预览节点 → 节点失去 `data-math` → 重新入队，形成稳态churn；本轮未定位到
确证，需下一轮专门查）。**这是用户三项里的第三项的阅读模式一半，本轮没修完。**

同一探针还有两条断言因窗口化而过期（不是产品缺陷，是断言口径）：

| 断言 | 现在的结果 | 判断 |
|---|---|---|
| `renderer privateBytes drops in reading mode` | `[555 vs 447]` 失败 | 编辑态有了窗口化后**本身就更省**，阅读面 555MB 反而高于窗口化后的编辑面 447MB。"阅读模式一定更省内存"这个前提不再成立——它仍然省的是**渲染面 DOM**（2,881 vs 52,922 节点，−95%） |
| `editing DOM fully restored after click-to-edit` | `[45370 vs 45314]` 失败 | 差 56 个节点 ≈ 点击落入的那个公式被重新渲染（窗口化下它原本是占位）。**这是窗口化的正确行为**，断言需要放宽 |

其余 20 项（全选复制完整性 217,249/216,295、离屏占位、窗口内挂载数有界、任意位置无空视口、
大纲跳转、点击回编辑落点 166,061–166,185 精确命中）全绿。
