## 一、桌面版：从「单文档」改成「一个文件一个窗口」

### 1.1 原来的硬编码在哪里（取证）

| 位置 | 事实 |
| --- | --- |
| `app/main/main.js:135`（改前） | `createWindow(port)` 只调用一次 |
| `app/main/main.js:194-195` | `global.doc = new DocController(...)`、`global.win = win` 各一个槽位 |
| `app/main/doc.js:27` | `this.current` 单个文档对象 |
| `app/main/doc.js:84` | 注释直接写明「单文档模型：切换前若有未保存修改，先确认」 |
| `app/shell/shell.html:51` | 只有一个 `<iframe id="editor">` |
| `app/shell/shell.js:56` | `f.src = url` 就是"打开第二个文件"的全部实现 |

### 1.2 改法（为什么改多窗口比改标签条更省）

现有 `DocController` / `DocumentExporter` / `Workspace` 本来就是"一个窗口一份"的语义，
所以**实例化 N 份**即可；渲染层（`extension-src/render`）和外壳页（`app/shell/*`）**一行未改**
（外壳只改了拖放处理器，见 §1.4）。改动集中在主进程：

- 窗口注册表 `Map<webContentsId, rec>`；`rec = {id, win, doc, exporter, workspace, queue, boot, closing}`
- `global.win` / `global.doc` / `global.workspace` 改成**「当前聚焦窗口」的访问器**——
  菜单与 IPC 里「作用于当前文档」的写法不用重写；跨窗口的动作（`tree-*`、`export-*`、`boot`）
  一律按 `event.sender` 找发起窗口
- `ipcMain.on('ed-msg')` 只注册一次，按 `event.sender` 路由到对应控制器（改前它注册在
  `createWindow` 内部，多窗口下会重复注册、后者抢走全部消息）
- 每窗口装一遍导航/侧键守卫（`installWindowGuards`）
- 打开规则（`openPaths` / `openPathSmart`）：
  1. 文件已在某个窗口打开 → **聚焦那个窗口**，不开第二份（同一文件两份会互相把对方保存
     当成外部变更，实测确认这个取舍更稳）；
  2. 发起这次打开的窗口还停在欢迎页 → 填进去；
  3. 否则新开一个窗口；
  4. 目录 → 切换发起窗口的工作区
- 会话：`state.windows = [{file, ws, bounds, maximized}]`；`boot` 按记录逐个恢复
- 退出：`before-quit` 里逐窗口确认未保存，任一取消即中止整个退出
- 工作区 watcher 按根共享（`tree.js` 的 `watchHub`，引用计数），同目录多窗口只起一个递归 watch

### 1.3 新增接口（外壳/测试用）

`open-in-window`（在发起窗口里替换文档）、`new-window`、`open-paths`（多文件各开一窗）、
`windows-list`、`focus-window`、`close-window`；菜单新增「新建窗口」「在此窗口打开文件…」
「关闭窗口 Ctrl+W」。

### 1.4 外壳唯一改动：拖放多文件

`app/shell/shell.js` 的 drop 处理器原来只取 `files[0]`，现在把每个文件都交给 `open-paths`。
（这是本轮唯一的外壳改动。）

## 二、新套件当场抓出来的四个真 bug（都已修）

| 症状 | 根因 | 修法 |
| --- | --- | --- |
| 一次拖入/多选两个文件，最后只剩一个窗口 | `emptyRec()` 把**刚 createWindow、还没 boot** 的窗口也当成"空窗口"，第二个文件被塞进同一个新窗口 | 判据加上 `rec.queue.started` 与 `!rec.boot.file`（外壳真的 boot 过、也没有待装载文件才算空窗口） |
| 退出应用时弹「Object has been destroyed」错误框并卡住退出 | 窗口销毁过程中的 `focus` 事件回调里读已销毁窗口的 `webContents` | `focusedRec()` 包 try/catch 并先判 `isDestroyed()`；`focus` 回调跳过销毁中的窗口 |
| 新开的窗口全都跟着最大化 | 新窗口继承了「上一个窗口的 maximized」 | `maximized` 只由会话恢复与启动欢迎窗口显式传入；其余新窗口按上次的普通尺寸开窗 |
| 打开窗口时 `win.webContents.id` 抛异常 | `closed` 事件后 `webContents` 已不可访问 | 建窗口时把 `contentsId` 抓牢，之后统一用 `rec.id` |

另外两个由新套件暴露、属于**共享渲染层**的既有缺陷（见 §三）。

## 三、共享渲染层修复（桌面与 IDE 扩展同时受益）

**隐藏文档不派发 `<dialog>` 的 close 事件**（Chromium 既有行为，实测：多窗口下新建 dialog →
`showModal()` → `close()`，close 事件永不触发）。后果不只是弹窗关不掉：各弹窗都按 id 判重，
节点永久留在 DOM 里，于是「关于」「快捷键设置」**再也打不开**。

- 新增 `render/js/util.js` 的 `dialogSlotFree(id)` / `closeDialog(dialog, finish)`
- 六个弹窗统一改用：`about.js` / `edit-shortcuts.js` / `themes.js` / `reading-palette.js` /
  `surface.js` / `media-tools.js`；`close` 事件只作兜底
- 这也让「程序化关闭」在任何可见性状态下都确定收尾

## 四、超小窗口的工具栏自动收纳 + 最小高度按「实时渲染高度」定

### 4.1 自动收纳（工具栏占比 ≥ 35% 时）

- 触发：工具栏布局高度 / 编辑器可视高度 ≥ **35%**（实测极端小窗里达到 **116%**）
- 收起后鼠标贴顶（≤4px）滑出；鼠标停留在工具栏范围内保持；离开 **420ms** 后收回
- 键盘焦点落在工具栏按钮上同样滑出（无障碍）；`prefers-reduced-motion` 下不做动画
- 阈值以下**完全不介入**（正常高度实测占比 10%，一个像素都不变）
- 实现：`render/js/toolbar-autohide.js` + `render/css/toolbar-autohide.css`（工具栏本来就是
  绝对定位浮层，所以收起不会让正文重排跳动）

### 4.2 最小窗口高度：跟着「换行后的实测高度」走，不是固定 cap

用户原话：「不是 cap minimum Height……工具行会随着窗口变窄变成多行重叠。所以你应该检测的是
它实时渲染之后占了多高，这不光是高度问题，还涉及宽度有多窄」。做法：

- 渲染层每次布局变化（窗口 `resize` + 工具栏上的 `ResizeObserver`）把**实测**的工具栏高度
  连同**量它的那个视口高度**一起报给宿主（IPC `toolbar-height`，变化 >2px 才报，避免每帧 IPC）
- 宿主按 `最小高度 = ceil(工具栏高 / 0.8) + (窗口外框 − 渲染层视口)` 设 `setMinimumSize`，
  下限 320px、上限屏幕工作区 −40px，另加 420px 最小宽度
- 分母用渲染层给的视口（内容区减去状态栏）而不是窗口内容区，是为了和自动收纳那条 35% 的
  比值线**严格同分母**：否则状态栏那二十来像素会让「≤80%」实际变成 87%
- 真机实测（`toolbar-autohide` 套件 12 条断言）：

| 窗口宽度 | 工具栏换行后高度 | 窗口最小高度 | 工具栏占视口 |
| --- | --- | --- | --- |
| 1400px | 36px（单行） | 320px（下限生效） | 5% |
| 460px | 421px（多行） | **614px** | 80% |
| 460px、请求压到 150px | 421px | 被挡在 **616px** | **80%** |
| 再拉宽回 1400px | 36px | **回落 320px** | 5% |

「压窄 → 最小高度升到 614」与「拉宽 → 最小高度回落到 320」这一对方向相反的断言，正是
「它算的是实时渲染结果、不是写死的 cap」的证明（写死的 cap 在拉宽那一步不会降）。

## 五、规模/压力实测（用户要求：多大大文件、多少窗口到极限）

> 完整证据、未测项与**后续可改进方向**（每条都写了预期收益/代价/怎么验证）见
> `docs/PERF-MULTIWINDOW-20260912.md`；本节只放结论表。

套件 `scripts/windows-scale.cjs`，素材现场合成（700KB / 367,924 字符，正文为主、每 10 节插
公式+表格+代码）。全部数字来自 `app.getAppMetrics()` 与 `os.freemem()`。

### 10 窗口（默认上限）

| 窗口数 | 打开耗时 | 渲染进程 | 进程总数 | 全部 RSS | 系统可用内存 |
| --- | --- | --- | --- | --- | --- |
| 1 | 4404ms（冷） | 1 | 4 | 536MB | 104.1GB |
| 2 | 2382ms | 2 | 5 | 952MB | 103.8GB |
| 5 | 2231ms | 5 | 8 | 2490MB | 102.6GB |
| 10 | 2258ms | 10 | 13 | 4901MB | 100.5GB |

- **每窗口约 470〜490MB**，**打开耗时全程稳定在 ~2.2s**（0→10 窗口没有退化，说明没有争用）
- 多核证据（并行标定：同一份纯 CPU 活 = 整篇 `setValue` 重解析+重渲染）：
  **单窗 5006ms / 10 窗同时 4937ms = 0.99×**（串行会是 ~10×）
- 压力下真实输入往返 **532ms**，仍可用
- 关掉 9 扇窗后 RSS **8330MB → 695MB**（基线 227MB），只涨不落的情况不存在

### 16 窗口（`STRESS_WINDOWS=16`）

- 打开耗时仍然 **~2.2〜2.4s/窗**；16 窗口 / 16 渲染进程 / 19 进程；RSS **7526MB**（可用内存 97.7GB）
- 并行标定：**单窗 4991ms / 16 窗 7478ms = 1.5×**——仍然是并行，但开始出现争用（10 窗是 0.99×）
- 压力下输入往返 609ms；关掉 15 扇后 10929MB → 693MB

### 结论（本机 128GB / 20 逻辑处理器）

- **内存不是瓶颈**：每窗口 ~0.5GB，16 窗口 7.5GB（重编辑状态 10.9GB），占物理内存 6%〜8.5%；
  按套件自设的 25% 内存闸（32GB）估算可开到 60 扇以上
- **CPU 更早触顶**：10 扇完全并行、16 扇开始 1.5×，即"重文档并行窗口数"大致在
  **10〜16 扇**（约核数的一半到四分之三）之后开始互相挤压
- 安全阀全程生效：每开一扇窗之前检查 `RSS ≤ 25% 物理内存`、`可用内存 ≥ 20%`、
  单窗打开 > 8s 即停；本轮两次跑都停在"达到设定窗口数"，从未接近内存闸

### 6b.2 套件当场抓出的两个真 bug（都已修，`render/js/media-tools.js`）

| 症状（实测载荷/现象） | 根因 | 修法 |
| --- | --- | --- |
| 复制复杂表单元格，粗体记号与反引号**被静默吃掉**：载荷是 `粗体\t加粗\t$x_{1}+1x1+1$\tconst a=1`（`**加粗**`→`加粗`、`` `const a=1` ``→`const a=1`，公式还被 MathML 文本重复了一遍） | 单元格文本用 `textContent` 取：IR 里粗体是 `<strong>`、行内代码是 `<code>`，`textContent` 拿不到记号；公式因为源码留在 marker 里才侥幸没丢 | 新增 `cellMarkdown(editor,cell)`：走 Lute 的 `VditorIRDOM2Md`（与粘贴时 Md→DOM 同一引擎）序列化整格，先剔预览岛（KaTeX）。修后载荷：`**加粗**\t$x_{1}+1$\t`const a=1`` ` |
| 剪切表格矩形只得到 `a1a2a3`（三格拼在一起、没有制表符），粘到另一个窗口只剩一格，表形还可能被撑坏 | 表**没有** `cut` 处理器：浏览器默认的 cut 是线性 DOM 删除，与已被接管的 `copy`（矩形切片）根本不是一套语义 | 新增 `cut` 处理器：与复制同一套载荷（TSV + 只含该矩形的 html）+ `clearRectangle` 整格清空（一次撤销），并把光标落在矩形左上格 |
| 剪切图片粘到另一个文档后引用的是**源文档目录**（`images/A/…`），跨文档即断链 | 图片只有 `copy` 处理器，cut 落到浏览器默认路径（把 `<img>` 连相对路径写成 HTML） | `installImageMultiCopy` 里补图片 `cut`：先按"图片"写文件拖放列表（与复制同一路径），再把选中的图删掉；`context` 上加 `selectedImage` getter 供删除使用 |

同批还修了一个**连带 bug**：粘贴侧 `cellNodes(kind='markdown')` 原本会把反斜杠先翻倍，
而复制侧现在给的是**合法 Markdown**（`a\| b`）——翻倍后 Lute 读成"字面反斜杠 + 列分隔符"，
整行被撑成 5 列。改为只给"前面是偶数个反斜杠"的竖线补转义（纯文本那条分支行为不变）。

### 6b.4 一处如实说明的边界

引用式链接 `[ref][ref]` 的**定义行**在表格之外，单元格级复制只带得走标签本身，落到别的文档
会成为没有目标的 `[ref]`。契约断言因此用行内链接 `[例子](https://example.org)`（实测原样往返），
这条限制记在此处，不假装覆盖。

## 七、IDE 侧（VS Code / Trae）

### 7.1 取证：为什么"只能单开"

1. **`.md` 根本不归 MarkPilot**：两个 IDE 的 `settings.json` 里
   `workbench.editorAssociations` 都把 `*.md` 指向了另一个扩展 `seepine.md-editor`。
2. **预览标签**：两个 IDE 都没有设 `workbench.editor.enablePreview`（默认 `true`），单击文件会
   用同一个标签顶掉上一份——`CustomTextEditorProvider` 的标签同样受这套机制管。
3. **扩展没登记**：VS Code 的 `extensions.json` 里没有 markpilot（磁盘上有 2.0.19 目录）——
   目录侧载不会写登记表。

### 7.2 改动

- `contributes.configurationDefaults`：`workbench.editor.enablePreview` /
  `…FromQuickOpen` / `…FromCodeNavigation` = `false`（**默认值**，用户自己设过就尊重用户）
- 新命令 + 资源管理器右键 + 命令面板：「用 MarkPilot 打开（新标签页）」→
  `vscode.openWith(uri, 'markpilot.editor', {viewColumn: ViewColumn.Active, preview: false})`
  （`preview:false` 是任何设置组合下都成立的强制钉住手段）
- `markdownEditorProvider.js`：新增 `onDidChangeViewState` —— 标签重新可见时按宿主权威文本
  对齐一次；**内容一致就什么都不做**（避免无谓 `setValue` 冲掉撤销历史与光标）
- `install-vsix.cjs` 的登记问题用 IDE 自带 CLI 解决（`code --install-extension`），
  并核对 `extensions.json` 里出现 `jinxi.markpilot@2.1.0`
- 按用户批准改了两个 IDE 的 `*.md` 关联 → `markpilot.editor`（改前备份 `settings.json.bak-2.1.0`，
  diff 只有一行）

```bash

node scripts/publish-store-userenv.cjs --only=vsce
```
