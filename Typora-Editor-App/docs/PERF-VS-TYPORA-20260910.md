# MarkPilot 2.0.18 对 Typora 1.14.10 同口径性能对照

**日期**：2026-09-10（当日深夜至次日凌晨）
**被测**：MarkPilot 2.0.18（已安装的交付产物 `D:\Users\ltmroberthk\AppData\Local\Programs\MarkPilot\MarkPilot.exe`）对 Typora 1.14.10（`D:\Users\ltmroberthk\AppData\Local\Programs\Typora\Typora.exe`）
**机器**：i7-12700K / 127.7 GB / 屏幕 1707×960，两个应用都以最大化（客户区 1706×889）运行，与用户真实使用状态一致
**问题**：目前的性能是否比 Typora 强了？

---

## 零、去工程腔版（已同步到线上 README 首屏显著位置）

同一台电脑、同一个窗口大小、同一份「中文 + 公式」素材，两边都按最大化窗口打开；每一项都跑多次取中位值，并且用**两套互相独立的测法**交叉验证过，结论一致。

| 场景 | 实测 |
| --- | --- |
| 打开小文档（1.7 KB） | MarkPilot **快约 0.2 秒**（0.51 秒 vs 0.71 秒） |
| 打开中文档（67 KB） | MarkPilot **快约 0.14 秒**（0.61 秒 vs 0.75 秒） |
| 打开大文档（240 KB） | 几乎一样快（0.91 秒 vs 0.90 秒） |
| 双击文件后窗口弹出来的速度 | MarkPilot **更快**（0.29 秒 vs 0.33 秒） |
| 在大文档末尾点开一个公式、直接进源码编辑 | MarkPilot **快 6.5 倍**（0.024 秒 vs 0.156 秒） |

对照对象是同期最新版 Typora（1.14.10），MarkPilot 用 Windows 桌面版 2.0.18。
线上位置：`README.md` 第 16 行 / `README.en.md` 第 20 行，都在首屏大图正下方；用 `verify-readme-keep.cjs` 证明过"只增不删"（0 个标题、0 段正文丢失）。

## 一、结论（先说答案）

**分项看，不是一句话的强弱，但整体站得住：**

| 项目 | 结论 | 差距 |
| --- | --- | --- |
| 打开小文档（1.7 KB） | **MarkPilot 更快** | 正文进 DOM 快 ~195 ms（514 对 709） |
| 打开中文档（67 KB） | **MarkPilot 更快** | 快 ~140 ms（612 对 753） |
| 打开大文档（240 KB） | **打平** | 913 对 895 ms，差 18 ms（在噪声内） |
| 窗口出现速度 | **MarkPilot 更快** | 289 对 332 ms（像素尺子：175 对 318 ms，差得更明显） |
| 大文档文末点公式→展开进 LaTeX 源编辑 | **MarkPilot 明显更快** | **24 ms 对 156 ms（快 6.5 倍）** |
| 展开后画面彻底安静 | Typora 更快 | 584 对 358 ms（见第四节的口径说明，此项不宜单独下结论） |

一句话：**打开文档整体略胜（小中档明确、最大档持平），而"点公式展开编辑"这一项是压倒性的**——这恰好是 MarkPilot 主打的能力，也是本次新增验收项要盯的东西。

## 二、两把独立的尺子（为什么这次要两把）

一开始只有一把：屏幕像素（`win-peer-witness.ps1`，用 `PrintWindow` 让窗口自己渲染一份，按像素色量判断"正文上屏"）。它是"用户真的看见了什么"的最硬证据，但有个死穴——**窗口被遮挡时 Chromium 会返回纯色**。

本轮实测踩到了三次：
1. 抓到的"Typora 大文档"截图其实是**用户正在用的编辑器窗口**（`CopyFromScreen` 抓到的是遮挡物），一轮样本全废；
2. 改用 `PrintWindow` 后仍然在用户操作电脑时返回纯色（连续 3249 帧色量 0）；
3. 抢救机制（检测到纯色就激活并提到最前）在**对方窗口自己也是最前层且是活动窗口**时无效——`SetWindowPos(HWND_TOPMOST)` 对已经是 topmost 的窗口是空操作。

于是补了第二把尺子：**CDP over pipe**。Typora 接受 `--remote-debugging-port` 但**不监听**（开关被丢掉），却接受 `--remote-debugging-pipe`（fd 3 读 / fd 4 写）——这一点是本次的突破口。走 CDP 之后，窗口可见性、z 序、焦点统统无关，输入也走 `Input.dispatch*`（不会打到别的窗口上），机器被占用时照样能测。

**两把尺子的结论一致**（见第三节对照），所以下面的数字不是某一种测量方式的产物。

## 四、"安静"这一项为什么不下结论

"画面安静"两种口径不同：
- 像素口径 = 屏幕像素连续 400 ms 不再变化；
- CDP 口径 = 编辑器 DOM 的节点数/文本长度/后台渲染队列连续 400 ms 不再变化。

中档那一行两边打架（像素：MarkPilot 1240 / Typora 1257；CDP：MarkPilot 1528 / Typora 2451）。原因是 Typora 的 DOM 在像素稳定之后还在做记账式的变动（懒布局），DOM 口径把它算成"没安静"。**这一项依赖定义，不作为结论**；作为参考，用户在屏幕上体感到的"不动了"更接近像素口径。

## 五、大文档中后位置：点公式 → 展开进 LaTeX 源编辑（本轮新增验收项）

**场景**（用户点名要的）：在 240 KB 大文档里定位到文末的公式段，瞬时点击一个行内公式，量"展开成 LaTeX 源码可编辑"要多久。

**为什么把公式段放在文末**：滚轮格数在两个应用里走的距离不同，"向下滚 N 格"会落到完全不同的位置，根本不可比。`Ctrl+End` 是两边都会落到同一个地方的确定性锚点，所以素材 `large-tail-math.md`（240 KB / 1843 块 / 2320 个行内公式）刻意把公式块安排在文档最后一段之前。

**判据**（两边语义相同，各自贴合自己的 DOM；写成表达式，不是靠肉眼）：
- MarkPilot：`code[data-type="math-inline"]` 所属 `.vditor-ir__node` 带上 `--expand`，且该 `code` 元素真的占位可见（`width/height > 4`）；
- Typora：`span.md-inline-math` 带上 `md-expand`，且其内部 `script[type="math/tex"]` 从 `display:none` 变为可见（实测点击后确实变成 `inline`，且选区落在源码上，例如 `a_{5} + b_{5} = c_{5}`）。

**结果**（5 轮，两边各 5/5 成功展开，没有一次算作 no-op）：

| 应用 | 点击 → 展开 | 展开 → 画面安静 | 光标落在源码里 |
| --- | --- | --- | --- |
| **MarkPilot** | **24 ms**（16/27/24/25/16） | 584 ms | 5/5 ✓ |
| **Typora** | **156 ms**（156/161/145/148/157） | 358 ms | 2/5（点击视口内第一个公式时选区没进源码） |

**素材一致性核对**（不是看图）：两个应用的 DOM 一级标题都等于磁盘文件的一级标题「大文档文末公式节验收」✓；滚动定位都到达 100%（MarkPilot 75414/75413，Typora 134005/134005）✓。

**如实披露**：
- 两个应用的 DOM 文本长度不可直接比（MarkPilot 的 180517–210197 字符包含全部隐藏源码，Typora 的 141599 不含 MathJax 的 `script` 内容）；标题一致性才是素材同一性的证据。
- 判据只要求"源码可见可编辑"，不要求光标必然落在源码里；MarkPilot 5/5 光标在源码，Typora 2/5（点它视口里第一个公式时没有），这一列单独记录、不混进判据。
- 输入走 CDP（`Input.dispatchMouseEvent`），两个应用同一类事件。这一点比 OS 级 `SendInput` 稍弱（不经过系统输入栈），但对被测应用而言仍是真实鼠标事件，且两边完全对等。

## 六、有效性闸门与失败样本（宁缺毋假）

- 像素尺子：`captureFailed`（整轮最大色量低于门限 → 疑似取景失败）直接判废；24/24 通过。判废过的轮次在台账里留有原因（例如"抓不到窗口内容（最大色量 0 < 门限 600）"）。
- CDP 尺子：正文长度 < 200 字符 → 无效；打开耗时 18/18 有效。
- 公式点击：展开判据不成立 → 记为 no-op 并打印像素变化幅度；本次两边都没有 no-op。
- 素材保护：两个应用各自独立命名的副本，跑完核对 sha256；被改动就从原件恢复。全程未碰用户的真实文档。
- 「素材 145176 字节」为磁盘真值，`large-tail-math.md` 由 `fixtures.cjs` 生成（`fixtures.largeTailMath()`）。

## 七、过程中的三个坑（下次直接绕开）

1. **Typora 的 CDP 只能走管道**：`--remote-debugging-port` 它收下但不监听（`DevToolsActivePort` 不出现、端口不开放）；`--remote-debugging-pipe` 正常。Node 侧用 `stdio: ['ignore','ignore','ignore','pipe','pipe']` 拿到 fd3/fd4。
2. **注入输入前必须先"点进正文"建立焦点**：MarkPilot 的编辑器在 iframe 里，窗口成为前台并不等于编辑器拿到键盘焦点（实测 `document.hasFocus()===false`、`activeElement===BODY`），此时 `Ctrl+End` 送到外壳、文档一动不动；先在正文里点一下，`Ctrl+End` 立刻生效（实测 scrollTop 0 → 75085）。另外窗口被激活后要留 ~250 ms 再发输入，激活是异步的。
3. **`SendInput` 的返回值必须看**：它返回真正塞进队列的事件数。0 = 被拒（例如前台窗口完整性级别更高）。本轮实测都是正常插入（chord 4/4、click 3/3），问题不在"没送到"而在"送到了没人理"，第 2 条才是真因。

node scripts/probe-formula-click.cjs --rounds=5

node scripts/probe-input-delivery.cjs            # 全套

- `scripts/peer-cdp.cjs`：CDP over pipe 客户端（启动 + 接管道 + eval + 输入 + 截图）
- `scripts/acceptance/win-peer-witness.ps1`：屏幕像素证人（含遮挡抢救与输入安全闸门）
- `scripts/acceptance/win-sendinput.ps1`：最小 SendInput 驱动（wheel/click/key/origin）
- `scripts/probe-typora-dom.cjs`、`scripts/probe-typora-math-click.cjs`：摸 Typora DOM 与点击语义的发现脚本
