## 1. 复现（真产物 + 你的文档，确定性的）

拿你说那一行（`（原笔记此处写作 $\sum b_i\mu\{1^{-1}_{A_i}(b_i)\}$，是同一意思的绕远写法；直接以 $\mu(A_i)$ 计。）`）：
每个字按**上缘+2 / 中心 / 下缘-2** 三个高度各点一遍，共 162 次。判据是"光标是不是落在点的那个字附近"：

| 纵向位置 | 修前 偏离 | 修后 偏离 |
| --- | --- | --- |
| **上缘+2** | **27/29** ❌ | 2/30 |
| 中心 | 1/29 | 1/29 |
| 下缘-2 | 1/29 | 1/29 |

**"任何字的偏上都会触发"**——数字与你的描述完全一致。修前那 27 次光标全部落到同一个东西上：
`(PRE.vditor-reset, 92)`，也就是**编辑器根下第 92 个块的边界**；而那一段正文正好是第 92 个块，
于是光标显示在**这一行的最开始**。

## 2. 根因（几何量到像素）

`js/math-edit.js` 的 `fenceClick` 里有个 `blankLanding`：它负责把"贴着折叠块公式的那条空白留白"翻译成
"公式之前/之后"这个插入点。**为什么需要它**：留白不属于任何块，Chromium 会把那个点解析成隐藏源码里的
位置，接着一次退格就吃掉公式里一个字符（这条是 2.1.3 修的老问题，不能退回去）。

它的纵向容差是**公式盒 ±10px**。你那一行上面的情况是：

```
块 91：DIV[data-type="math-block"]   盒子 y = 257 .. 387   （130px 高的 $$…$$）
块 92：<p>（你说的那一行）            盒子 y = 387 .. 412
```

**两块紧贴**（公式底 = 正文顶）。于是"正文第一行字的上半截"（字形盒大约从 y=386/391 起）
整块落在 `387+10 = 397` 这条容差里，被当成了"公式下方的留白" → 光标被搬到公式之后那个插入点
= `(根, 92)` = **这一行的最开始**。

你说的"应该是点击在行内相对高度判定的问题"——就是这个判定。

## 3. 修法

留白在几何上就是"**任何块的盒子之外**"。所以 `blankLanding` 在给出结论之前先看落点有没有压在
**别的块**的盒子里；压着就认定那是正文，把这次点击交回给浏览器（Chromium 自己的答案本来就是对的——
这也一并量过：同一个点 `caretRangeFromPoint` 一直给出正确的文字位置，是我们的处理器把它改坏了）。

```js
const other = kids[index === lo ? lo - 1 : lo];
if (other) { const side = other.getBoundingClientRect();
  if (y >= side.top && y <= side.bottom && x >= side.left - 1 && x <= side.right + 1) return null; }
```

同一行 8 个纵向位置（上缘+1/+2/+3/+4）实测：修前**全部 32 次**落到段落之外（行首），修后**全部落回正文文字**。

## 4b. 「为何不能紧贴公式插入?」——没有拿走，改的只是"压在正文上"那一类

紧贴公式的**那条路原样保留**：留白在几何上就是"任何块的盒子之外"，最典型的是文档首块公式**上方**那条页边距。
这条写成了断言（场景 84 的 B 组）：

| 动作 | 结果 |
| --- | --- |
| 第一条块公式盒子 `y=85..177`，在它上方 5px（`y=80`）点一下 | 光标 = `(编辑器根, 0)` = **紧贴这条公式之前** ✅ |

**改掉的只有一类**：落点其实压在**另一个块（正文那一行）的盒子里面**。
在你自己那份文档里，块公式和下一段正文是**紧贴的**（实测 `gapPx: 0`，公式盒底 = 正文盒顶）——
也就是说那一带**根本不存在空白像素**，那些像素属于正文第一行，点它就该把光标放进正文。
原实现把"正文第一行的上半截"当成留白，才会把它搬到公式之后（= 行首）。

顺带作证：那个判断**没有**退回到老毛病——把光标放进"看不见的源码"里。
块公式留白相关的 5 组老断言（`test:math-caret`）与场景 74（`math-fence-and-boundary`，41/41）都还是绿的。
