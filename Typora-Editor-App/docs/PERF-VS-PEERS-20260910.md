# 性能定位：我们 vs 同类产品（2026-09-10）

> 结论先说：**在"富文本 + 公式 + 表格、30 万字符级文档仍然可编辑"这一问题类里，我们的分层方案处在
> 公开证据的最前沿；但不能声称全面最好——内存是明显弱项，且我们没有同机同素材的对手实测。**
> 本文把"我们测到什么"和"同类产品公开做了什么"分开列，最后给逐项判定和证明缺口。

## 1. 口径

- 本产品：MarkPilot 2.0.12（Electron 44 / Vditor 3.11.1 IR + Lute）。
- 素材：`.testws/教材合订本.md`，30.4 万字符 / Typora 式字数 12.1 万 / 5,563 行 / **2,576 顶层块 /
  5,689 个公式**（`.perf/optimized.json`：253,062 DOM 节点 / 5,064 公式）。
- 测量：CDP 驱动真实应用 + 页内 rAF 计时 + V8 CPU Profiler；数字全部落在 `.perf/*.json` 与
  `docs/PERF-RESULTS-*.md`，探针可复跑。

## 3. 同类产品的公开事实

- **Typora**：源码里 `MAX_FILE_SIZE: 2e6` 硬上限，超出直接拒绝渲染（"The file is too large to render"）；
  作者 2016 年起承认"cannot handle very large file well"；社区长期反馈输入/滚动卡、公式上百个即"难以忍受"，
  可行建议是降级到 1.6.7、拆文件，或用 `truncate_text` 插件把离屏内容 `display:none`。
  **它没有视口虚拟化，也没有增量重解析。**
- **ProseMirror / Milkdown / Tiptap 系**：不做视口虚拟化。作者 Marijn Haverbeke 的原话是
  "ProseMirror doesn't do viewporting. It might be possible to implement on top of it, but I don't know
  anyone who does."；一篇 2026 年的实测文章记录 400 KB Markdown 一次 5.75 s Long Task、5,000+ DOM、
  229 ms 编辑延迟，作者最后采用"按体积分级降级 + `content-visibility`"；有开发者在 HN 上因为
  Milkdown 长文档慢而自研了带原生虚拟化的编辑器。
- **CodeMirror 6（Obsidian、VS Code 的编辑器底座）**：**唯一在生产中真正做可编辑虚拟化的**——
  只渲染视口内若干行，其余用 `cm-gap` 占位元素顶高度；作者明确说视口系统是架构级、不可关闭，
  代价是快速滚动会出现空帧、高亮滞后。**注意它虚拟化的单位是"纯文本行"，不是富块。**
- **Obsidian**：2026-09-02 发布的 1.14.0 才修"大库里由属性后台重算引起的周期性输入延迟"，
  说明"大文档输入延迟"在头部产品里仍是活跃缺陷域。
- **Vditor（我们的内核）**：上游社区在 20 万字级别就有卡顿报告，社区建议是分片/虚拟滚动/拆文件；
  上游并没有块级增量 IR，也没有离屏渲染跳过——这两块是本项目的自有实现。
- **Atlassian（Confluence）**：只对表格、媒体、展开块这几类开 `content-visibility`（2026-09-10 全网
  调研结论，已固化进 SKILL §7）。
- **`content-visibility` 本身**：Chrome 85+ / Firefox 125+ / Safari 18 起基线可用（本轮检索确认）；而
  **"可编辑内容 + 跳过子树的编辑与光标语义尚未解决"这一点来自本项目上一轮的全网调研**（CSSWG #9337 /
  Chromium #40733057，已固化进 SKILL §7）——本轮针对 `contenteditable` + `content-visibility` 的定向检索
  没有再找到直接的官方缺陷条目，因此这条按"上一轮结论、待复验"看待；它正是我们"编辑面不虚拟化、只对
  只读面窗口化"的设计依据（该决定不依赖这条结论是否成立，因为编辑态我们用的是渲染跳过而非节点卸载）。
  **[2.1.30 已复验结案]** 定向检索仍找不到直接的上游条目（只对上 CSSWG #9337 的 `scrollIntoView`
  相关性讨论）；而我们**本来就在可编辑面上用它**（`css/large-doc.css` 的 `.typora-cv` +
  `contain-intrinsic-size:auto`，`large-doc.js` 对"跳过子树内没有可靠几何"显式临时切回 `visible`）。
  该论断降级为"未获上游证实"，设计不依赖它。详见 `docs/LOG-2.1.30.md` Step 7 第二件。
- **Lexical**：自定义渲染、性能优于 contenteditable 系，但官方文档仍没有长文档虚拟化能力。

## 4. 逐项判定

| 维度 | 判定 | 依据 |
|---|---|---|
| 可编辑大文档规模 | **领先** | Typora 2 MB 硬上限；我们对 30.4 万字符 / 5,689 公式仍可编辑 |
| 离屏渲染跳过（编辑态） | **领先** | 同类只见 Atlassian 局部使用；我们 ≥1500 块全局生效，最差帧 50–67 → 17 ms，内存反降 60–70 MB |
| 公式交互（点击→可编辑） | **领先** | 19–32 ms，公开资料里没有同级对手数据 |
| 增量序列化 | **领先** | 2,321 ms → 1.9 ms（对照原生 Lute 全文输出） |
| 只读窗口化 | **并列最好** | 与 CM6 同思路（等高占位）；我们做在富块上且保住原生全选复制，CM6 是纯文本行 |
| 稳态输入延迟 | **持平/落后** | 77–113 ms，不是 16 ms 级；CM6 系对纯文本输入更快 |
| 常驻内存 | **落后** | 渲染进程 ~1 GB；CM6 系同级文档量级更低 |
| 打开到"全部公式完成" | **落后但可解释** | 26 s；这是 5,689 个 KaTeX 的渲染总量，非交互阻塞（期间输入 28–53 ms） |
| 阅读模式首次准备 | **落后** | 98 s（等公式队列清空才窗口化）；期间阅读面可用，只是内存红利未到 |

## 5. 要"证明最好"还缺什么

上面第 4 节的"领先/并列"都建立在**我们自己的实测 + 对手的公开资料**之上，不是同机同素材对照。要把它
变成可辩护的结论，需要一次三方对照（本产品 / Obsidian / Typora）跑同一份 fixture，量四项：
打开到可交互、输入 p95、滚动最差帧、常驻内存。

可行性：Obsidian 与 Typora 都是 Electron，可以开 remote debugging 用与本项目相同的 CDP 探针；
但 Typora 在 2 MB 上限与闭源补丁上会让"同口径"打折。**这项工作要安装第三方软件到本机，需要你先点头。**

## 6. 一句话

对"同一个文档、同一种富文本能力"这个比较集，我们的成绩在公开证据里已经是第一梯队且部分指标领先；
真正落后的是**内存**和**非交互阶段的绝对耗时**（全公式渲染、阅读模式准备），这两项是下一步的着力点，
而不是再去做可编辑虚拟化——那是 CSSWG 至今未解决、ProseMirror 作者直言没人做成的事。
