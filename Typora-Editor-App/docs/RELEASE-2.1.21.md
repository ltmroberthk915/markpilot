# MarkPilot 2.1.21 发布说明（私版）

你问的是"能不能给行内公式的预渲染框也建起像素→光标的映射，复用渲染结果那份映射逻辑"。
查下来：**这份映射数据本来就在**（渲染结果上的 `data-typora-source-start/end` 就是映射本身），
但浮框那条路**根本没走它**——点浮框是交给浏览器自己夹光标的，而浏览器把光标解进了 KaTeX 的子树。

## 一 取证：两条路点同一个字形，得到两个不同的偏移

取证脚本 `scripts/acceptance/probe-inline-box-map.cjs`（真窗口、真鼠标事件、按下后**真的等**再松开，
逐拍记录"落点上是什么元素 / 光标在哪个节点 / 公式展没展开"）。展开一条行内公式，沿它的渲染宽度取 5 个点：

| 路径 | 点 6% | 28% | 50% | 72% | 94% |
| --- | --- | --- | --- | --- | --- |
| 折叠态点渲染结果（参照） | 0 | 3 | 6 | 7 | 10 |
| **展开态浮框里点（修前）** | **null** | **0** | **0** | **0** | **null** |

- **中段**（28/50/72%）一律得到源码偏移 **0**——也就是"点公式中段，光标跑到公式最前面"；
- **两端**（6/94%，落在浮框的内边距上）更糟：`null`（光标跑到框外的正文里），而且逐帧采样采到
  **`展开=false`**——`refreshMathEditing` 见"光标不在公式里"就把这条公式收回去，松手后又弹回来，
  **一次点击跳两下**。

事件时间线把成因钉死了（同一个探针的记录）：

```
mousedown target = SPAN.mbin（KaTeX 字形，在浮框里）
按住中：展开=true  光标=TEXT@0(offset=null, inCode=false)   ← 浏览器把光标解进了 katex 子树
松开后：展开=true  光标=CODE.vditor-ir__marker@0(offset=0)  ← click 的 target 变成 vditor-reset
冒泡到 document 的 click = 1（defaultPrevented=false）      ← 我们的 click 处理器压根没跑
```

两个原因叠在一起：

1. **按下时我们没接**。`math-source-map.js` 的 mousedown 里对展开态是明确让路的（旧注释：
   "展开态：原生选区留在只读预览里，别抢第一次点击"）。于是浏览器按自己的规则落光标——预览是
   `user-select:text`，光标就解进了 KaTeX 的子树（`inCode=false`）；
2. **松开时接不到了**。按下与松开之间浮框被重建，Chromium 把 `click` 派发到两次落点的**最近公共
   祖先**（= `vditor-reset` 编辑器根）。我们的 click 处理器开头就是
   `if (!host || !own) return;`（落点不在公式节点里就退出），于是这一次点击**完全没人管**，
   光标停在哪算哪。

内边距那两点的连锁反应也是同一根源：光标被夹到框外正文 → 收回循环摘掉 `--expand` → 公式塌回折叠态。

## 二 修法：浮框上按下 = 在这条公式的源码里落光标

`render/js/math-source-map.js` 的 mousedown 处理器，展开态不再让路：

```js
if (!event.shiftKey && !event.ctrlKey && !event.metaKey && !event.altKey &&
    event.detail <= 1 && pointer.offset !== null) {
  event.preventDefault();
  placeCaret(root, code, pointer.offset);
}
```

- **偏移用的是按下那一刻的版面**——这一点是现成的：`pointer.offset` 本来就在按下时算好了
  （`targetOffset()`，就是折叠态那条路用的**同一个函数、同一份映射数据**），旧代码只是没用它；
- 光标落进源码之后，`refreshMathEditing` 自然把这条公式判成"正在编辑"，**不会收回**；
- 随后那次 `click` 里的映射照旧会跑（算出同一个偏移、幂等），所以两条路的结果一致，不靠时序碰运气；
- **多击**（双击选词）与**带修饰键**的按下照旧留给浏览器；算不出映射的（预览不是我们这份 KaTeX
  渲染的）也照旧留给原生路径。

修后同一个探针：浮框内 offset 序列 **0 / 3 / 6 / 8 / 11**，其中 3 个与折叠态参照逐点相同，另两个各差 1
——那两处采样点正好压在字形边界上（浮框比渲染结果多了 9px 内边距，按宽度比例取点会左右平移），
场景 92 改成照**字形盒子**取点后完全一致。按下期间逐帧采样 **0 个"收起"帧**。

## 六 请你手验（三步）

1. 随便找个行内公式 `$...$`，**点开它**（渲染结果下方会浮出预渲染框）；
2. 在**浮框里**点几个位置（左、中、右、以及框的最边上）——光标应停在**你点的那个字符**那里，
   公式不会塌下去再弹回来；
3. 点浮框**最边上那圈内边距**——同样只是落光标，公式不动。

## 七 已知差异（如实说明，不影响本次口径）

- 点**行内公式最后一个字形**时，浮框那条路给的是**源码末尾**（行末口径：最后一个字形整格都算行末），
  折叠态那条路偶尔给的是"最后一个字符之前"。原因是折叠态那条路在**松手那一刻**重算一次映射，
  而那时公式已经展开、浮框已经挪到源码下方十几像素，落点对着的就不是原来那个字形了。这一版没动那条
  老路（它有 math-caret / 场景 83 的一串断言守着口径），只把差异记在场景 92 的证人里。
- WYSIWYG 模式下的行内公式浮框没有一并改动（你报的是 IR 模式；WYSIWYG 的展开/预览是另一套显隐机制）。
