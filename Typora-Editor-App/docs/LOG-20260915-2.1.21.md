# 2026-09-15 · v2.1.21 工作记录（行内公式预渲染浮框的像素→光标映射）

用户这一轮的请求只有一句：

> 「能否在inline math的预渲染框也同样建立像素级到光标的映射链接，链接的逻辑可以复用在渲染好的
>   in ma 的地方对于代码的映射逻辑」

这不是报错，是一个"能不能"的功能请求——按规矩先取证再动手：不先量一遍，就不知道这份映射到底
"有没有、通不通"。

## 一 先问"数据在不在"，再问"路通不通"

读代码的第一印象是：`.vditor-ir__preview` 只有一个（折叠态它在正文里、展开态它浮到源码下方），
而映射属性（`data-typora-source-start/end`）是渲染时就带上的——**那浮框里应该也有**。
真正去查（不是靠读代码猜）用的是仓库里现成的 IR 快照（`.perf/ir-formula-undo-*.json`），
里面存着一整条展开态行内公式的 DOM：

```html
<span data-type="inline-node" class="vditor-ir__node vditor-ir__node--expand">
  <span class="vditor-ir__marker">$</span>
  <code class="vditor-ir__marker vditor-ir__marker--pre" data-type="math-inline">(\mathbb{R}^k,\mathcal{B})</code>
  <span class="vditor-ir__preview" data-render="1" contenteditable="false">
    <span class="language-math" data-math="(\mathbb{R}^k,\mathcal{B})">
      <span class="katex">…<span class="mopen" data-typora-source-start="0">…</span>…
```

结论：**映射数据在浮框里（`data-typora-source-start` 有 11 个）**，`preview.previousElementSibling`
就是源码 `code`。所以问题不在数据，而在**有没有人用它**。

## 二 探针：把两条路摆在一起量

`scripts/acceptance/probe-inline-box-map.cjs`（新写）。第一版就踩了三个坑，都记在探针注释里：

1. **照源码 `code` 的盒子取点** —— 折叠态下源码是 0×0，五个点全部落在 x=0（连点都没点上）；
2. **坐标系用错**：`getBoundingClientRect()` 给的是 iframe 内的坐标，CDP 的鼠标事件认的是**外壳视口**
   坐标（本机 iframe 左边有 244px 的侧栏）。第一版把"iframe 内坐标"直接当外壳坐标发出去，点到了
   段落文字上，看起像"点击没反应"；
3. **采样点压字形缝**：按浮框宽度取比例时，浮框比渲染结果宽 18px（1px 边框 + 8px 内边距 ×2），
   同样的比例落到的是**另一个像素**，于是差 1 个偏移——那是采样的差别，不是映射的差别。
   最终场景 92 改成照**字形盒子**取点（每个字形左起 1/4 处）。

量出来的东西（修前）：

| 路径 | 点 6% | 28% | 50% | 72% | 94% |
| --- | --- | --- | --- | --- | --- |
| 折叠态点渲染结果 | 0 | 3 | 6 | 7 | 10 |
| 展开态浮框里点 | null | 0 | 0 | 0 | null |

加上事件时间线（mousedown / 按住中 / 松开后三拍）与"click 有没有冒泡到 document"这个判据：

- 按住中：`展开=true 光标=TEXT@0(offset=null, inCode=false)` —— 光标解进了 katex 子树；
- 松开后：`光标=CODE.vditor-ir__marker@0`，`click` 冒泡到 document 且 `defaultPrevented=false`
  ——**我们的 click 处理器压根没跑**（`click` 的 target 是 `vditor-reset`：按下与松开之间浮框被重建，
  Chromium 把 click 派发到两次落点的最近公共祖先）。

## 三 修法（一处，7 行）

`render/js/math-source-map.js` 的 mousedown：展开态不再让路，按映射自己落光标。

```js
if (!event.shiftKey && !event.ctrlKey && !event.metaKey && !event.altKey &&
    event.detail <= 1 && pointer.offset !== null) {
  event.preventDefault();
  placeCaret(root, code, pointer.offset);
}
```

关键点是**复用**：`pointer.offset` 是按下那一刻用 `targetOffset()`（折叠态那条路的同一个函数）
算好的，旧代码算完就搁在那里没用。用户说的"复用渲染结果那份映射逻辑"正是这个意思——不用新写映射。

## 六 这一轮踩到的两个坑（写给下一轮）

1. **"阅读用时 45 分钟"里有一半花在坐标系上**。`getBoundingClientRect()` 的坐标系（iframe 内）
   与 CDP 鼠标事件的坐标系（外壳视口）不是一回事，而现成的 `spot()` 助手把两者**都**塞在一个对象里
   （`left/top` 是内层、`shellLeft/shellTop` 是外层），第一版混用了 `left`——点到的地方与量到的地方
   差了 244px。**先量 elementFromPoint**（内层外层各测一次）再发鼠标事件，是这一轮最快的定位手段。
2. **采样别按容器宽度取比例**。浮框有内边距，同样的比例是**不同像素**；差 1 个偏移会被误读成映射错了。
   照**字形自己的盒子**取相对位置，两条路才是真的同像素。
