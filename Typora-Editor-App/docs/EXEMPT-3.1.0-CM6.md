## A 类 · 真正的豁免（产品里存在"只对某形态生效"的护栏）

### EX-1 超长行的行内标记护栏（`scanInlineMarks` 的 `huge` 分支）

- **形态**：`src-cm6/main.js` 里 `const huge = t.length > 20000;` ⇒ 超过 2 万字符的**单行**跳过
  转义隐藏与全部行内标记正则（粗体/斜体/代码/链接/删除线/自动链接），**图片扫描仍然执行**。
- **为什么架构容纳不了（本轮结论）**：该分支的两个代价都与**行宽**成正比——① 转义循环逐字符；
  ② 十余条行内正则各扫整行（本题材实测单行 91.6 万字符）。**视口虚拟化不解决"单行 O(n)"**：
  CM6 只保证不给视口外的行建 DOM，不负责把一个**行内**的扫描切小。要把这条消除，必须把行内扫描
  切成**按位置窗口/分片**并在分片边界上带状态续接——那是引擎数据层的结构改动，不是这版的范围。
- **用户可见影响**：≥2 万字符的单行里，`**粗体**`、`` `代码` ``、`[链接](…)` 保持**字面**；
  图片写法仍渲染成图；光标可正常进入与编辑（该行仍按普通段落换行显示，见清单 §5.13 判据）。
- **消除条件（何时）**：把行内标记扫描改为**分片增量**（与 A1 同一族）之后复核；
  届时判据＝"3 万字符单行里的 `**粗体**` 渲染成粗体，且该行每键延迟不劣于同文档普通行"。
- **当前状态**：**保留**（有豁免，且已在本版 §5.13 判据里如实写明口径）。

## B 类 · 判据口径修订（不是产品豁免，也不是缺陷）

### EX-2 零宽字符"占宽 ≤2px"（清单 §5.12）——**已消除：它不是判据问题，是产品缺陷**

- **当时的判定（错）**：两条独立量法同值（`coordsAtPos` 5.5px、DOM `Range` 5.5px）+ 3.0.8 对照同样红
  ⇒ 判为"本机字体对 U+200B 的度量"，归**口径修订**。
- **真因（2026-10-09 查明）**：那 5.5px 不是字体给的。同一个字符放到编辑器外用**同一个字体栈**量是
  **0.01px**（11 种字体全为 0 或 0.01）；编辑器行里它被替换成了
  `<span class="cm-specialChar" title="Control character zero width space">•</span>`
  ——**CM6 `highlightSpecialChars` 的可见占位字形**（默认红点）。是产品行为。
- **处置**：**修产品**（引擎 CSS 一条规则把该占位压成零宽，其它控制字符保留红点提示），
  **不动判据**。复核：视觉前后对比图 + 全量验收 **80/80**。
- **留档的价值**：这条记的是"**当测量与实现都指向同一个渲染结果时，怎么区分'字体给的'和'我们画的'**"
  ——答案是**把同一个字符搬到被测系统之外、用同样的排版条件再量一遍**。
  详见 `LOG-3.0.9-3.1.0-CM6.md` §4-b/§4-c 与 `ARCH-3.1.0.md` §22.6。

## C 类 · 未完成/已收窄的架构项（**不是**豁免；按第一条的口径走架构路线）

### OPEN-1 轴 2：超长单行下的键入延迟 —— **本轮已把主要部分收口，剩余面收窄**

**本轮已完成（实测，详见 `LOG-3.0.9-3.1.0-CM6.md` §8）**：定位到 93% 的代价来自
`scanInlineMarks` 在 23 条"单行大图"（每条 20~90 万字符）上的三处**逐字符 JS 循环**
（找 `<img>` 的 `>`、找 `![]()` 的配平 `)`、实体替换正则），改成原生跳读 + 早退后：

| 读数 | 修复前 | 修复后 |
|---|---|---|
| 扫描器合计（Node 孤立计时，同一夹具） | 57.81 ms | **12.02 ms** |
| 每键 dispatch · 文档末尾 | 95.4 ms | **13.0 ms** |
| `§7.8 perfLargeDocTyping` 验收 | ✗ | **✓** |

**剩余面（仍然开着，不许当成"已解决"）**：
1. **在 50 万字符的单行内部打字**：p50 **41.9 ms**。**这笔钱不在引擎数据层**——
   把那条巨行单独做成夹具量，四个扫描器合计只要 **0.8 ms**（`lineStyles 0.01 / tables 0.40 /
   mathSpans 0.02 / inlineMarks 0.38`）。其余约 41ms 花在 **CM6 自己对"整行 DOM 文本"的重写上**：
   一行就是**一个文本节点**，改一个字符也要重写整行。
   ⇒ 所以"行内分片扫描"（原计划的下一步）**并不能解决它**；要降它只有两条路，**都需要产品决策**：
   - **行内分片渲染**：把一行拆成多段 DOM（CM6 不支持，等于自建行内虚拟化）——工程量大、风险高；
   - **不让超大图停在一行里**：入库时把几百 KB 的 data URI 折行或外置成附件——**这会改写用户的文档**，
     必须由用户拍板（本版不做）。
   **判据（若继续）**：先定"超大图是否允许改写文档"这条产品口径；定了以后再谈数字。
   **这种行是从哪来的（量过，不是猜）**：普通散文文档根本没有长行——
   本项目自己的 `ARCH-3.1.0.md`（802 行，最长 411 字符，中位 44）与 `LOG-3.0.9-3.1.0-CM6.md`
   （482 行，最长 421，中位 44）里 **>2 万字符的行 = 0**。长行只有一种常见来源：
   **图片被内联成 base64 写在同一物理行**（`<img src="data:image/png;base64,…">` / `![](data:…)`）。
   而**本产品的图片策略默认就是 `inline`**（`imageModePref()` 缺省返回 `inline`；设置面板可切
   "落盘 assets/ + 相对路径"，文档头 `mp-image-mode: assets` 亦可）⇒ **粘贴一张截图就造出一条几十万字符的行**。
   实测代价分布（同一份 8.5MB 内联图文档）：
   · 视口里**有**巨行、改的是空行 ⇒ **12.7–15 ms**
   · 在巨行**内部**改 ⇒ **40–57 ms**
   · 同等体量但**没有巨行**的合成夹具 ⇒ **~1.4 ms**
   
外部对照（子代理调研，2026-10-09）：**没有任何主流编辑器把 inline 作为默认**（Typora / Obsidian / VS Code / JetBrains / Zettlr / MarkText 全部落盘；base64 在 Markdown Monster、Markdown All in One 里都是 opt-in 且默认关），且 **GitHub / GitLab 渲染会剥离 `data:` 图片**（html-pipeline 白名单：img src 仅 http/https/相对）⇒ 内联文档推上 forge 必裂图。报告与来源链接：`.mp-verify/images-research/REPORT.md`。
⇒ 结论：**代价跟"视口里有没有巨行"走，不跟文档大小走**；把图片策略切到 `assets`
   就等于从源头消掉这一族（代价是文档不再自带图、换目录需要带上 assets 目录）。
2. **`lineStylesField` / `scanTables` / `scanInlineMarks` / `buildBlockMath` 仍是全量重扫**
   （合计 ~12ms）。原本计划的"按行缓存"经**对抗复核证伪**：多行件端点（跨行 `$$`、跨行注释）
   与整表列宽/格内容**不是行局部量**，照原设计复用会**静默出错**（含"覆盖层按旧格写回 ⇒ 可能写错格"
   这类数据损坏级形态）。⇒ **原设计不予推进**，改走"只修热点 + 保守门"，见下。
3. **与 Typora 的成对入表尚未做**（Typora 1.14 拔了 CDP 熔丝，需另建屏幕采集法）。
   按性能宪章第二条，**没有 Typora 数的轴不得宣称"超越"**——本版只报绝对读数，不宣称超越。

**已落地的一处正确性修复（顺带）**：`a1ScanMath`（数学 span 增量）此前**就是错的**
（单步编辑穷举 1539 例中 5 例与全量不一致，最小 6 行可复现，症状是公式块整条消失）。
修法＝窗口自洽扩张（用扫描器自己的产出判断是否切在半截）+ 脏区邻域保守门；
复验＝1539 例 + 2000 步 fuzz 均 0 不一致。
