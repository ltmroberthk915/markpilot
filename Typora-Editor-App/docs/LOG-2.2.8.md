# LOG-2.2.8：查找面板焦点被抢（我上一版带出来的回归）+ 标题块首的 ← 死路与退格吃 `#` + 94 号场景的走法修正

修标题块首的 ← 卡死、修查找面板的焦点被抢。三件都做完，另有一处**我自己的方法论错误**要更正。

## 一 查找面板：焦点被**我上一版的点击补丁**抢走（回归，已修）

**病象**（场景 75 的两条红）：Ctrl+F 打开面板、点输入框、输入 `a1+b1=1`（只存在于块公式源码里）——
面板一直报 `0 / 0`，而**那 7 个字符进了文档**（52 → 59 字节）。

**追凶**（`probe-repro-findfocus.cjs`，focus/blur/activeElement 时间线 + `focus()` 调用栈）：

```
t=3    面板打开，find-replace.js 自己 focus() 输入框 ✓
t=721  真鼠标点输入框：mousedown/mouseup/click 全落在 INPUT ✓ 焦点也在 INPUT ✓
t=737  focusout INPUT → focusin PRE.vditor-reset ✗   ← 14ms 后焦点被搬回编辑器
```

`focus()` 代理里**没有**对应调用 ⇒ 不是 JS 主动抢的，是"**选区落进可编辑区时 Blink 会把 DOM 焦点一起搬过去**"。
谁写的选区？我自己的点击类补丁标记给出了答案：

```
空白带: {"点":[522,150],"方向":"之前","落":"这是一段正文。"}
```

—— **`patchBlankBandClick`（2.2.6 加的那条）** 只按"块公式盒子的几何"判定空白带，
**不知道查找面板浮在正文之上**，于是把它当成"点块公式旁边的空白"，把光标挪进了正文，
顺带把焦点带走了。

**修法**：两条点击补丁（`patchBlankBandClick`、`patchClickIntoFormulaSource`）加同一道闸门——
`document.elementFromPoint(点)` 必须在**编辑器正文里**（`root.contains`）才算数；浮层上的点击一律不接管。

**A/B**：2.2.5 便携版 75 = **50/50 通过**；2.2.6/2.2.7 = 48/50（同一形状）⇒ **是我 2.2.6 带出来的回归**，
不是"既有红"。修完 dev 树 75 = **50/50** ✓。

## 二 标题块首：← 是死路、退格会吃 `#`（都修了）

**实测**（`probe-repro-headstart.cjs`，2.2.5 与 2.2.7 读数一致）：点标题正文 → 光标落在 `# ` 记号里
（offset 2）→ 按一次 ← → 落到**块首**（文本节点 offset 0）→ **再连按三次 ← 完全不动**。
契约是"行首 ← 去上一行行尾"（2.2.3 定的），这里是死路。

**修法**：`patchCaretWatchdog` 增补一手——← 之后若光标**原地不动**、且停在"偏移 0"的块首位置上，
就按几何去上一行的可落点（`邻行` 的 ← 方向从行右缘往左扫，取到的是**行尾**）。
判"是不是真块首"交给"原地没动"这一条：块中间的 offset 0（比如加粗段开头）按 ← 是会动的。
实测：`{"状态":"已左走到上一行","从":237,"到":181}` ✓（标题 → 上一行＝表格末行）。

**顺带查出一个更严重的**（`probe-repro-headbackspace.cjs`）：在这个块首位置按**退格**，
`# ` 会被吃掉（`井号被吃: true`、标题当场降级）——正是用户 2026-09-15 报的"非常奇怪错误的逻辑"，
只是换了个落点形状：2.1.25 的护栏只认"光标在**记号里** offset 0"，而现在产品给的是
"**正文** offset 0"（记号右边一格）✗。

**修法**（`marker-caret-guard.js`）：`atBlockStart` 增加第三种形状——"块首正文 offset 0"
（必须是这个块跳过记号后的**第一个正文位置**，避免把"加粗段开头"误判成块首）；
命中后走原有两条路：
- 上一块**吞不下正文**（表格/代码块/公式块…）→ `preventDefault`，这一按什么都不做 ✓
  实测 `守卫标记: {"blocked":true,"prev":"TABLE"}`、`标题还在: true` ✓；
- 上一块**能合并**（段落/标题/引用）→ 先把光标挪到记号之前再交给浏览器 ✓
  （不挪的话 Chromium 会删掉左边的 `#`；挪了之后它会正常把标题并进上一段 ✓）。

## 三 94 号场景：走法改回真实手势（用户选的 A）

它 ② 段的 setup 原来用 JS 直接把光标塞进正文文本 offset 0，再断言"光标在 `# ` 记号里（记号 offset 0）"——
那条捷径在新产品上落到的是**正文 offset 0**（记号右边一格），于是整个 ② 段连带 6 条断言全红。
按用户选的口径改成：

- setup 走**真实手势**：点开标题 → 按 ← 走到最左（与它自己注释里写的一致）；
- 断言的判据换成用户看得见的性质：**光标停在这一块的最前面（偏移 0）**，在记号里或紧贴记号右侧都算；
- ② 那段的退格断言**一条没动**（表格上文：什么都不做；段落上文：合并进上一段、不留 `#`；一次 Ctrl+Z 可退回）。

实测：94 = **16/16 通过** ✓（修前 10/16）。

## 四 我自己的方法论错误（必须记一笔）

`scripts/acceptance/run.cjs` 的 `--app` **默认是 `installed`**（已安装的成品）。
本会话里我有几轮场景批**没写 `--app`**，于是跑的是"当时已安装的那一版"，而不是我正在改的开发树——
`fix2.2.5` / `fix-2.2.7` 两批的通过数字因此**归属错了**（它们证明的是当时已装版本，不是那一轮的改动）。

- 已确认受影响：2.2.5 轮的"14 场景全绿"、2.2.7 轮的"13 场景全绿"。这两批当时被测的分别是
  已安装的 2.2.4 / 2.2.6，**不能**算作那两轮改动的验收。
- 不受影响：所有显式带 `--app=dist-2.2.x/win-unpacked/...` 的**打包产物**批、
  以及显式带 `--app=installed` 的**实装**批（那两类的口径本来就是"成品"）。
- 补救：本轮起一律显式写 `--app`；下面第五节是 **dev 树**上的复验（12 个场景）。
