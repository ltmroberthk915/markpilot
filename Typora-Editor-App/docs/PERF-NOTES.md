# 大文档性能基准与优化需求（供插件侧 GPT 参考）

> 2026-09-05：P0/P1 已在 1.0.1 实现。实测、测量口径修正、初始化取舍和回归记录见 [PERF-RESULTS-2026-09-05.md](PERF-RESULTS-2026-09-05.md)。以下保留原始诊断记录。

测试环境：Typora Editor EXE v1.0.0（渲染层 = seepine.md-editor 0.1.7-local 原样副本），
样本 `教材合订本.md`（30.4 万字符 / Typora 式字数 12.1 万 / 5,563 行 / 972 个 `$$` 块标记 / ~6,000 行内公式）。
测量方式：CDP 驱动真实应用 + 页内 rAF 精确计时 + V8 CPU Profiler。

## 实测数据

| 指标 | 1万字 | 3万字 | 12万字(6000公式) |
|---|---|---|---|
| 打开（全文进 DOM，冷启动） | <1s | — | ~1.1s |
| 输入→DOM 渲染延迟（稳态） | 68ms | 245ms | 1184ms |
| 输入→DOM（刚加载完的窗口期） | — | — | **最高 13.5s** |
| 滚动帧率（连续滚轮） | — | — | 21fps（应 60） |
| 点击公式预览→源码可编辑 | — | — | **16-22ms（50%/75%/95% 深度均优）** |

DOM 规模：53,449 节点 / KaTeX 预览 6,172 个 / 滚动高度 19 万 px。

## 输入卡顿的 Profiler 归因（12万字，稳态 0.9s 的一次插入）

- GC 23.7%、(program) 15.5%
- Lute（Go→WASM）重解析合计 ~30%：`$append`、`$subslice`、`readByte`、`$restore`、`bytesToString` 等
- `normalizeSnapshot @ typora-patches.js` 1.6%
- 其余为 vditor `index.min.js` 内部

结论：**瓶颈不在语言速度**（Lute 已是编译型 WASM；公式点击定位 16ms 证明管线 scoped 时很快），
而在三点架构行为：

1. **输入触发大范围 Lute 重解析 + 快照重建** —— 延迟随全文档规模线性增长（68ms→1.2s 曲线为证）。
2. **公式后台渲染队列与输入抢主线程** —— 加载完成后的队列窗口期内输入可卡 13.5s（观察：加载 2 分钟后
   KaTeX 计数仍在 5686→6172 增长）。
3. **急切渲染全部 6000 公式 + 5.3 万 DOM 节点常驻** —— 滚动 21fps。

## 建议的优化（按投入产出排序，均在 render/ 层）

### P0 公式队列让路（小改动，修 13.5s 窗口期）
`typora-patches.js` 的后台公式渲染改为分片 + `requestIdleCallback`；收到 `beforeinput`/`keydown` 时
暂停队列，空闲若干 ms 后恢复。预期：窗口期输入回到稳态水平。

### P1 输入重解析收窄（中等工作量，稳态延迟降一个量级）
检查 vditor IR 输入路径上是否把大范围内容重新过 Lute + `normalizeSnapshot`；把重解析范围限制在
当前块（光标所在段落/公式节点）。目标：12万字稳态输入 ≤150ms。

### P2 大文档分块渲染 / 虚拟滚动（架构级，滚动 60fps + 打开提速）
只渲染视口附近块，离屏块保留占位高度。工作量大，P0/P1 做完实测后再评估是否需要。

## 不建议的方向

C++/Rust 重构：需要替换 Vditor+Lute+KaTeX+全部 Typora 补丁（数月级），而热点数据显示编译型内核
（WASM Lute）已经在位、卡点在架构调度与 DOM 规模 —— 换语言不解决任何一个卡点。
Typora 本尊同为 Web 渲染栈（CEF），同类产品无原生渲染先例。
