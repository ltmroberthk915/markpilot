# 低成本补全优化：实现与 100 处成对验证

2026-09-07。采用于插件 0.1.24-local、桌面版 1.0.14。

**本轮直接可用率为旧版 76%、新版 85%；总输入 token 增加 1.3%，输出 token 减少 25.3%。** 通过事先固定的工程采用门槛后，将改动同步到 EXE 和 VSIX。结果支持小范围采用，尚不证明跨文档、重复抽取下稳定提高 9 个百分点。

## 实际改了什么

1. **少量文内定义。** 复用现有标题索引，在同一次 Markdown 遍历中记录短定义。数学请求按当前表达式、终值/节点等局部线索筛选同章原文，最多两条、定义正文合计最多 480 字符；连同章节标题仍不超过原有 1,200 字符上限。已有局部上下文中出现的整条定义不再重复注入。明确的同名定义优先；找不到相关信息就不补这一部分。
2. **更具体、较短的提示词。** 约束模型沿用字母、星号、下标、矩阵方向和控制历史；填入后应与光标右侧直接接通，不另起定义、重复等式。文字补全要求短语衔接、完整 dollar 定界符，避免在已有动词前留下冒号。这些仍在同一次生成中完成。
3. **保守的标点清理。** 对已确认的粗体结束标记，透过 `**` 或 `__` 识别原有句号，去掉补全末尾重复的句号。跳过转义、代码、数学内容及单词内部的下划线；不自动猜改数学符号，也不改用户已有的右侧文本。

没有新增检索服务、外部依赖、后台模型、二次模型检查或推理链。定义功能沿用工具栏补全菜单的“章节上下文”开关；关闭时保留原有光标附近上下文范围。

## 质量

A=语义正确且能直接插入；B=小改可用；C=含义/记号错误或插入失败；D=无可用输出。等价数学式和合理的其他文字表述可以得 A，不要求原文逐字恢复。

| 类别 | 旧版 A / B / C / D | 新版 A / B / C / D | 直接可用率 |
| --- | --- | --- | --- |
| 数学 70 处 | 55 / 2 / 13 / 0 | 59 / 1 / 10 / 0 | 78.6% → 84.3% |
| 文字 30 处 | 21 / 3 / 6 / 0 | 26 / 2 / 2 / 0 | 70.0% → 86.7% |
| 合计 100 处 | 76 / 5 / 19 / 0 | 85 / 3 / 12 / 0 | **76% → 85%** |

15 处从非 A 变为 A，6 处从 A 变为非 A，净增加 9 处。等级比较为 16 改善、6 变差、78 不变；A+B 为 81% → 88%。

分层配对 bootstrap 20,000 次，探索性 95% 差异区间为 **0～18 个百分点**；精确 McNemar 双侧 p=0.078。按通常 0.05 门槛尚未达到统计显著。样本来自同一份已测试过的笔记，缺口之间相关、每组每处仅抽一次、评分只有本助手一位评审；这些限制可能让区间显得过于乐观，不应当成独立用户的真实接受率。

具体改善包括 M19 终值函数重新使用 `Phi`，M25 漂移项使用 `g*`，M42 恢复节点概率乘收益函数。新版仍有 12 条 C；部分原本正确的缺口也退步，例如连续收益补成离散求和、把带可行约束的问题误称为无约束最大化。未通过逐题改提示词再重抽来掩盖这些错误。逐项内容及理由保留在下方文件。

## 时延与 token

时延从调用到完整响应及清理结束，不含编辑器防抖或灰字显示。使用线性插值分位数。

| 类别 | 旧版中位 / P95 | 新版中位 / P95 |
| --- | --- | --- |
| 数学 | 1,200 / 1,667 ms | 1,177 / **2,206 ms** |
| 文字 | 1,419 / 1,942 ms | 1,251 / 1,582 ms |
| 全体 | 1,231 / 1,747 ms | 1,196 / 1,721 ms |

总体中位数约快 35 ms，但**数学 P95 增加约 540 ms（32.4%）**。本轮不能宣称全面加速，更不能用总体 P95 掩盖数学长尾变化。供应商负载和缓存没有完全控制，尚不能确定长尾差异是否由策略导致。

| API 返回的 token | 旧版 | 新版 | 变化 |
| --- | ---: | ---: | ---: |
| 总输入（含缓存读取） | 126,481 | 128,110 | **+1.3%**，平均约 +16 token/次 |
| 输出 | 1,624 | 1,213 | **−25.3%** |
| 其中：文字输出 | 733 | 363 | −50.5% |

58/70 个数学请求获得额外定义，文字不做定义提取。本轮章节与定义最多 661 字符。精简提示词抵消了大部分定义输入；JSON 请求平均字符数下降不等于 token 必然下降，所以以上以实际 usage 为准。

本地性能另作零 API 测量：178,107 字符文档的索引构建约 3 ms，新版缓存查询中位 0.11 ms、P95 0.365 ms，旧版约 0.042 / 0.081 ms。新增本地工作量很小，但单次冷启动数据受 JIT/运行顺序影响，不能据此宣称启动更快；也未进行整机功耗测量。

两组输入缓存读取比例为旧版 **95.4%**、新版 **16.4%**，明显不对等。新提示首轮缓存较冷，实际本轮计费差异不能作为日常稳定成本差异。按官方非高峰单价估算，200 次合计约 **$0.0277**；这是 usage 推算，不是账单实扣。若两组都假定完全未命中缓存，旧版约 $0.02890、新版 $0.02898，差约 **0.3%**；这只是同等缓存的算术情景。价格依据 [DeepSeek 官方价格表](https://api-docs.deepseek.com/quick_start/pricing/)。

总输入按兼容接口的未缓存 input、cache-read、cache-creation 三部分求和；字段口径见 [Anthropic 缓存说明](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) 与 [DeepSeek 兼容接口说明](https://api-docs.deepseek.com/guides/anthropic_api/)。
