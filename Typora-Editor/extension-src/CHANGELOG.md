## 2.1.29 (2026-09-16)

### 软换行 + 中文输入法：光标被复位到段落开头

- 现象（用户报告）：素材开头是"植树问题-加密共隔"那类笔记时，在行尾按 Shift+Enter 软换行、接着键入中文（拉起输入法），光标跳到上一行、字插进段落开头。
- 根因：块尾软换行的零宽脚手架（`SOFT_BREAK_PLACEHOLDER`）由 `input` 监听摘掉，而输入法上屏的 `input`（`inputType=insertCompositionText`）也在其中。**在组合还活着的时候改组合所在的文本节点**，Blink 会把这次组合判作失效、在节点开头重新起一次（实测 `compositionstart` 的选区从行尾 39 跳到 0），于是候选串与上屏的字都插进了段落开头。
- 修法（`render/js/typora-patches.js` 的 `removePlaceholder`）：组合期间只记状态不动 DOM（`composing` 标志 + `event.isComposing` 双重守卫）；`compositionend` 之后**推到下一个宏任务**再摘——实测在 `compositionend` 处理器里改节点同样会跳（Blink 要等这条事件派发返回之后才把组合落定）。另加一条：只有新行上真落了字才摘脚手架，输入法空组合被取消时块尾那行不会塌掉。
- 验收：`scripts/acceptance/scenarios/100-ime-softbreak-caret-2.1.29.cjs`（21 条断言 / 8 证人，含窗口真实像素的"第一行逐行一致 + 第二行从无墨变有墨"与磁盘证人）。负对照（临时撤掉守卫）该场景 11/21，失败项正是用户描述的症状（`路边路边等间隔种树…`）。

### 行内公式周围的四个光标问题（用户要求"按实际书写笔记流程按实际键盘输入一个一个测"）

- 现象（用户报告）：行内公式（Ctrl+Shift+E）里打完字，用右方向键走到右 `$` 之外再键入任何内容，光标会跳回数学区；并明确要求"方向键碰到 inline 数学区"要像 Typora 那样打开编辑代码区，而不是整块跳过；同时要求核查块公式。
- 定位方式：新增真键盘"写笔记流程"体检探针 `scripts/acceptance/probe-note-flow.cjs`（82 步 / 36 条"输入必须落在光标处"的不变量），从空文档一路写到标题、正文、软换行、行内公式、块公式、加粗、行内代码、列表，逐步校验不变量。
- 四处修法：
  - `selectOutside`（`typora-patches.js`）：**空文本节点不算可落点**。它上面的位置会被 Chromium 归一化回前一个文本节点，而公式节点里的前一个文本节点正是零宽的 `$` 标记——于是"右方向键走出公式"把光标停在右 `$` 上，再按也走不出去；接着打的字被当成"在围栏上打字"塞回源码。
  - `fenceCaret`（`math-edit.js`）：行内公式的 `$` 有**内外两半**（开 `$` 之前/闭 `$` 之后是正文，内侧才是公式）。原来四者一律当"进源码"。外侧新增 `insertBeside`（直接建一个装着这段文字的文本节点，不落在位置型光标或空文本节点上）与 `standOutside`（输入法起手先归位）。
  - `patchMathCaret`（`typora-patches.js`）：光标在公式**外面**、方向键又朝着公式走时，把光标放进源码里（展开态由 Vditor 跟着光标挂上）。原来整块跳过。
  - 软换行（`patchSoftBreak`）：光标停在行内公式的 `$` 标记上时先归位到公式外侧的**真实文本位置**再插换行，否则换行写进标记文本里、"闭 `$` 之后"这个位置就没了。
- 块公式：核查后没有同类光标问题；打字落在光标处的源码里，`$$` 围栏不会被拆散。`$$\n…\n$$` 与 `$$…$$` 之间的换行差异是 Lute 自己收放围栏的形式，与光标无关。
- 验收：`scripts/acceptance/scenarios/101-inline-math-caret-2.1.29.cjs`（32 条断言 / 15 证人，含像素证人"进公式时源码展开、节点盒子变宽"与磁盘证人）。四条负对照逐条生效（撤掉哪一处、哪一条断言就失败）。
- 顺带修掉验收基座自身的缺陷：`harness.cjs` 记录 `app-stderr.log` 偏移时用的是**字节数**、读取时却按字符串 `slice`——日志里出现中文（如 KaTeX 的 `Unicode text character 甲 used in math mode`）后偏移就会错位，把本次的 `Debugger listening` 行整段切掉，表现为"同一个场景每次都说主进程调试器没接上"。

- 摆放位置的选择理由（写进代码注释备查）：按钮是工具栏自己的末项，所以任何窗口宽度都不会跟浮条自己重叠（右上角/左上角的独立浮标在窄窗口都会被顶到 `max-width` 的浮条压住），也避开了大纲栏（`margin-top` 把它推到工具栏带之下）、右下角缩放角标与滚动条；内容缩放只作用于 `.vditor-content`，按钮大小与位置不随缩放变化。
- 动画只动 transform / opacity / 颜色：收起先让其余项与浮条底色淡出（140ms），再把其余项 `display:none`、浮条改贴右上角，按钮用 FLIP 平移补位；展开反过来。**不收放任何布局**，一次点击只量两次 `getBoundingClientRect`。
- 与 `toolbar-autohide.js`（窗口太矮时自动收纳）互斥：手动收起时那条自动规则整体让位（`measure()` 不再启用、`reveal()` 直接返回），鼠标贴顶不会把它弹回来。
- 收起后浮条只剩透明壳子，因此 `pointer-events:none`、指针事件收回给按钮自己；其余项用的是 `display:none !important`——vditor 会按编辑模式给工具栏项写内联 `display`，不收 `!important` 实测会有 5 项留在浮条里。
- 收起会让 `outline-layout` 的 ResizeObserver 改写作区保留带（`--typora-toolbar-inner`），正文因此上移一次——这正是「把空间还给正文」的可见效果；143,656 字符 / 2002 块的大文件上实测无长任务（<50ms）。

### 窄窗口下标题级别角标左侧留白消失

## 2.1.7 (2026-09-14, private)

这一轮把「以前根本测不了」的一整类功能补上了：**系统原生对话框**（打开文件/打开文件夹/另存为/确认框）与
**应用菜单**。它们此前既没有自动化入口，也因此在下面这些日常操作上悄悄坏了很久。为此新建的验收能力见第八节。

### 一、开始界面（无文档启动）没有任何反馈
- 用户报：「新开一个无文档载入的开始界面，里面的打开文件夹和打开文件的功能就是坏的」。
- 取证：侧栏可见性是一条**持久化偏好**（一次 Ctrl+Alt+B 就一直收着）。侧栏收起来时点「打开文件夹」，
  文件树确实读出来了，但长在隐藏的侧栏里——屏幕上零变化（probe-welcome-battery2 的 R2）；侧栏开着时，
  欢迎页那句"已打开工作区，从左侧文件树选择"的提示只在**启动时**会话里就带工作区才显示（shell.js:110），
  用户主动打开文件夹反而拿不到任何反馈。
- 修复：`ws-open` 推送带 reveal 标记 → 侧栏自动展开 + 欢迎页补提示；启动时恢复的工作区仍尊重收起来的偏好。

### 二、正常退出把会话记录清空（重启只剩欢迎页）
- 现象：开两个文件窗口 → 正常退出 → 再打开，两个窗口都不回来；**强杀**反而能恢复。
- 根因：`win.on('close')` 一律 `detachRec()`（把该窗口从 state.windows 摘掉并写盘）。退出时所有窗口都会走
  这条路径，于是记录被逐条清空成 `[]`（对照实验 probe-session-restore：正常退出后 windows 2→0 条；
  强杀保留 2 条 → 恢复机制本身是好的）。
- 修复：加 `quitting` 标记（before-quit 置位）+「只剩一个窗口」判据：只有"关掉多个窗口中的一个"才摘除，
  退出（含关掉最后一个窗口）保留整套记录。既有 windows 套件断言（关闭的窗口从会话移除 / 退出确认链）全绿。

### 三、文件树「删除（回收站）」永远不生效
- 根因：外壳里用 `window.confirm()`，而实测（probe-confirm.cjs）它在 Electron 外壳页里**恒返回 false**、
  2ms 返回、不弹任何界面（`window.prompt` 直接抛 not supported，`alert` 同样什么都不显示）。
- 修复：改走主进程原生确认框（`shell:confirm-trash`），与"未保存修改""外部修改冲突"同一套；
  同一类问题顺带修掉：新建/重命名失败时的 `alert` 也换成侧栏里可见的错误条（`#sb-error`）。

### 四、菜单「在此窗口打开文件…」开的是新窗口
- 根因：`chooseFile()` 丢掉调用方给的 rec，直接 `openPaths(files)`，与「打开文件…」完全同一条路。
- 修复：`chooseFile(rec,{here})` → `openPathSmart(files[0],{rec})`（未保存会先确认），其余文件仍各开一窗。

### 五、点文内锚点链接没有任何反应
- 根因：主进程 `openLink()` 一上来 `if (uri.startsWith('#')) return`，渲染层也不管。
- 修复：渲染层 `scrollToAnchor()`：按标题文字/id/slug 匹配后 `scrollIntoView` + 1.6s 高亮。
- 踩坑（值得记）：IR 模式下 `<h3>` 的 textContent 是 **`### 第三节`**（带着源码标记），逐字比对全部落空
  ——第一版实现就是这么静默失败的（probe-anchor-steps.cjs 把每一步单独跑才看出来）。

### 六、Ctrl+多选图片之后按退格/Delete 没反应
- 用户报。两层原因：①删除处理器只认"单击选中的那一张"，`multiSelected` 集合被无视；
  ②更隐蔽的是 Ctrl+点选之后**编辑区 iframe 丢掉键盘焦点**（`document.hasFocus()` 变 false，
  实测 probe-img-del4），此后按键全部落到外壳文档，编辑区一个都收不到（连打字也进不去）。
- 修复：多选路径补回焦点（保留光标位置，选区补在下一个任务里做），删除一次处理整个多选集合，
  与 Ctrl+X 的多图语义一致（撤销可回退）。

### 七、矮窗口下补全面板压住正在编辑的那一行 / 鼠标
- 用户报（附截图）：「点积分符号时光标落点是对的，但提示框正好盖在鼠标上，一点就插进一个别的公式」。

### 一、根因：Blink 原生的右键选区行为，不是我们的代码

编辑区**当前没有选区**时，右键落在「放不下光标」的东西上（图片本体、包图片的 span.vditor-ir__node、行内/块公式渲染出的 KaTeX、contenteditable=false 的预览岛、原样 HTML 图片块、代码高亮岛），Blink 会走 SetSelectionFromNone：把选区设成整篇文档的内容、光标落到第 0 位。素材（305,561 字符 / 330 行，图片在文档 80% 处）上实测光标被扔到视口上方 7059px 的文档开头，此后第一次输入会插到文章最前面。

取证要点（scripts/acceptance/probe-*.cjs，七支探针）：

- iframe realm 里给 Selection.*、focus、scrollIntoView、scrollTop setter、window.scrollTo/scrollBy 全部套上带调用栈的记录器 → **一条记录都没有**（不是 JS 干的）；我们自己 contextmenu 里的 menu.focus() 记到的选区**已经是**文档开头 ⇒ 事情发生在我们之前。
- 只按下不抬起就已经在块 0 ⇒ 触发点是 mousedown；IR 里捕获阶段 preventDefault 就能挡住。
- WYSIWYG 下 preventDefault **挡不住**（记录器读到 defaultPrevented=true，光标照样在块 0）⇒ 那边 Blink 是在派发 mousedown 之前改的选区。
- 时间线采样（按下后 0/40/120/300/700/1200ms）发现 mouseup/contextmenu 会**再摆一次**：原样 HTML 图片块按下时补到块 4、抬手后又回块 0。
- 补出来的位置还要能用：用接着打一个字当判据，caretRangeFromPoint 与邻近可编辑文本两种补法都会把字打到**文档最前面**（磁盘上读到 # Q第一部分…），只有岛所在顶层块的边界之前这一种不会。

### 一、①是真缺陷：清空整篇之后光标落在公式源码里，接着打字会变成公式

**现象（真产物 2.1.4、真按键、探针 `scripts/acceptance/probe-empty-math-and-marker.cjs`）**：`Ctrl+A` 全选（实测选区 221 字符、非折叠）→ 一次退格 → markdown 只剩 `"$$\n\n\n$$\n"`（8 字符：一个被删空的块公式），而**光标在它的源码里**（实测 `inMathCode: true`、owner 已展开）→ 接着打 `abc`，实测得到 `"$$\nabc\n$$\n"`：字进了 TeX，屏幕上出现的是一段被当成公式渲染的斜体字，而不是用户想要的正文。**这不是"多了一个空壳"的观感问题，是"清空文档后打的第一句话会变成公式"**——2.1.4 把它记成"只观测、未改"是错的。

**归因（四条实验，只观测，都不是我们干的）**：

1. **不是我们的删除路径。** 只选中最后一条块公式再退格：实测删掉 15 字符、其余 196 字符原样留着；而全选那一下是 221 → 8（整篇都没了）。我们的删除只摘**一条**节点，两条不是一个路径。
2. **不是我们的键处理。** 用 `document.execCommand('delete')` 删（实测事件流里连 `beforeinput` 都没有，只有一条 `input`）照样留下同一个空壳、光标照样在源码里。
3. **是公式特有的形状。** 把文档换成"最后一块是围栏代码块"再全选退格：清空后只剩一个空段落（实测 `blocks: []`、`value: "\n"`），接着打字进的是正文。所以这不是通用的"删块"行为，也不是"空 `$$` 对本来就该留着"。
4. **WYSIWYG 模式（工具栏可切）不出现这个形状。** 同样手势后留下的是 `$$\na0+b0=1\n$$\n`、光标在编辑面上（`inMathCode: false`）——那里没有"光标落进源码"这回事，所以本轮没有动 wysiwyg 的任何行为（它自身的表现要单独取证）。

**修法**：只在"整篇被选中"这个前提下、且删完只剩一个**空的**块公式时，把那个壳换成空段落——复用既有的 `removeNode`（它本来就是"整条公式被删掉时换成空段落"的路径，撤消/保存走既有通道）。判据卡得很死，所以"用户自己 `$$` 回车新建的空公式块"不会被误伤：那条路径上没有"整篇被选中"，记号根本不会被置起来。

**改完实测（开发树、同一探针）**：清空后 `value: "\n"`、光标在空段落里（`inMathCode: false`）、接着打 `abc` 得到 `"abc\n"`（正文）；清空后**一次** `Ctrl+Z` 依旧逐字节回到原文——历史粒度没被多推一层（这是这条修法唯一可能伤到的地方，专门钉了读数）。已知未覆盖：既不发 `beforeinput`、也没有 keydown 的编程式删除（本产品的菜单里没有这种入口；Edit 菜单只有剪切，剪切会发 `deleteByCut`，属于已覆盖）。

## 2.1.3 (2026-09-13, private)

### 复现到的三个真实机制（都在安装版 2.1.2 上量到）

1. **点公式块下方的"留白"其实点进了隐藏的源码里。** 折叠态下块公式的源码 `pre` 是 `0×0` 的壳（实测几何），Chromium 会把落在这片留白上的点击解析成源码文本里的某个位置：同一片留白，靠左拿到 `TEXT@70`（源码末尾）、中间拿到 `TEXT@0`、更靠外还拿到 `pre@27`（渲染预览子树里的元素级位置）。于是"在 (2) 之前点一下再退格"= 删掉公式源码里的一个字符。产物级复现：`x+y=1` → `x+y=`（本版新增的验收断言把这一条钉死了）。
2. **段落贴边的保护只看同级兄弟，跨 blockquote 就漏。** 素材里 `> $$ … $$` 后面是一行**不带 `>` 的空行**，再跟 `> (2)`，于是 `(2)` 和上面那条公式分处两个 blockquote。2.1.2 的判定从段落往上只找同级兄弟，找不到公式就放行——Vditor 接手后把整段引用块的 `>` 前缀削掉（实测 `> (2)` → `(2)`、`> 证:` → `> 证:(1)`），用户读作"公式被删掉了"。
3. **点围栏把人塞进源码里（所见非所得）。** 2.1.2 的约定是"点前 `$$` = 光标落在源码开头、点后 `$$` = 源码末尾"。用户要的是光标**站在 `$$` 那里**；而这个落点再按退格就是删源码，正好又是同一句抱怨。

### 修复

- **折叠态的鼠标落点按几何归位**：点在公式块的空白留白上 → 光标落到公式块**之前/之后**（按点在上半还是下半），公式**不展开**、光标不落在隐藏源码里；点在渲染结果上照旧交给 Vditor（点公式 = 展开源码，把光标放进源码）；展开态下点围栏 → 光标**就停在 `$$` 自己身上**（`$` 前 / 两个 `$` 之间 / `$` 后都能站，按点击的横向位置决定）。带修饰键的点击、双击/三连击不接管，拖选与选词不受影响。
- **段落贴边改成沿祖先链找相邻公式**：同级兄弟没有就往上找，父级的兄弟**末尾/开头**是块公式同样拦下（修掉上面第 2 条）。
- **贴边/围栏位置只做两件事，文档一个字节都不改**：光标停在**看不见**的位置（零宽 `$` 标记、owner 缝隙）才把它挪到最近的可见文字位；已经站在看得见的位置（围栏、相邻段落首尾、预览子树）就原地不动，只弹一句说明。头一回把"没反应"变成"有解释"。
- **围栏上打字 / 粘贴 / 输入法**：字符只能进源码，落到点击那一端（前围栏→源码开头，后围栏→源码末尾），围栏与 markdown 都不会被写坏。块公式的 `$$` 标记再也不会持有游离字符（`recoverMarkerInput` 扩到块公式）。

### 如实说明（仍旧做不到的那件事，以及新量到的数字）

用户在报告里把"源码编辑只会删掉最后一个 dollar 符"当期望，但**渲染态里 `$$` 不是文档里的字符**，所以"按一下退格删掉一个 `$`"做不到。本轮把代价量清楚了（三条都是实测）：

1. 直接改围栏 span 的文本（`$$`→`$`、`$$`→`$$$$`）后 `getValue()` **一个字节都不变**——围栏是 Lute 每次重排生成的标记，不参与序列化。
2. 真去改 markdown（把闭合围栏写成 `$`）会让 Lute **重新配对围栏**：实测闭合围栏少一个 `$` 后，紧随其后的 `> (2)` 那一行被**吞进公式源码**里（`code.textContent` 末尾出现 `(2)`），公式渲染成垃圾；开场围栏少一个 `$` 则把**下一条公式的开场 `$$` 拉上来**当自己的闭合围栏。
3. 改 markdown 只能整篇重排（`setValue`）：2 万字素材 **24 ms**，49 万字（348K 字符 / 5634 条公式）**2.0–2.2 s**，而且重排前后**不是逐字节相同**（Lute 会顺带规范化别处的内容）——等于用一个"删一个 `$`"的按键去动整篇文档。

所以本版的选择是：**围栏成为真实可站的光标位置（用户要的"自由插入到 `$` 的位置"做到了），但围栏上按退格不改文档，并当场说明原因与正路（源码视图里 `$$` 就是文本，逐字符删正是那里的事）**。要整条删公式：选中它再按 `Backspace`/`Delete`（干净、无残渣）。

## 2.1.1 (2026-09-12, private)

全部是「光标停在公式边上」这一类编辑手感的修复，来自用户在同一份排版测试文档里的报告与随后的一轮奇怪操作巡检。每条都先复现、再修、再拿修复前的渲染层跑同一套断言做基线差分（新套件 16 条：修复前 28 条失败 / 5 条通过，修复后 16 条全通过）。

- **行尾公式弹出预渲染框**：光标插在一行最后、而这一行以公式的 `$` 结尾时，Vditor 会按「光标所在节点」把最后一个公式展开、浮出预渲染框。现在贴边的光标不算在编辑公式（`formulaEdge` 区分「外层边界」与「源码边界」），并且会把 Vditor 自己挂上的 `--expand` 收回来；收回后若光标最终落在源码里（点公式正中就是这种时序）会再确认一遍，避免把该展开的也收掉。
- **块公式的 `$$` 无法落光标**：`$$` 原本是 `::before/::after` 伪元素，不参与命中测试，展开后无论点哪儿光标都只能停在源码第 0 个位置。改为展开态显示真实 `$$` 文本节点（并 `content:none` 关掉伪元素，避免画两遍），实测前 `$$` 里能落在两个字符位置上、尾 `$$` 也能点。
- **贴边退格毁公式（4 种形状）**：①光标作为节点首/尾子位置（Chromium 在行尾的常用落点）退格会吃掉收尾的 `$`；②块公式源码开头退格会把 `$$` 围栏拆掉、整块散成一行文本；③行内公式源码末尾删除会整条消失；④紧邻段落的段首退格/段尾删除会把块公式并进段落文本。现在这四类位置的第一下只**选中整条公式**（文档不动），第二下整体删除；**向内**的正常改字（源码末尾退格、源码开头删除）不受影响。
- **整条公式选中后删除留残渣**：浏览器删 `div[data-type="math-block"]` 会在 markdown 里留下字面 `span`，并连带吃掉后面的段落；改为自己摘节点（块公式换成一个空段落，行内公式留一个零长文本锚点）。
- **公式源码里的格式快捷键**：`Ctrl+B`/`Ctrl+I`/`Ctrl+U` 会把 `****`/`**`/`<u></u>` 插进 TeX 源码（实测 `$a+1$` → `$a****+1$`）。公式源码内不再响应格式命令（剪贴板、撤销重做、全选照旧）。
- **公式源码里的回车**：行内公式源码里回车会拆断 TeX（实测 `$a+1$` → `$a$a+1+1$`），现在只把光标移到公式之后、不改文档；块公式是多行源码，回车照旧换行。

### 一、打开文档时滚动位置被反复重写满 6 秒
`render/js/util.js`：锚点误差 `anchorError()` 的两项相减顺序写反，返回的是 **2×偏差**
（实测 delta=1 → 2、delta=−11 → 22），永远越不过 `<= 2` 的收敛线，于是 ticker/poll 一直贴到
`ANCHOR_GIVE_UP_MS`(6000ms) 才收工（实测 applies=76；修好后 13 次、约 1.1 秒收工）。同时
